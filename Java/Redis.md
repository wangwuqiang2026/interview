## **<font style="color:rgb(51,51,51);">什么是 Redis？</font>**
Redis 是一个基于**内存的高性能键值型数据库**，它采用 C 语言开发，数据主要存储在内存中，因此具有非常高的读写性能。Redis 不仅支持简单的字符串类型，还支持 **Hash、List、Set、ZSet、有序集合、Bitmap、HyperLogLog、Geo 等多种数据结构**，可以满足缓存、计数、排行榜、分布式锁、消息队列等多种业务场景。  

| 特点 | 说明 |
| --- | --- |
| 基于内存 | 数据主要存储在内存中，读写速度非常快 |
| Key-Value 存储 | 通过 key 查询 value，例如 `user:1001 → 用户信息` |
| 高性能 | 单机 Redis 可以支持几十万级 QPS |
| 丰富数据结构 | 不只是简单字符串，还支持集合、列表等 |
| 支持持久化 | 可以将内存数据保存到磁盘 |
| 支持高可用 | 支持主从、哨兵、集群 |






## **<font style="color:rgb(51,51,51);">Redis 有什么优点和缺点</font>**
Redis 的优点主要有以下几个方面：第一，**性能非常高**，Redis 基于内存存储，读写速度非常快，同时采用单线程事件循环模型，避免了线程切换和锁竞争，并通过 I/O 多路复用提升并发处理能力；第二，**支持丰富的数据类型**，除了常见的 String，还支持 Hash、List、Set、Sorted Set、Bitmap、HyperLogLog、Geo 等，可以满足缓存、排行榜、计数器、消息队列等多种业务场景；第三，**提供了丰富的功能机制**，比如持久化（RDB、AOF）、主从复制、哨兵模式、集群模式，可以保证数据可靠性和高可用；第四，**支持分布式场景**，可以通过 Redis Cluster 实现数据分片和水平扩展；第五，**使用简单**，命令丰富，开发成本较低。  

| 优点 | 说明 | 应用场景 |
| --- | --- | --- |
| 高性能 | 数据存储在内存，读写延迟低 | 缓存热点数据 |
| 丰富的数据类型 | 支持 String、Hash、List、Set、ZSet 等 | 排行榜、计数器、消息队列 |
| 高并发能力 | I/O 多路复用 + 单线程事件模型 | 秒杀、接口限流 |
| 支持持久化 | RDB 快照、AOF 日志 | 数据恢复 |
| 高可用 | 主从复制、哨兵、Cluster | 分布式系统 |
| 扩展性强 | Redis Cluster 数据分片 | 大规模业务 |


Redis 的缺点主要有以下几个方面：第一，**数据存储在内存中，成本较高**，相比 MySQL 等磁盘数据库，Redis 单位容量的存储成本更高；第二，**数据容量受到内存限制**，不适合存储大量冷数据；第三，**数据可靠性相比关系型数据库较弱**，虽然 Redis 提供了 RDB 和 AOF 持久化机制，但是由于数据主要在内存中，如果配置不合理，仍然可能存在数据丢失风险；第四，**单线程模型存在瓶颈**，虽然 Redis 单线程性能很高，但是如果执行一些耗时操作，比如大 Key 删除、复杂集合运算，会阻塞其他请求；第五，**数据一致性较难保证**，在缓存场景中，需要处理缓存穿透、缓存击穿、缓存雪崩以及缓存和数据库的数据一致性问题。  

| 缺点 | 说明 | 解决方式 |
| --- | --- | --- |
| 内存成本高 | 内存价格比磁盘高 | 只存热点数据 |
| 容量有限 | 受服务器内存限制 | 集群扩容 |
| 数据可靠性弱于数据库 | 可能丢失少量数据 | 开启 AOF、主从复制 |
| 大 Key 问题 | 操作可能阻塞 Redis | 拆分 Key、渐进删除 |
| 数据一致性问题 | 缓存和数据库可能不一致 | Cache Aside 模式 |
| 单线程瓶颈 | 慢命令阻塞请求 | 避免复杂操作 |








## Redis 为什么速度快？  
 ① Redis 基于内存存储数据，避免了磁盘 I/O 带来的性能开销，数据读写直接操作内存    

 ②  Redis 使用单线程模型处理核心请求，避免了多线程上下文切换和锁竞争带来的开销，同时通过 I/O 多路复用技术，可以同时处理大量客户端连接    

 ③  Redis 底层采用高效的数据结构，比如 String、Hash、List、Set、ZSet 等，并针对不同场景进行了优化，例如跳表、压缩列表等，使数据操作效率更高  

 ④Redis 的通信协议简单，采用 RESP 协议，减少了网络传输和解析的开销  

 ⑤Redis 采用事件驱动模型，通过事件循环处理请求，使 CPU 利用率更高   

| 数据类型 | 底层结构 | 优势 |
| --- | --- | --- |
| String | SDS动态字符串 | 查询快、减少内存浪费 |
| Hash | 哈希表 | O(1)查询 |
| List | quicklist | 插入删除效率高 |
| Set | 哈希表 | 快速判断成员存在 |
| ZSet | 跳表 + 哈希表 | 支持范围查询和排序 |






## Redis 的 I/O 多路复用是什么？
Redis 的 I/O 多路复用是一种**高性能网络通信模型**，它允许 Redis 使用**一个线程同时监听和处理多个客户端连接**，从而提高服务器的并发处理能力。

传统的阻塞 I/O 模型中，一个连接通常需要一个线程处理，当客户端数量增加时，会创建大量线程，导致线程切换开销变大。而 Redis 采用 I/O 多路复用技术，通过操作系统提供的机制（如 Linux 下的 **epoll**），让一个线程同时监听多个 socket，当某个连接有数据到达时，操作系统通知 Redis，Redis 再处理对应请求。

Redis 本身采用**单线程事件循环模型**，主线程通过 I/O 多路复用监听大量客户端连接，然后按照事件类型执行对应操作。由于 Redis 的操作主要是内存操作，执行速度非常快，因此通过这种方式可以实现高并发处理。





## **<font style="color:rgb(51,51,51);">Redis 为什么设计成单线程的？</font>**
Redis 设计成单线程主要是为了**简化实现、减少线程切换开销，并利用内存操作速度快的特点提高整体性能**。Redis 的核心瓶颈通常不是 CPU，而是网络 I/O 和内存访问，因此采用单线程模型可以避免多线程之间的锁竞争、上下文切换以及数据同步问题，让命令执行过程更加简单高效。同时，Redis 使用 **I/O 多路复用技术**，可以让一个线程同时处理大量客户端连接，当多个客户端请求到达时，Redis 会通过事件驱动模型依次处理命令。由于 Redis 的数据都存储在内存中，命令执行速度非常快，所以单线程已经能够支撑很高的并发量。不过，Redis 单线程主要指**命令执行核心线程是单线程**，在 Redis 6.0 之后，也引入了多线程网络 I/O 来处理请求读写，但真正执行 Redis 命令的部分仍然保持单线程。  

| 设计原因 | 作用 |
| --- | --- |
| 避免线程切换 | 降低 CPU 消耗 |
| 避免锁竞争 | 提高执行效率 |
| 保证命令原子性 | 简化数据一致性 |
| I/O 多路复用 | 支撑高并发连接 |
| 内存操作快 | 单线程已经足够 |
| 简化代码设计 | 提高稳定性 |






## Redis 为什么单线程还能支持高并发？  
Redis 单线程之所以能够支持高并发，主要是因为 Redis 的单线程指的是**执行核心命令的线程是单线程**，并不是整个 Redis 都只有一个线程。Redis 通过 **I/O 多路复用机制**，让一个线程可以同时监听和处理大量客户端连接，避免了传统多线程模型中线程创建和上下文切换带来的性能损耗。

另外，Redis 的数据主要存储在**内存中**，大部分操作都是非常快速的内存读写，不需要频繁访问磁盘，所以命令执行速度非常快。同时，Redis 使用了高效的数据结构，并且采用事件驱动模型，使得单线程能够充分利用 CPU。

因此，Redis 单线程高性能主要依赖三个方面：**基于内存操作、I/O 多路复用、高效的数据结构和事件驱动模型**。不过，Redis 单线程也存在限制，如果执行耗时命令（例如大范围 `keys` 查询、大数据量排序等），会阻塞后续请求，所以 Redis 需要避免执行慢命令。





## **<font style="color:rgb(51,51,51);">Redis 的线程模型</font>**
Redis 的线程模型可以分为两个阶段来看。Redis 3.x 之前主要采用**单线程模型**，也就是由一个主线程负责处理客户端请求、命令解析以及命令执行。Redis 6 之后引入了**多线程网络模型**，将网络 I/O 的读写操作交给多个线程处理，而核心的命令执行仍然由主线程完成。

整体流程是：客户端请求到达 Redis 后，首先通过 I/O 多路复用监听多个客户端连接，当有请求事件发生时，网络线程负责读取请求数据，然后交给主线程执行具体命令，执行完成后再由网络线程负责返回响应。Redis 采用这种模型的原因是命令执行通常是内存操作，速度非常快，多线程执行命令反而会引入锁竞争和线程切换开销，而网络 I/O 才是高并发场景下更容易成为瓶颈的部分。因此 Redis 通过“多线程处理网络 I/O + 单线程执行命令”的方式，在保证数据操作简单高效的同时，提高了整体吞吐量。

## **<font style="color:rgb(51,51,51);">为什么要用缓存</font>**
① 提高访问速度  

② 降低数据库压力  

③ 提升系统吞吐量  

④ 降低服务响应时间  

⑤ 保护数据库，防止系统雪崩  

在项目中使用缓存，主要是为了**提高系统访问速度和降低数据库压力**。因为数据库通常是系统中的瓶颈，尤其是在高并发场景下，大量请求直接访问数据库，会导致数据库连接数增加、查询压力变大，甚至影响整个系统的稳定性。

缓存一般将**访问频率高、变化不频繁的数据提前存储在内存中**，当用户再次访问时，可以直接从缓存中获取数据，而不需要查询数据库。由于内存的读写速度远高于磁盘数据库，所以可以显著降低响应时间，提高系统吞吐量。

除此之外，缓存还可以起到**削峰填谷**的作用。例如秒杀活动中，大量用户同时请求商品信息，如果全部访问数据库，很容易造成数据库压力过大，通过缓存可以让大量请求先访问缓存，保护后端数据库。

## 缓存和数据库如何保证一致性？  
查询数据时，首先查询缓存，如果缓存存在则直接返回；如果缓存不存在，则查询数据库，将查询结果写入缓存后返回。

更新数据时，不直接更新缓存，而是先更新数据库，数据库更新成功后，再删除对应的缓存。之所以采用“更新数据库后删除缓存”，是因为数据库是数据的最终存储来源，缓存只是数据库的一个副本，删除缓存可以避免缓存中保存旧数据，下一次查询时会重新从数据库加载最新数据。

## Redis 缓存刷新策略有哪些？
Redis 缓存刷新策略主要有三种：**定时刷新、主动更新、被动更新（惰性删除）**。其中最常用的是**主动更新 + 过期淘汰**的 Cache Aside 模式。

第一种是**定时刷新策略**，即通过定时任务按照固定时间周期刷新缓存，例如每天凌晨重新加载热点数据。这种方式实现简单，适合数据变化频率低、对实时性要求不高的场景。

第二种是**主动更新策略**，也叫 Cache Aside 模式。当业务数据发生变化时，先更新数据库，然后删除 Redis 中对应的缓存；下一次查询时，如果缓存不存在，再从数据库读取最新数据并重新写入 Redis。这种方式可以保证数据库和缓存的一致性，是企业项目中最常用的方案。

第三种是**被动更新策略**，也叫惰性刷新，即给 Redis 设置过期时间 TTL，当缓存过期后，访问该数据时发现缓存不存在，再重新从数据库加载数据写入缓存。这种方式可以避免缓存长期保存旧数据。

除此之外，在一些高并发场景中，还会使用**延迟双删、消息队列异步刷新、Canal监听数据库变化等方式**进一步提高缓存一致性

| 策略 | 原理 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| 定时刷新 | 定时加载数据 | 简单稳定 | 实时性低 | 配置、字典 |
| 主动更新 | 改库后删缓存 | 一致性较好 | 需要业务控制 | 大多数业务 |
| 被动更新 | TTL过期重建 | 简单 | 首次访问慢 | 普通缓存 |
| 延迟双删 | 更新前后删除 | 一致性更强 | 增加复杂度 | 高并发 |
| MQ异步刷新 | 消息驱动 | 解耦、高性能 | 引入MQ | 大型系统 |
| Canal同步 | 监听binlog | 自动同步 | 架构复杂 | 大规模系统 |

## Redis 的同步机制是什么？
Redis 的同步机制主要是指 **Redis 主从复制（Replication）机制**，用于实现数据在主节点和从节点之间的同步。Redis 主从同步分为**全量同步和增量同步**两种方式。当从节点第一次连接主节点或者无法进行部分同步时，会触发全量同步，主节点会生成 RDB 快照文件并发送给从节点，从节点加载快照完成数据恢复；当主从节点之间网络正常，只是部分数据存在差异时，会采用增量同步，主节点将复制积压缓冲区中的写命令发送给从节点，从节点执行这些命令完成数据追平。Redis 通过复制偏移量（offset）、复制积压缓冲区（replication backlog）以及运行 ID（runId）来判断是否可以进行部分同步。通过主从复制机制，Redis 可以实现数据备份、读写分离以及提高系统可用性。  

![](https://cdn.nlark.com/yuque/__mermaid_v3/089b230d0d66d788b861eb45fd08bad4.svg)

| 同步方式 | 触发条件 | 同步内容 | 性能 |
| --- | --- | --- | --- |
| 全量同步 | 首次连接、数据差距过大 | RDB文件+缓冲命令 | 较慢 |
| 增量同步 | 短暂断开 | 复制积压缓冲区命令 | 较快 |
| 持续复制 | 正常运行 | 实时传播写命令 | 最快 |






##  Redis 为什么需要主从复制？  
Redis 需要主从复制主要是为了**提高系统的高可用性、读写性能和数据安全性**。在单机 Redis 中，所有数据都存储在一个节点上，如果 Redis 节点发生宕机，就会导致服务不可用，同时数据也可能丢失。而通过主从复制，可以让一个主节点（Master）将数据同步给多个从节点（Replica），当主节点故障时，可以通过哨兵或者集群机制选举新的主节点，实现故障转移，提高系统可用性。另外，在高并发场景下，可以让主节点负责写操作，从节点负责读操作，通过读写分离分担主节点压力，提高 Redis 的吞吐能力。同时，从节点还可以作为数据备份节点，避免主节点数据丢失。因此，Redis 主从复制主要解决了**单节点故障问题、读压力过大问题以及数据备份问题**，是 Redis 实现高可用架构的重要基础。  

| 作用 | 说明 | 解决的问题 |
| --- | --- | --- |
| **故障恢复，提高可用性** | 主节点数据复制到从节点，主节点宕机后可以切换从节点作为新的主节点 | 避免 Redis 单点故障 |
| **读写分离，提高性能** | 主节点负责写数据，从节点负责读数据 | 降低主节点读压力，提高并发能力 |
| **数据备份，提高安全性** | 从节点保存完整的数据副本 | 防止数据丢失 |






## Redis 为什么主从复制会丢数据？  
Redis 主从复制会丢数据，主要是因为 **Redis 默认采用异步复制机制，主节点执行写命令后，不需要等待从节点确认同步完成就会返回成功**。如果主节点刚写入数据，还没有同步给从节点时突然宕机，那么这些数据就会丢失。另外，在故障转移过程中，如果选择了一个数据不完整的从节点作为新的主节点，也可能导致部分数据丢失。因此，Redis 主从复制的数据丢失主要分为两种情况：**主节点故障导致异步复制的数据未同步丢失，以及故障切换过程中从节点数据不一致导致丢失**。  





## 如何减少主从复制的数据丢失？
**方案一：开启复制安全策略  **  

min-replicas-to-write 1  表示：至少有一个从节点连接正常时，Master 才允许写入。

min-replicas-max-lag 10  表示：从节点超过 10 秒没有同步，Master停止写入。作用：降低数据丢失概率。

**方案二：使用 Redis Sentinel  **

Sentinel 可以：监控 Master、自动故障转移、选择较新的 Replica、减少人工切换造成的数据丢失**。**

**方案三：使用 Redis Cluster  **

Cluster：数据分片、主从复制、自动故障转移、提高整体可用性**。**







## Redis 如何保证数据不丢失？  
Redis 保证数据不丢失主要通过**持久化机制、高可用机制和数据备份机制**来实现。

首先，在持久化方面，Redis 提供了 **RDB 和 AOF 两种持久化方式**。RDB 是按照一定时间间隔生成数据快照，将内存中的数据保存到磁盘中，恢复速度较快，但是可能会丢失最近一次快照之后的数据；AOF 是记录每一次写操作命令，通过重新执行这些命令来恢复数据，数据可靠性更高，但是文件体积较大，恢复速度相对较慢。在实际生产环境中，通常会采用 **AOF + RDB 混合持久化**，既保证恢复速度，又减少数据丢失风险。

其次，Redis 还可以通过**主从复制和哨兵机制**提高数据可靠性。主节点会将数据同步给从节点，当主节点宕机时，哨兵可以检测故障并进行故障转移，将某个从节点提升为新的主节点，避免服务不可用。

另外，在 Redis Cluster 集群环境中，可以通过**数据分片和副本机制**提高容灾能力，每个分片都有多个副本节点，即使部分节点故障，也可以保证数据继续提供服务。

**持久化机制：**

| 持久化方式 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| RDB | 定期生成内存快照 | 文件小，恢复快 | 可能丢失最后一次快照后的数据 |
| AOF | 记录每次写命令 | 数据安全性更高 | 文件较大，恢复慢 |
| 混合持久化 | RDB + AOF结合 | 恢复速度快，数据可靠 | 配置复杂 |


**优化方案：**

| 优化方式 | 作用 |
| --- | --- |
| 开启 AOF | 保存写操作 |
| 使用 everysec 刷盘 | 平衡性能和安全 |
| 开启主从复制 | 增加副本 |
| 使用 Sentinel/Cluster | 自动故障转移 |
| 避免关闭持久化 | 防止重启丢数据 |
| 定期备份 RDB | 防止灾难恢复 |






## AOF 为什么默认每秒刷盘，而不是每次刷盘？  
AOF 默认每秒刷盘而不是每次刷盘，主要是为了**在数据安全性和性能之间取得平衡**。如果每执行一条 Redis 写命令都立即刷盘（always 策略），虽然可以最大程度保证数据不丢失，但是每次写操作都需要进行磁盘 I/O，会严重降低 Redis 的性能。而每秒刷盘（everysec）会先将写命令追加到 AOF 缓冲区，由后台线程每秒执行一次 fsync 刷盘，这样既能保证较高的写入性能，又能将数据丢失控制在最多 1 秒左右。因此 Redis 默认选择 everysec 策略，在性能和数据可靠性之间做折中。  





## RDB 和 AOF 有什么区别？  
RDB 和 AOF 都是 Redis 提供的数据持久化方式，主要区别在于**数据保存方式不同**。RDB 是通过**定期生成内存快照**的方式保存数据，它会在某个时间点将 Redis 中的全部数据写入磁盘，恢复速度比较快，但是由于是定时保存，所以可能会丢失最后一次快照之后的数据。AOF 是通过**记录 Redis 每一次写操作命令**来实现持久化，Redis 重启时会重新执行这些命令恢复数据，因此数据安全性更高，但是文件体积较大，恢复速度相对较慢。  

| 对比项 | RDB | AOF |
| --- | --- | --- |
| 全称 | Redis Database | Append Only File |
| 持久化方式 | 数据快照 | 记录写命令 |
| 保存内容 | 某个时间点的全部数据 | Redis执行过的写操作 |
| 文件类型 | 二进制文件 | 文本文件 |
| 数据恢复速度 | 快 | 较慢 |
| 数据安全性 | 较低 | 较高 |
| 文件大小 | 小 | 大 |
| 对性能影响 | 较小 | 相对较大 |
| 适用场景 | 数据备份、灾难恢复 | 对数据可靠性要求高的场景 |






## Redis 为什么默认开启 RDB，而不是 AOF？  
Redis 默认开启 RDB 而不是 AOF，主要是因为 **RDB 在性能、恢复速度和资源占用方面更适合作为 Redis 的默认持久化方案**。RDB 是通过定期生成数据快照保存数据，持久化过程对 Redis 主线程影响较小，而且生成的文件体积更小，恢复数据速度更快，适合 Redis 作为缓存场景使用。而 AOF 虽然数据可靠性更高，可以减少数据丢失，但需要记录每条写命令，文件体积更大，恢复速度更慢，同时会带来一定的性能开销。因此 Redis 默认选择 RDB，在保证基本数据安全的同时，优先考虑 Redis 的高性能特点。不过在对数据可靠性要求较高的业务中，通常会开启 AOF，或者同时开启 RDB 和 AOF。  





## Redis 重启恢复时优先加载哪个文件？
Redis 重启恢复数据时，**如果同时开启了 AOF 和 RDB 持久化，Redis 会优先加载 AOF 文件进行数据恢复**。原因是 AOF 记录的是 Redis 的写操作命令，数据通常比 RDB 快照更加完整，能够恢复到更接近宕机前的状态。  

![](https://cdn.nlark.com/yuque/__mermaid_v3/88d51f37d032952dc3f80c9fc2770e04.svg)





## AOF 为什么会越来越大？如何解决  
 Redis 的 AOF 文件会越来越大，是因为 **AOF 采用追加写命令的方式记录每一次写操作，即使同一个 key 被多次修改，历史命令也不会被删除**。例如一个 key 从 `100` 修改到 `200`，再修改到 `300`，AOF 文件中会保存这三次操作，随着运行时间增长，AOF 文件会不断累积。为了解决 AOF 文件过大的问题，Redis 提供了 **AOF 重写（rewrite）机制**，它会根据当前 Redis 内存中的最新数据重新生成一个新的 AOF 文件，只保留最终状态对应的命令，从而压缩文件大小。同时，Redis 会在后台子进程中进行重写，避免阻塞主线程。  

可以设置 `auto-aof-rewrite-percentage 100 ``auto-aof-rewrite-min-size 64mb  `，表示当AOF 文件超过 64MB、当前大小比上次重写增长超过100%触发重写。





## AOF 重写期间有新的写命令怎么办？ 
AOF 重写期间如果有新的写命令，Redis **不会阻塞客户端写入**，而是采用 **AOF 重写缓冲区（AOF Rewrite Buffer）** 来保存重写期间产生的新写命令。

具体流程是：Redis 通过 `fork()` 创建子进程执行 AOF 重写，子进程根据当前内存数据生成新的 AOF 文件；与此同时，主进程继续处理客户端请求，并将新的写命令同时写入**旧 AOF 文件**和**AOF 重写缓冲区**。当子进程完成重写后，主进程会将 AOF 重写缓冲区中的新增命令追加到新的 AOF 文件末尾，最后使用新的 AOF 文件替换旧文件，完成重写。

这样既保证了 **AOF 重写期间客户端可以正常写入**，又保证了**重写后的 AOF 文件包含完整的数据变化，不会丢失重写期间的新数据**。 

![](https://cdn.nlark.com/yuque/__mermaid_v3/f10d6ebc2e7a6d1e7236c5bac49ee612.svg)





## AOF Rewrite 和 AOF Append 有什么区别？  
AOF Append 和 AOF Rewrite 都是 Redis AOF 持久化机制中的操作，但是它们的目的完全不同。

**AOF Append** 是将 Redis 执行过的每一次写命令追加保存到 AOF 文件中，用于记录数据变化过程，保证数据可以恢复；**AOF Rewrite** 是根据 Redis 当前内存中的最终数据状态，重新生成一个新的 AOF 文件，用于压缩 AOF 文件大小，提高恢复速度。





## Redis 主节点宕机后，如何实现故障转移？ 
Redis 主节点宕机后的故障转移主要通过 **Redis Sentinel（哨兵机制）** 实现。Sentinel 会持续监控 Redis 主点、从节点以及其他 Sentinel 节点的状态，当发现主节点不可用时，会先通过**主观下线和客观下线机制**判断主节点是否真正宕机。如果确认主节点故障，Sentinel 会从多个从节点中选择一个合适的节点提升为新的主节点，然后通知其他从节点复制新的主节点，同时更新客户端访问地址，使客户端重新连接新的主节点，从而完成自动故障转移。整个过程包括**故障检测、选举 Sentinel 领导者、选择新的主节点、执行故障转移、通知客户端**几个阶段。 

![](https://cdn.nlark.com/yuque/__mermaid_v3/b573d0e2f18aac89dc52916fd8a985a2.svg)





## **<font style="color:rgb(51,51,51);">pipeline 有什么好处，为什么要用 pipeline？</font>**
 Redis Pipeline（管道）主要用于**批量执行多个 Redis 命令，减少客户端与 Redis 服务器之间网络往返次数（RTT），从而提高 Redis 的吞吐量**。

正常情况下，客户端执行一条 Redis 命令，需要发送请求、等待 Redis 执行、接收响应，然后才能执行下一条命令，这种频繁的网络交互会产生较大的网络开销。而 Pipeline 可以一次性将多个命令发送给 Redis，Redis 依次执行这些命令后，再一次性返回所有结果，从而减少网络通信次数，提高执行效率。不过需要注意，Pipeline 只是减少网络 IO，并不会让 Redis 命令并行执行，Redis 仍然按照单线程顺序执行这些命令，同时 Pipeline 中的命令不具备事务特性，如果需要保证原子性应该使用 Redis 事务或 Lua 脚本。

## Pipeline和事务有什么区别？  
Redis Pipeline 和事务的主要区别在于：**Pipeline 是为了提高 Redis 的执行性能，而事务是为了保证多个命令执行的原子性。** Pipeline 通过一次性发送多个 Redis 命令，减少客户端和 Redis 服务器之间的网络往返次数，从而提高吞吐量，但是这些命令并不会作为一个整体执行，执行过程中某条命令失败，其他命令仍然会继续执行。而 Redis 事务通过 `MULTI` 和 `EXEC` 将多个命令包装成一个事务，保证这些命令按照顺序一次性执行，但是Redis 事务并不支持回滚。因此，Pipeline 关注的是**性能优化**，事务关注的是**命令执行的一致性和隔离性**。  

| 对比 | Pipeline | Redis事务 |
| --- | --- | --- |
| **主要目的** | 提高性能，减少网络开销 | 保证多个命令作为一个整体执行 |
| **核心机制** | 批量发送命令 | `MULTI`+ `EXEC` |
| **是否保证原子性** | ❌ 不保证 | ✅ 保证命令执行过程不被其他客户端打断 |
| **是否支持回滚** | ❌ 不支持 | ❌ 不支持 |
| **命令执行方式** | 批量发送，Redis依次执行 | 进入队列，EXEC时统一执行 |
| **适用场景** | 批量操作数据 | 多个操作必须一起完成 |
| **性能** | 更高 | 相对较低 |






## Redis事务  
Redis 事务是指**将多个 Redis 命令放入一个执行队列中，然后按照顺序一次性执行**，从而保证这些命令执行过程的连续性。Redis 事务主要通过 **MULTI、EXEC、WATCH、DISCARD** 等命令实现。

Redis 事务的执行流程是：客户端发送 `MULTI` 开启事务，之后发送的命令不会立即执行，而是进入事务队列；当客户端发送 `EXEC` 时，Redis 会按照命令进入队列的顺序依次执行。

Redis 事务具有**原子性、一致性、隔离性**，但是不保证严格意义上的持久性。需要注意的是，Redis 事务和 MySQL 事务不同，它**不支持回滚**。如果事务执行过程中某条命令失败，Redis 不会自动撤销已经执行成功的命令，而是继续执行后续命令。

| 命令 | 作用 |
| --- | --- |
| MULTI | 开启事务 |
| EXEC | 执行事务 |
| DISCARD | 取消事务 |
| WATCH | 监视 Key，实现乐观锁 |
| UNWATCH | 取消监视 |

## Redis事务为什么不支持回滚？  
Redis 事务不支持回滚，主要是因为 **Redis 设计理念追求高性能和简单性，而回滚机制会增加系统复杂度并降低执行效率**。Redis 事务中的命令在执行过程中如果出现错误，Redis 不会撤销已经执行成功的命令，而是继续执行后续命令。Redis 认为大部分错误可以在执行前被发现，例如命令格式错误、参数错误等，而运行时错误（例如数据类型错误）属于业务问题，应该由应用层处理。因此 Redis 采用了“命令顺序执行 + 不回滚”的设计，而不是像 MySQL 一样通过 undo log、锁机制等实现完整事务回滚。

## Redis事务如何保证原子性？  
Redis 事务只能保证**有限的原子性**，并不是像 MySQL 事务一样提供完整的原子性。Redis 通过 `MULTI` 和 `EXEC` 命令将多个操作放入一个事务队列中，在执行 `EXEC` 时，Redis 会按照入队顺序一次性执行这些命令，并且执行过程中不会被其他客户端插入命令，从而保证事务内命令执行的连续性。但是 Redis 不支持回滚，如果事务执行过程中某条命令失败，已经成功执行的命令不会撤销。因此 Redis 事务保证的是**执行过程的原子性（整体执行、不被打断）**，而不是**结果的原子性（全部成功或全部失败）**。  





## **<font style="color:rgb(51,51,51);">怎么使用 Redis 实现消息队列？</font>**
Redis 实现消息队列主要有三种方式：**List、Pub/Sub、Stream**。其中在生产环境中最推荐使用 **Redis Stream**。

第一种是使用 **List 实现消息队列**，利用 Redis 的 `LPUSH` 和 `BRPOP` 命令实现生产者和消费者模型。生产者将消息放入 List，消费者从 List 中阻塞获取消息。这种方式实现简单，支持阻塞消费，但是不支持消息确认、消息持久化管理和消费者组，不适合复杂业务场景。（`BRPOP`<font style="color:rgb(51,51,51);">在没有消息的时候，它会阻塞住直到消息到来</font>）

第二种是使用 **Pub/Sub 发布订阅模式**，生产者发布消息，消费者订阅频道接收消息。这种方式实时性较高，但是消息不会持久化，如果消费者不在线，消息会直接丢失，因此可靠性较低。

第三种是使用 **Redis Stream**，这是 Redis 5.0 引入的专门用于消息队列的数据结构。Stream 支持消息持久化、消费者组、消息确认机制，可以实现类似 Kafka 的消息队列功能。生产者通过 `XADD` 添加消息，消费者通过 `XREADGROUP` 消费消息，处理完成后通过 `XACK` 确认消息。
![](https://cdn.nlark.com/yuque/__mermaid_v3/cd4624453228c3c4c0b917fdf8b31141.svg)





## **<font style="color:rgb(51,51,51);">什么是 bigkey？会存在什么影响？</font>**
BigKey 是指 **Redis 中某个 Key 对应的 Value 占用内存过大，或者包含的数据量过多的 Key**。Redis 本身没有严格定义 BigKey 的标准，一般认为 String 类型 Value 大于几 MB，或者 List、Hash、Set、ZSet 等集合类型元素数量特别多，就可以认为是 BigKey。BigKey 会带来很多问题，例如占用大量内存、影响 Redis 性能、导致网络阻塞、增加主从同步压力，甚至可能造成 Redis 服务不可用。因此在实际开发中，需要通过合理设计数据结构、拆分 Key、限制集合大小以及使用工具提前发现和治理 BigKey。  

**如何发现 BigKey？ ** 

① 使用`redis-cli --bigkeys`扫描

② 使用` MEMORY USAGE  `查看内存占用

③ 使用 RedisInsight  图形化界面





## Redis 删除 BigKey 为什么不用 DEL，而使用 UNLINK？
Redis 删除 BigKey 不使用 `DEL` 而推荐使用 `UNLINK`，主要是因为 `**DEL**`** 是同步删除，会在 Redis 主线程中直接释放内存，删除大量数据时会阻塞 Redis，影响其他请求；而 **`**UNLINK**`** 是异步删除，它会先从 Redis 主线程中快速解除 Key 的引用关系，然后由后台线程慢慢释放内存，因此可以降低删除 BigKey 对 Redis 性能的影响。** 

| 对比 | DEL | UNLINK |
| --- | --- | --- |
| 删除方式 | 同步删除 | 异步删除 |
| 执行线程 | Redis 主线程 | 主线程 + 后台线程 |
| 是否阻塞 | 会 | 基本不会 |
| 删除速度 | 删除完成后返回 | 快速返回 |
| 适合场景 | 小 Key | BigKey |






## Redis 集群模式
Redis 集群模式主要是为了解决**单机 Redis 容量有限和并发压力过高的问题**。Redis Cluster 采用**分布式无中心架构**，通过 **数据分片（Sharding）** 将数据分散存储到多个 Redis 节点上。Redis Cluster 将整个数据空间划分为 **16384 个 Slot（槽）**，每个 Key 根据 CRC16 算法计算后映射到对应 Slot，然后由负责该 Slot 的节点处理请求。同时，Redis Cluster 通过**主从复制实现高可用**，每个主节点可以拥有多个从节点，当主节点宕机时，可以通过故障转移机制选举新的主节点继续提供服务。  

1. `Redis Sentinel`  
体量较小时，选择`Redis Sentinel` ，单主 Redis 足以支撑业务。
2. `Redis Cluster`  
Redis 官方提供的集群化方案，体量较大时，选择` Redis Cluster `，通过分片，使用更多内  
存。
3. `Twemprox`  
Twemprox 是 Twtter 开源的一个 Redis 和 Memcached 代理服务器，主要用于管理 Redis 和  
Memcached 集群，减少与Cache 服务器直接连接的数量。
4. `Codis`  
`Codis` 是一个代理中间件，当客户端向 Codis 发送指令时， Codis 负责将指令转发到后面的  
Redis 来执行，并将结果返回给客户端。一个 Codis 实例可以连接多个 Redis 实例，也可以启  
动多个 Codis 实例来支撑，每个 Codis 节点都是对等的，这样可以增加整体的 QPS 需求，还能  
起到容灾功能。





## **<font style="color:rgb(51,51,51);">集群的原理是什么？</font>**
Redis 集群的核心原理是**通过数据分片将数据分散到多个 Redis 节点上，同时通过主从复制保证高可用**。Redis Cluster 会将整个数据空间划分为 **16384 个 Slot（槽）**，每个 Key 根据 **CRC16 算法计算出对应的 Slot**，然后由负责该 Slot 的 Master 节点存储和处理。当集群中的某个节点故障时，会通过主从复制和故障转移机制，将对应 Slave 提升为新的 Master，继续提供服务，从而实现 Redis 的水平扩展和高可用。  

![](https://cdn.nlark.com/yuque/__mermaid_v3/7afc124e8e8b783001748a320491dd63.svg)







## **<font style="color:rgb(51,51,51);">Redis Cluster 集群方案什么情况下会导致整个集群不可用？</font>**
 Redis Cluster 集群并不是节点越多就一定越安全，它在某些情况下仍然会导致**整个集群不可用**。最主要的情况是：负责某些 Slot 的 Master 节点宕机，并且没有可用的 Slave 节点进行故障转移，导致部分 Slot 无法提供服务；如果这些 Slot 覆盖了整个数据范围，就会导致整个集群不可用。另外，如果集群中大量节点之间发生网络分区，导致无法达成故障判断，也可能造成集群不可用。

## 缓存穿透、击穿、雪崩有什么区别？  
缓存穿透、缓存击穿、缓存雪崩都是缓存异常导致数据库压力增大的问题，但产生原因不同。**缓存穿透**是指查询的数据在缓存和数据库中都不存在，大量请求绕过缓存直接访问数据库；**缓存击穿**是指一个热点 Key 过期失效，在失效瞬间大量请求同时访问数据库；**缓存雪崩**是指大量缓存 Key 在同一时间过期或者 Redis 服务不可用，导致大量请求同时访问数据库。解决方式上，缓存穿透主要通过布隆过滤器和缓存空对象解决；缓存击穿主要通过互斥锁、热点数据永不过期解决；缓存雪崩主要通过设置随机过期时间、服务降级、限流以及高可用架构解决。

| 问题 | 缓存穿透 | 缓存击穿 | 缓存雪崩 |
| --- | --- | --- | --- |
| 访问对象 | 不存在的数据 | 热点数据 | 大量缓存数据 |
| Redis情况 | 没有Key | 某个热点Key过期 | 大量Key同时失效 |
| 数据库压力 | 大量请求直接访问数据库 | 热点请求打到数据库 | 大量请求同时打到数据库 |
| 发生规模 | 单个不存在Key | 一个热点Key | 大量Key |
| 攻击方式 | 恶意请求不存在ID | 正常热点访问 | 系统设计问题 |


**解决方案：**

**缓存穿透  ： **① 布隆过滤器   ② 缓存空对象  

**缓存击穿  ： **① 互斥锁   ② 热点数据永不过期  

**缓存雪崩  ： **① 设置随机过期时间   ② 服务降级   ③ Redis高可用  





## 如何从大量数据中查找固定开头的 key？
如果 Redis 中有大量 Key，需要根据固定前缀查找 Key，不推荐使用 `KEYS` 命令，因为 `KEYS pattern` 会一次性遍历所有 Key，并且 Redis 是单线程模型，执行期间会阻塞其他请求，导致线上服务不可用。正确做法是使用 `SCAN` 命令进行渐进式遍历，然后结合前缀匹配筛选目标 Key。例如使用 `SCAN 0 MATCH prefix:* COUNT 1000`，Redis 每次返回一批 Key，客户端持续调用直到游标返回 0，这样可以避免长时间阻塞 Redis。如果数据量特别大，还可以提前设计 Key 结构，维护前缀索引，或者使用其他数据结构保存 Key 列表，提高查询效率。  


![](https://cdn.nlark.com/yuque/__mermaid_v3/596eee2cbc46b268c360b4892e99607a.svg)

**注意事项：**

①  SCAN 不保证一次返回全部结果   ② 可能重复返回 Key   ③ COUNT 不是严格数量  





## **<font style="color:rgb(51,51,51);">什么情况下可能会导致 Redis 阻塞？</font>**
Redis 本身采用单线程事件循环模型，大部分命令都会在主线程执行，如果某些操作执行时间过长，就会阻塞 Redis，导致其他客户端请求无法及时处理。常见导致 Redis 阻塞的情况包括：执行复杂度高的命令，例如 `KEYS *`、大范围 `HGETALL`、`SMEMBERS`；操作 BigKey，例如删除超大 Key、获取超大集合数据；Redis 内存过高导致淘汰、RDB 持久化 fork、AOF 重写造成资源竞争；以及网络阻塞，例如客户端发送或接收大量数据。解决方式主要是避免使用危险命令、拆分 BigKey、使用 `SCAN` 替代 `KEYS`、使用 `UNLINK` 异步删除、合理配置持久化策略，并通过慢查询日志定位耗时操作。  

| 原因 | 示例 | 解决方案 |
| --- | --- | --- |
| 慢命令 | KEYS、HGETALL | SCAN、优化命令 |
| BigKey | 大Hash、大List | 拆分Key、UNLINK |
| 大数据传输 | 返回MB级数据 | 分页、限制大小 |
| RDB fork | BGSAVE | 调整策略 |
| AOF重写 | BGREWRITEAOF | 合理调度 |
| 内存不足 | swap、淘汰 | 限制内存 |
| 大量连接 | 连接过多 | 连接池、限流 |






## **<font style="color:rgb(51,51,51);">怎么提高缓存命中率？</font>**
提高缓存命中率主要从缓存设计、数据预热、缓存更新策略以及热点数据处理几个方面入手。首先，需要合理设计缓存 Key，保证相同业务数据能够命中同一个缓存；其次，可以通过缓存预热提前加载热点数据，避免系统刚启动时大量请求访问数据库；对于访问频率高的数据，可以延长缓存有效期或者设置热点数据永不过期；同时需要合理设置缓存淘汰策略，避免热点数据被频繁淘汰。另外，还可以通过增加缓存容量、拆分热点 Key、多级缓存以及避免缓存穿透等方式提高整体缓存命中率。  

| 方法 | 作用 |
| --- | --- |
| 合理设计Key | 保证同一数据命中 |
| 缓存预热 | 提前加载热点数据 |
| 合理TTL | 减少频繁失效 |
| 热点数据永不过期 | 保证高命中 |
| 增加Redis容量 | 减少淘汰 |
| 多级缓存 | 减少Redis访问 |
| 布隆过滤器 | 避免无效请求 |
| 热点Key拆分 | 提高访问稳定性 |
| 合理淘汰策略 | 保留热点数据 |






## **<font style="color:rgb(51,51,51);">Redis 报内存不足怎么处理？</font>**
当 Redis 出现内存不足时，首先需要定位内存增长原因，判断是数据量增长、BigKey、内存泄漏还是配置问题导致。处理方式主要包括临时释放内存和长期优化两个方面。临时处理可以删除无用 Key、清理过期数据、使用 `UNLINK` 异步删除 BigKey，避免阻塞 Redis；长期处理需要设置合理的 `maxmemory`，配置内存淘汰策略，例如 `allkeys-lru` 淘汰不常访问的数据，同时优化 Key 设计、拆分 BigKey、限制 Value 大小。如果业务数据量持续增长，还可以通过 Redis 集群进行水平扩容，将数据分散到多个节点。  

**内存淘汰策略：**

| 策略 | 说明 |
| --- | --- |
| noeviction | 不淘汰，写入失败 |
| allkeys-lru | 淘汰所有 Key 中最近最少使用 |
| volatile-lru | 淘汰设置过期时间的 Key |
| allkeys-random | 随机删除 Key |
| volatile-ttl | 删除即将过期 Key |

## **<font style="color:rgb(51,51,51);">热点数据和冷数据是什么</font>**
热点数据和冷数据主要是根据数据访问频率进行划分的。热点数据是指在一段时间内被频繁访问的数据，例如热门商品、首页推荐、排行榜等，这类数据通常需要优先放入缓存，以提高访问速度和降低数据库压力；冷数据是指访问频率较低的数据，例如历史订单、过期文章等，这类数据访问较少，可以降低缓存优先级，甚至直接存储在数据库中。实际开发中通常会根据数据访问热度进行缓存优化，例如热点数据采用较长缓存时间或多级缓存，而冷数据采用较短缓存时间或者不缓存。  





## **<font style="color:rgb(51,51,51);">Memcache与Redis的区别都有哪些？</font>**
Memcached 和 Redis 都是基于内存的缓存数据库，主要用于提高系统访问速度，减轻数据库压力。但两者在功能和应用场景上存在明显区别。Memcached 设计简单，主要用于缓存 Key-Value 数据，只支持字符串类型，数据不支持持久化；而 Redis 功能更加丰富，除了支持字符串，还支持 Hash、List、Set、Sorted Set 等多种数据结构，并且支持 RDB 和 AOF 持久化。除此之外，Redis 还提供事务、发布订阅、分布式锁、消息队列等功能。因此在实际项目中，如果只是简单缓存，可以选择 Memcached；如果需要复杂的数据操作、高可靠性或者更多能，一般选择 Redis。

Memcached  采用多线程模型，redis 采用单线程模型





## **<font style="color:rgb(51,51,51);">Redis的过期策略以及内存淘汰机制</font>**
Redis 的过期策略主要解决的是 Key 设置过期时间后，什么时候被删除的问题。Redis 采用的是「**惰性删除 + 定期删除**」两种策略结合的方式：**惰性删除**是在客户端访问 Key 时，Redis 检查 Key 是否过期，如果过期则删除；**定期删除**是 Redis 定期随机抽取一部分设置了过期时间的 Key 进行检查并删除。由于这两种策略都不能保证及时删除所有过期 Key，所以当 Redis 内存达到最大限制时，会触发内存淘汰机制，根据配置的淘汰策略删除部分数据。Redis 提供了多种淘汰策略，常见生产环境缓存场景一般使用 `allkeys-lru`，即从所有 Key 中淘汰最近最少使用的数据。
