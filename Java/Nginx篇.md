## **<font style="color:rgb(51,51,51);">简述一下什么是Nginx，它有什么优势和功能？</font>**
Nginx 是一个高性能的 **Web 服务器和反向代理服务器**，它采用事件驱动和异步非阻塞模型，能够处理大量并发请求，常用于 Web 服务部署、负载均衡、静态资源访问以及反向代理。相比传统 Web 服务器，Nginx 最大的优势是**高并发、低资源消耗、高稳定性**，它可以在较低的硬件成本下支撑大量用户访问。在实际项目中，Nginx 常作为系统入口，接收客户端请求，然后根据配置将请求转发给后端多个服务，实现请求分发和服务保护。同时，Nginx 还支持静态资源部署、HTTP/HTTPS配置、动静分离、缓存控制、限流以及安全防护等功能。  





## **<font style="color:rgb(51,51,51);">Nginx的特性</font>**
Nginx 的主要特性包括 **高性能、高并发、低资源消耗、反向代理、负载均衡、静态资源处理、扩展性强和高可靠性**。首先，Nginx 采用 **事件驱动模型、I/O 多路复用和非阻塞 I/O**，可以使用少量 Worker 进程处理大量并发连接，因此具有很高的性能和吞吐量。其次，Nginx 作为反向代理服务器，可以将请求转发给后端多个应用服务器，并通过负载均衡策略提高系统的处理能力和可用性。同时，Nginx 对静态资源处理效率很高，可以直接返回 HTML、CSS、JS、图片等文件，减少后端服务器压力。此外，Nginx 支持丰富的模块扩展，可以通过配置实现缓存、限流、HTTPS、安全控制等功能，并且支持热部署和平滑升级，保证服务的高可靠运行。

## Nginx 为什么使用 epoll？  
Nginx 使用 epoll 主要是为了实现**高并发网络请求处理**。传统的 select 和 poll 在处理大量连接时，需要每次遍历所有连接，时间复杂度是 O(n)，当连接数量非常大时效率会明显下降。而 epoll 采用事件通知机制，只返回真正发生事件的连接，时间复杂度接近 O(1)，不需要遍历所有连接。同时，epoll 基于 Linux 内核实现，可以减少用户态和内核态之间的数据拷贝，提高事件处理效率。因此 Nginx 结合自身的单线程事件驱动模型，通过 epoll 可以使用少量 Worker 进程同时处理大量客户端连接，从而实现高并发和高性能。  



### epoll 的两种工作模式  
** LT（水平触发）：** 只要事件没有处理完，就一直通知。  （默认）

** ET（边缘触发）：** 只在状态变化时通知。  





## Nginx 为什么性能这么高？  
Nginx 性能高主要是因为它采用了**事件驱动的异步非阻塞模型、多路复用机制以及高效的进程模型**。

首先，Nginx 使用 **单线程事件循环 + I/O 多路复用** 的方式处理大量连接，通过 epoll 等机制，一个线程可以同时监听多个客户端请求，避免了传统多线程模型中线程创建、切换带来的性能损耗。其次，Nginx 采用 **多进程模型**，主进程负责管理配置和工作进程，多个 worker 进程独立处理请求，充分利用多核 CPU，同时单个 worker 内部采用事件驱动，提高了并发处理能力。除此之外，Nginx 还针对网络请求进行了大量优化，例如使用 **零拷贝技术减少数据在内核态和用户态之间的复制**，支持长连接、连接池、缓存机制等，从而降低资源消耗。因此，Nginx 能够在较低的硬件资源下支撑大量并发连接，具有高并发、高性能和高稳定性的特点。  





## Nginx 的事件驱动模型是什么？  
Nginx 的事件驱动模型是一种**基于事件通知机制处理请求的 I/O 模型**，它的核心思想是**一个 Worker 进程不主动等待请求，而是通过事件机制监听多个连接，当某个连接发生读写事件时，再去处理对应请求**。Nginx 启动多个 Worker 进程，每个 Worker 都会通过事件模块监听大量客户端连接，Linux 下通常使用 epoll 实现。当客户端发送请求、数据读取完成或者响应可以发送时，epoll 会通知 Worker，Worker 再执行对应的处理逻辑。相比传统的一个请求对应一个线程或进程模型，Nginx 不需要为每个连接创建线程，而是通过少量 Worker 配合异步非阻塞 I/O 同时处理大量连接，从而实现高并发和高性能。

## Nginx worker_processes 设置多少合适？  
Nginx 的 worker_processes 一般设置为 CPU 核心数比较合适，因为 Nginx 的 Worker 进程主要负责处理网络事件和请求，多个 Worker 可以充分利用多核 CPU，提高并发处理能力。通常配置为 worker_processes auto;，让 Nginx 自动根据机器 CPU 核心数进行设置。如果是高并发场景，还可以根据业务压力、CPU 使用率以及是否存在 CPU 密集型任务进行调整，但一般不会设置超过 CPU 核心数太多，因为 Worker 过多会导致进程切换开销增加，反而降低性能。





## worker_connections 是什么？  
worker_connections 是 Nginx 中用于配置单个 Worker 进程最大允许处理的连接数的参数，它定义了一个Worker 能同时维护多少个客户端连接。由于 Nginx 采用异步非阻塞事件驱动模型，一个 Worker 可以通过 epoll 同时管理多个连接，因此通过提高 worker_connections 可以提升 Nginx 的并发处理能力。但它不是无限增加的，实际最大连接数还会受到操作系统文件描述符限制、CPU、内存以及网络带宽等因素影响。Nginx 理论最大连接数通常可以通过 worker_processes × worker_connections 计算。







## Nginx 的 Master-Worker 模型是什么？  
Nginx 的 Master-Worker 模型是一种**主进程负责管理，工作进程负责处理请求**的多进程架构。Nginx 启动后会创建一个 Master 主进程和多个 Worker 工作进程。Master 主要负责读取配置文件、管理 Worker 进程、监听信号以及实现平滑重启；Worker 是真正处理客户端请求的进程，每个 Worker 都会通过 epoll 等 I/O 多路复用机制监听连接，并在事件循环中处理请求。多个 Worker 之间相互独立，可以充分利用多核 CPU，同时某个 Worker 发生异常退出时，不会影响其他 Worker 工作，Master 可以重新创建 Worker，从而保证 Nginx 的高性能和高可用。  





## **为什么多个 Worker 可以监听同一个端口？**
Nginx 多个 Worker 能够监听同一个端口，主要是因为 **Linux 提供了 socket 共享机制**。Nginx 启动时，首先由 Master 进程创建监听 Socket，并绑定端口（例如 80 端口），然后通过 `fork()` 创建多个 Worker 进程。由于 `fork()` 会复制文件描述符，所以多个 Worker 都拥有同一个监听 Socket 的引用，因此可以共同监听同一个端口。当客户端请求到达时，操作系统会负责将连接分配给其中一个 Worker 进程进行处理，这样多个 Worker 就可以同时处理请求，提高并发能力。  





## Nginx 为什么采用多进程模型？  
Nginx 采用多进程模型主要是为了**充分利用多核 CPU、提高稳定性以及避免线程同步带来的开销**。Nginx 采用一个 Master 主进程管理多个 Worker 工作进程，Master 负责读取配置、管理 Worker 的启动和退出，而 Worker 负责真正处理客户端请求。每个 Worker 进程相互独立，都可以处理请求，这样可以充分利用服务器多核 CPU，提高并发处理能力。同时，由于进程之间相互隔离，即使某个 Worker 进程异常退出，也不会影响其他 Worker 继续工作，提高了系统的稳定性。另外，Nginx Worker 内部采用单线程事件驱动模型，不需要复杂的线程锁竞争，因此性能更高。  





## Nginx 为什么采用多进程，而不是多线程？  
Nginx 采用多进程模型，而不是多线程模型，主要是为了**提高稳定性、降低并发处理成本以及充分利用多核 CPU**。Nginx 采用的是 **Master-Worker 多进程架构**，Master 进程负责管理 Worker 进程，例如启动、停止、加载配置等；Worker 进程负责实际处理客户端请求。相比多线程模型，多进程之间资源相互隔离，一个 Worker 进程出现异常退出时，不会影响其他 Worker 继续提供服务，提高了系统稳定性。同时，Nginx 结合事件驱动和异步非阻塞 I/O，一个 Worker 就可以处理大量连接，因此不需要创建大量线程来提高并发能力。此外，多进程模型还能避免线程之间的锁竞争问题，并且可以通过多个 Worker 充分利用多核 CPU，所以 Nginx 选择了多进程架构。  





## Nginx 如何实现高并发？  
Nginx 能够实现高并发，主要依靠 **事件驱动模型、I/O 多路复用、非阻塞 I/O 和多进程架构**。传统服务器通常采用一个连接对应一个线程的方式，当并发量增加时，会创建大量线程，导致线程切换和内存开销变大。而 Nginx 采用事件驱动模型，一个 Worker 进程可以同时处理大量连接。Worker 通过 epoll 等 I/O 多路复用技术监听多个连接，当某个连接有数据可读或可写时，才进行处理，不需要阻塞等待。同时，Nginx 使用非阻塞 I/O，使 Worker 在等待网络数据时不会被阻塞，可以继续处理其他请求。另外，Nginx 采用 Master-Worker 多进程模型，通过多个 Worker 充分利用多核 CPU，提高处理能力。因此，Nginx 可以在很少的进程和线程下维护大量并发连接，实现高性能、高吞吐量。  





## 为什么Nginx的Worker可以处理多个请求  ？
Nginx 的 Worker 进程之所以可以同时处理多个请求，主要是因为它采用了 **事件驱动模型 + I/O 多路复用技术**。传统服务器通常是一个请求对应一个线程，线程需要一直等待请求处理完成，而 Nginx 的 Worker 不会阻塞等待某一个请求，而是通过 epoll 等 I/O 多路复用机制同时监听多个客户端连接。当某个连接有数据到达或者需要处理时，操作系统会通知 Worker，Worker 再执行对应的事件处理逻辑；没有数据的连接则不会占用 Worker 的执行时间。因此，一个 Worker 进程可以在单线程环境下管理成千上万个连接，实现同时处理大量请求的效果。  





## Nginx 如何避免一个耗时请求阻塞 Worker？  
Nginx 避免长时间请求阻塞 Worker，主要依靠 **非阻塞 I/O、事件驱动模型和异步处理机制**。Nginx 的 Worker 不会一直等待某个请求完成，而是将耗时操作注册为事件，然后继续处理其他连接。当操作系统通知 Worker 某个事件已经完成时，Worker 再回来继续处理该请求。因此，一个慢请求在等待网络数据、磁盘 I/O 或后端响应时，不会一直占用 Worker 的执行资源。不过需要注意的是，如果请求本身在 Worker 中执行大量 CPU 密集型任务，例如复杂计算或执行耗时模块，仍然可能阻塞 Worker，所以 Nginx 通常将复杂业务交给后端应用服务器处理。

| proxy_connect_timeout | 连接后端超时时间 |
| proxy_read_timeout | 等待后端响应时间 |
| send_timeout | 发送响应超时时间 |






## Nginx 和 Tomcat 有什么区别？  
Nginx 和 Tomcat 最大的区别在于它们的定位不同。**Nginx 是一个高性能的 Web 服务器和反向代理服务器，主要负责处理静态资源、请求转发以及负载均衡；而 Tomcat 是一个 Java Web 应用服务器，主要负责运行 Java Web 程序，处理动态业务逻辑。** Nginx 基于事件驱动的异步非阻塞模型，擅长处理大量并发连接，因此通常作为系统入口，接收客户端请求，再将动态请求转发给后端 Tomcat 处理。Tomcat 基于 Servlet 规范，通过线程池处理请求，更适合执行复杂的业务逻辑。所以在实际生产环境中，通常采用 **Nginx + Tomcat** 的架构，由 Nginx 负责高并发接入和负载均衡，Tomcat 负责业务处理，两者配合可以提高系统性能和稳定性。  





## 完整 server 配置
```nginx
server {

    # 监听端口
    listen 80;

    # 域名
    server_name www.example.com;


    # =========================
    # 1. 日志配置
    # =========================

    access_log /var/log/nginx/example.access.log;

    error_log /var/log/nginx/example.error.log;


    # =========================
    # 2. 静态资源处理
    # =========================

    location /static/ {

        root /usr/share/nginx/html;

        expires 7d;

        add_header Cache-Control "public";
    }


    # =========================
    # 3. 前端页面
    # =========================

    location / {

        root /usr/share/nginx/html;

        index index.html;

        # 前端Vue/React路由刷新处理
        try_files $uri $uri/ /index.html;

    }


    # =========================
    # 4. 后端接口代理
    # =========================

    location /api/ {


        # 转发到 upstream
        proxy_pass http://backend;


        # 设置请求头
        proxy_set_header Host $host;

        proxy_set_header X-Real-IP $remote_addr;

        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;


        # 超时时间

        proxy_connect_timeout 5s;

        proxy_read_timeout 60s;

        proxy_send_timeout 60s;

    }


    # =========================
    # 5. WebSocket代理
    # =========================

    location /ws/ {


        proxy_pass http://backend;


        proxy_http_version 1.1;


        proxy_set_header Upgrade $http_upgrade;

        proxy_set_header Connection "upgrade";

    }


    # =========================
    # 6. 限流
    # =========================

    location /api/login {


        limit_req zone=login_limit burst=5 nodelay;


        proxy_pass http://backend;

    }


    # =========================
    # 7. 禁止访问敏感文件
    # =========================

    location ~ /\. {

        deny all;

    }


    # =========================
    # 8. 错误页面
    # =========================

    error_page 404 /404.html;

    error_page 500 502 503 504 /50x.html;
}
```

```nginx

        server_name www.example.com;

    
        location /api/ {

            proxy_pass http://backend;

        }

    }
```

## location 匹配规则是什么？  
Nginx 的 `location` 用于匹配客户端请求的 URI，并根据匹配结果选择对应的配置块处理请求。Nginx 的 location 匹配规则主要包括**精确匹配、前缀匹配、正则匹配**三种，其中精确匹配优先级最高，正则匹配次之，普通前缀匹配优先级最低。匹配时，Nginx 会先查找最长的前缀匹配，然后判断是否存在正则匹配，如果匹配成功则使用对应的 location；如果最长前缀匹配使用了 `^~` 修饰符，则会跳过正则匹配。简单来说，Nginx 会按照“精确匹配 > ^~前缀匹配 > 正则匹配 > 普通前缀匹配”的规则选择最终处理请求的 location。

## Nginx 反向代理的执行流程是什么？
Nginx 反向代理的执行流程主要包括**接收客户端请求、匹配代理规则、转发请求到后端服务器、后端处理请求、Nginx 返回响应给客户端**这几个步骤。首先，客户端将请求发送给 Nginx，由 Nginx 作为统一入口接收请求；然后 Nginx 根据配置文件中的 `location` 规则匹配请求路径，判断是否需要进行反向代理；如果需要代理，Nginx 会根据 upstream 配置选择一台后端服务器，并将请求转发过去；后端服务器处理业务逻辑后返回响应结果；最后 Nginx 接收到后端响应，再将结果返回给客户端。整个过程中，客户端只知道 Nginx 的地址，并不知道真实的后端服务器地址，因此实现了隐藏后端服务、负载均衡和提高系统安全性的作用

## 正向代理和反向代理有什么区别？  
正向代理和反向代理的主要区别在于**代理对象不同**。正向代理是**代理客户端**，客户端主动配置代理服务器，通过代理服务器访问目标服务器，目标服务器不知道真实客户端是谁；而反向代理是**代理服务端**，客户端直接访问代理服务器，由代理服务器将请求转发给后端真实服务器，客户端不知道真正提供服务的是哪台服务器。简单来说，正向代理隐藏的是**客户端身份**，例如访问外网时使用代理；反向代理隐藏的是**服务器身份**，例如 Nginx 作为网站入口，将请求转发给多个 Tomcat 服务。在实际项目中，Nginx、Gateway 等通常使用的是反向代理。  

|  | 正向代理 | 反向代理 |
| --- | --- | --- |
| **代理对象** | 客户端 | 服务端 |
| **隐藏谁** | 隐藏客户端 | 隐藏服务器 |
| **谁配置代理** | 客户端主动配置 | 服务端部署配置 |
| **客户端是否知道代理** | 知道 | 不知道 |
| **服务端是否知道真实客户端** | 通常不知道 | 知道（可获取IP） |
| **典型应用** | 翻墙代理、企业代理上网 | Nginx、负载均衡 |






## Nginx 和 Gateway 有什么区别？  
Nginx 和 Gateway 都可以作为系统入口，实现请求转发和负载均衡，但是它们的定位不同。**Nginx **更偏向基础设施层，主要负责高性能的网络代理、静态资源处理、负载均衡和流量接入；**Gateway **更偏向业务网关层，主要用于微服务架构中的服务路由、权限认证、限流熔断、统一业务处理等。 Nginx 通常部署在整个系统最前端，负责接收外部请求并转发给网关或后端服务；Gateway 则根据微服务规则，将请求转发到具体的服务实例。因此在实际项目中，两者经常配合使用，例如 **用户请求 → Nginx → Gateway → 微服务服务集群**，由 Nginx 负责高并发接入，由 Gateway 负责业务治理。  

| | Nginx | Gateway |
| --- | --- | --- |
| 定位 | Web服务器、反向代理 | 微服务网关 |
| 所属层级 | 基础设施层 | 业务架构层 |
| 主要职责 | 流量接入、代理、负载均衡 | 服务路由、权限、安全控制 |
| 开发语言 | C语言 | Java（Spring Cloud Gateway） |
| 性能 | 极高 | 较高 |






## Nginx是如何处理一个HTTP请求的呢？
Nginx 处理一个 HTTP 请求的过程主要包括 **建立连接、接收请求、解析请求、处理请求、返回响应** 这几个阶段。首先，客户端向 Nginx 发送 HTTP 请求，Nginx 的 Master 进程负责管理 Worker 进程，真正处理请求的是 Worker 进程。Worker 通过 **事件驱动模型和 I/O 多路复用机制** 监听客户端连接，当有新的连接到来时，Worker 接收 TCP 连接并读取 HTTP 请求报文。然后，Nginx 会解析请求中的请求方法、URL、请求头等信息，根据配置文件中的 location 规则匹配对应的处理逻辑。如果请求的是**静态资源**，Nginx 会直接从文件系统读取并返回；如果是**动态请求**，则通过反向代理转发给后端服务器，例如 Tomcat、Spring Boot 服务等。后端处理完成后，将响应结果返回给 Nginx，Nginx 再将响应数据发送给客户端，最后关闭连接或者保持长连接等待后续请求。整个过程中，Nginx 通过事件驱动、非阻塞 I/O 和多进程模型，可以同时处理大量并发请求。

## **<font style="color:rgb(51,51,51);">在Nginx中，如何使用未定义的服务器名称来阻止处理请求？</font>**
在 Nginx 中，可以通过配置一个 默认 Server 块（default server），并使用一个未定义的服务器名称来阻止处理未知域名的请求。通常做法是将这个 Server 设置为默认虚拟主机，并返回 444 状态码或者直接拒绝连接。例如，可以配置 listen 80 default_server，然后设置一个不存在的 server_name，当客户端请求的 Host 不匹配任何已配置域名时，就会进入这个默认 Server，从而拒绝请求。这样可以防止恶意请求通过未知域名访问服务器，提高安全性。

```nginx
server {
    listen 80 default_server;
    server_name _;

    return 444;
}
```





## Nginx 负载均衡有哪些策略？  
| 策略 | 核心思想 | 适用场景 |
| --- | --- | --- |
| 轮询（**默认**） | 依次分配请求 | 普通Web服务 |
| 加权轮询 | 按性能比例分配 | 服务器性能不同 |
| IP Hash | 固定客户端访问服务器 | Session保持 |
| 最少连接 | 选择连接最少服务器 | 长连接、大请求 |
| URL Hash | 固定资源服务器 | 缓存服务器 |
| 一致性Hash | 减少节点变化影响 | 分布式缓存 |






## Nginx 如何配置负载均衡？
Nginx 配置负载均衡主要是通过 `upstream` 模块定义后端服务器集群，然后在 `location` 中使用 `proxy_pass` 将请求转发到该集群。Nginx 会根据配置的负载均衡策略，将客户端请求分发到不同的后端服务器，默认采用轮询策略，也支持权重、IP Hash、最少连接等策略。例如，可以通过 `upstream backend` 定义多个 Tomcat 服务，然后在 `proxy_pass http://backend` 中引用，实现请求的分发。同时，在生产环境中还需要结合健康检查、超时配置和故障剔除机制，保证后端服务不可用时不会继续转发请求。

## Nginx 如何判断后端服务器是否可用？  
Nginx 判断后端服务器是否可用，主要通过**被动健康检查**机制实现。Nginx 在转发请求时会记录后端服务器的响应情况，如果某个服务器连续出现连接失败、超时或者返回错误，达到配置的 `max_fails` 次数后，Nginx 会认为该服务器暂时不可用，并在 `fail_timeout` 时间内停止向它转发请求，之后再尝试恢复。另外，Nginx 开源版默认不支持主动健康检查，如果需要主动探测后端服务是否存活，可以使用 Nginx Plus 或第三方健康检查模块，通过定期发送探测请求判断后端状态。  





## Nginx 宕机怎么办？
Nginx 宕机的处理方式主要分为**故障发现、故障切换和故障恢复**三个阶段。在生产环境中，一般不会让单台 Nginx 直接对外提供服务，而是通过高可用方案避免单点故障。例如，可以部署多台 Nginx，通过 Keepalived 提供虚拟 IP，当主 Nginx 宕机后，Keepalived 会检测到故障并将虚拟 IP 漂移到备用 Nginx 上，实现自动切换。另外，也可以通过云厂商的负载均衡或硬件负载均衡将请求分发到多个 Nginx 节点。发生故障后，需要检查 Nginx 进程状态、错误日志、系统资源以及配置问题，修复后重新启动 Nginx，并通过监控和告警避免类似问题再次发生。





## Nginx 如何实现故障转移？
Nginx 实现故障转移主要依靠**高可用架构**，因为单台 Nginx 本身存在单点故障问题。生产环境通常部署多台 Nginx，并通过 Keepalived、负载均衡器或云厂商的 SLB 等方式实现故障检测和流量切换。例如使用 Nginx + Keepalived 时，主 Nginx 和备用 Nginx 共享一个虚拟 IP（VIP），Keepalived 会持续检测主节点状态，如果发现主 Nginx 宕机，就会将 VIP 漂移到备用 Nginx，之后用户请求会自动转发到备用节点，实现故障转移。除此之外，Nginx 自身的 Worker 进程故障由 Master 进程自动拉起，保证单机内部稳定。  





## Nginx 如何实现 Session 共享？
Nginx 本身不负责存储 Session，它主要负责请求转发。如果后端存在多台服务器，而 Session 保存在单台服务器内存中，就会出现用户请求被转发到不同服务器导致 Session 丢失的问题。实现 Session 共享主要有三种方式：第一种是**Session 复制**，让多台服务器之间同步 Session 数据；第二种是**Session 粘滞（Session Sticky）**，通过 Nginx 的 `ip_hash` 或 Cookie 方式让同一个用户始终访问同一台服务器；第三种也是现在最常用的方式，是**将 Session 存储到统一的外部存储中**，例如 Redis，所有后端服务器都从 Redis 中读取 Session，实现真正的共享。在分布式系统中通常推荐 Redis 方案，因为它不依赖具体服务器，扩容和故障转移更加方便。  





## Nginx reload 和 restart 有什么区别？
`nginx reload` 和 `nginx restart` 的主要区别在于是否停止 Nginx 服务。`reload` 是**平滑重载配置**，不会停止 Nginx 服务，Master 进程会重新读取配置文件，并启动新的 Worker 进程处理新的请求，同时等待旧 Worker 处理完已有请求后再退出，因此不会影响正在访问的用户，适合生产环境修改配置时使用。而 `restart` 会先停止 Nginx 服务，再重新启动 Nginx，期间会关闭现有连接，可能导致正在处理的请求失败，适用于 Nginx 进程异常或者需要完全重启服务的场景。生产环境修改配置一般优先使用 `nginx -s reload`，避免服务中断。  





## Nginx 如何实现优雅关闭？
Nginx 实现优雅关闭主要依靠 **Worker 进程的平滑退出机制**。当 Nginx 收到停止信号后，Master 进程不会立即强制关闭 Worker，而是先通知 Worker 停止接收新的请求，同时继续处理已经建立的连接和正在执行的任务，等已有请求处理完成后，Worker 进程再退出，最后 Master 进程结束。这样可以避免正在处理的请求被强制中断，提高服务可用性。在生产环境中，通常通过 `nginx -s quit` 实现优雅关闭，而不是直接使用 `kill -9` 强制终止。

| 操作 | 作用 |
| --- | --- |
| reload | 重新加载配置 |
| quit | 优雅关闭服务 |
| stop | 快速停止服务 |
| restart | 停止后重新启动 |






## Nginx 中如何限制请求频率？
Nginx 限制请求频率主要通过 **限流模块** 实现，常用的是 `ngx_http_limit_req_module`，它基于**漏桶算法**控制客户端请求速率。通过 `limit_req_zone` 定义限流规则，例如按照客户端 IP 记录请求频率，再通过 `limit_req` 应用到具体接口。当请求超过限制时，Nginx 可以选择排队等待处理或者直接返回错误码，例如 429 或 503，从而防止恶意请求、接口被刷以及后端服务压力过大。除了基于 IP 限流，还可以根据用户 ID、接口路径等维度进行限流。
