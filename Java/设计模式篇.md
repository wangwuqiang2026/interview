## 什么是设计模式？为什么需要设计模式？  
设计模式是一套**经过大量软件开发实践总结出来的、用于解决软件设计中常见问题的可复用设计方案**。它不是具体的代码，而是一种设计思想和解决问题的方法。目前比较经典的设计模式有 **23种**，主要分为创建型、结构型和行为型三大类，比如单例模式、工厂模式、代理模式、观察者模式等。

我们需要设计模式主要有三个原因：第一，提高代码的**可维护性和可扩展性**，通过合理的设计降低代码之间的耦合；第二，提高代码的**复用性**，避免重复造轮子，让开发人员可以使用经过验证的设计方案；第三，提高团队协作效率，因为设计模式是一套通用的交流语言，比如说使用工厂模式、观察者模式，团队成员可以快速理解系统设计。





## 设计模式有哪些分类？  
设计模式主要分为三大类，分别是**创建型模式、结构型模式和行为型模式**，一共包含经典的 **23种设计模式**。

第一类是**创建型模式**，主要关注对象的创建过程，目的是将对象的创建和使用进行解耦，提高创建对象的灵活性。

第二类是**结构型模式**，主要关注类和对象之间的组合关系，通过合理组织类的结构来降低系统复杂度。

第三类是**行为型模式**，主要关注对象之间的通信和职责分配，用于提高对象之间协作的灵活性。

## 设计模式六大原则是什么？  
设计模式六大原则也称为**SOLID原则加开闭原则等面向对象设计原则**，是指导我们进行软件设计的基本思想，主要包括：**单一职责原则、开闭原则、里氏替换原则、依赖倒置原则、接口隔离原则、迪米特法则**。

其中最重要的是**开闭原则**，要求软件实体应该对扩展开放，对修改关闭；单一职责原则要求一个类只负责一个功能；里氏替换原则要求子类可以替换父类而不会影响程序正确性；依赖倒置原则要求依赖抽象而不是具体实现；接口隔离原则要求接口应该小而专，不应该让实现类依赖不需要的方法；迪米特法则要求对象之间尽量减少直接依赖，降低耦合。





## 什么是单例模式？有哪些实现方式？  
单例模式是一种**创建型设计模式**，它保证一个类在整个应用程序生命周期中**只有一个实例存在，并且提供一个全局访问入口来获取这个实例。使用单例模式主要是为了避免频繁创建对象造成资源浪费，同时保证某些核心资源的一致性，比如线程池、数据库连接池、配置管理类、缓存管理类等。**

单例模式主要有饿汉式、懒汉式、双重检查锁、静态内部类、枚举单例等实现方式  

### 饿汉式（线程安全）  
**特点：**类加载时就创建对象。

**优点**

+  简单 
+  天然线程安全 

**缺点**

+  不管是否使用，都会提前创建对象 
+  浪费资源

```java
public class Singleton {

    // 类加载时创建唯一实例
    private static final Singleton INSTANCE = new Singleton();

    // 私有构造方法，防止外部创建对象
    private Singleton() {

    }

    // 提供获取实例的方法
    public static Singleton getInstance() {
        return INSTANCE;
    }
}
```

### 双重检查锁（DCL）  
```java
public class Singleton {


    private volatile static Singleton instance;


    private Singleton(){}


    public static Singleton getInstance(){

        if(instance == null){

            synchronized(Singleton.class){

                if(instance == null){

                    instance = new Singleton();

                }
            }
        }

        return instance;
    }
}
```

## 为什么DCL需要volatile？  
DCL需要 `volatile`，主要有两个作用：**防止指令重排序和保证对象的可见性**。

因为 `instance = new Singleton()` 并不是一个原子操作，它实际上分为三个步骤：第一步，给对象分配内存；第二步，执行对象初始化；第三步，将引用指向对象。

但是 JVM 为了优化性能，可能会发生指令重排序，把步骤调整为：第一步，分配内存；第二步，将引用指向对象；第三步，初始化对象。

这样可能导致一个线程看到 `instance` 不为 null，但是对象还没有初始化完成，另一个线程直接获取这个对象，就可能使用到一个半初始化状态的对象。

`volatile` 可以禁止 JVM 对对象初始化过程进行指令重排序，同时保证一个线程修改 `instance` 后，其他线程能够立即看到最新值。

所以，DCL 中：

+ `synchronized` 解决的是多个线程同时创建多个实例的问题； 
+ `volatile` 解决的是指令重排序导致获取到未初始化对象的问题。 

因此，DCL 必须配合 `volatile` 才能保证单例模式的线程安全。





## 饿汉式和懒汉式单例有什么区别？  
饿汉式和懒汉式单例最大的区别在于**对象创建的时机不同**。饿汉式是在类加载的时候就立即创建单例对象，因此天然线程安全，实现简单，但是如果这个单例对象一直没有被使用，会造成一定的资源浪费。懒汉式是在第一次调用获取实例的方法时才创建对象，可以实现延迟加载，节省资源，但是需要考虑线程安全问题，如果多个线程同时第一次访问，可能会创建多个实例，因此需要通过 synchronized、双重检查锁 DCL 或静态内部类等方式保证线程安全。实际开发中，如果对象创建成本低且一定会使用，可以选择饿汉式；如果对象创建成本较高，希望延迟初始化，一般选择线程安全的懒汉式实现。  

|  | 饿汉式 | 懒汉式 |
| --- | --- | --- |
| **创建时机** | 类加载时 | 第一次使用时 |
| **线程安全** | 天然安全 | 需要额外处理 |
| **实现难度** | 简单 | 复杂 |
| **是否延迟加载** | ❌ | ✅ |
| **是否推荐** | 小对象推荐 | 大对象推荐 |






## 为什么饿汉式天然线程安全？  
饿汉式单例之所以天然线程安全，是因为**实例在类加载阶段就已经创建完成了，而 Java 类加载过程本身由 JVM 保证线程安全**。当多个线程同时访问单例对象时，由于对象已经存在，不会再发生多个线程同时创建实例的问题，因此不需要额外加锁。  





## 单例一定只有一个对象吗？
单例模式保证的是在指定作用范围内，一个类只创建一个实例，并提供全局访问点。但是“只有一个对象”是有前提的，比如同一个 JVM、同一个 ClassLoader、同一个应用环境下。特殊情况下，例如多 JVM 部署、不同 ClassLoader 加载、反射、序列化、克隆等，都可能破坏单例，产生多个对象。  





## 如何防止反射破坏单例？  
反射破坏单例的原因是反射可以绕过类的私有构造方法，直接调用构造器创建新的对象。常见的解决方式是在构造方法中增加判断，如果实例已经存在，则直接抛出异常，禁止再次创建。另外，枚举单例天然防止反射破坏，因为 JVM 规定枚举类的实例不能通过反射创建。  





## 序列化为什么会破坏单例？如何解决？  
序列化会破坏单例，是因为**反序列化时 JVM 会通过无参构造方法之外的机制重新创建一个对象，而不是直接使用原来的实例**。比如单例对象序列化到文件后，再通过 `ObjectInputStream.readObject()` 读取时，会重新创建一个新的对象，导致内存中存在两个实例，从而破坏单例。解决方式是在单例类中重写 `readResolve()` 方法，在反序列化时返回原来的单例对象。除此之外，使用枚举实现单例也可以天然防止序列化破坏单例，因为 JVM 对枚举的序列化机制进行了特殊处理。  

```java
public class Singleton implements Serializable {

    private static final Singleton INSTANCE = new Singleton();

    private Singleton(){}


    public static Singleton getInstance(){
        return INSTANCE;
    }


    private Object readResolve(){
        return INSTANCE;
    }
}
```

单例被破坏的几种方式：

| 方式 | 原因 | 解决 |
| --- | --- | --- |
| **反射** | 调用私有构造方法创建对象 | 构造方法防御 |
| **序列化** | readObject创建新对象 | readResolve |
| **克隆** | clone创建副本 | 禁止clone |
| **多个类加载器** | 不同ClassLoader加载不同类 | 统一类加载器 |






## 如何保证单例模式线程安全？  
保证单例模式线程安全，主要是解决**多线程环境下同时创建多个实例的问题**。常见方式有饿汉式、同步方法、双重检查锁 DCL、静态内部类以及枚举单例。其中饿汉式利用 JVM 类加载机制保证线程安全；懒汉式可以通过 synchronized 加锁保证同一时间只有一个线程创建对象；DCL 通过两次判空减少锁竞争，并配合 volatile 防止指令重排序；静态内部类利用 JVM 类加载机制实现延迟加载和线程安全；实际开发中推荐使用静态内部类或者枚举单例，因为实现简单且性能较好。  





## 为什么推荐静态内部类实现单例？
推荐使用**静态内部类实现单例模式**，主要是因为它同时解决了**懒加载、线程安全和性能问题**。静态内部类中的单例对象会在内部类第一次被加载时创建，而 Java 类加载机制保证了类加载过程是线程安全的，因此不需要额外加锁。同时，由于内部类只有在调用 `getInstance()` 方法时才会被加载，所以实现了延迟加载，避免了饿汉式提前创建对象的问题。相比双重检查锁（DCL），静态内部类实现更加简单，不需要使用 `volatile`，代码可读性更高。    





## 枚举单例为什么不会被破坏？  
枚举单例不会被破坏，主要是因为 **Java 枚举在 JVM 层面天然保证单例特性**。首先，枚举类的每个枚举值在 JVM 中只会被创建一次，JVM 会保证枚举实例的唯一性；其次，枚举无法通过反射创建新的实例，因为 Java 反射机制禁止调用枚举类的构造方法；另外，枚举还天然支持序列化和反序列化，反序列化时 JVM 不会重新创建对象，而是返回已经存在的枚举实例。因此，枚举单例能够同时防止**反射破坏**和**序列化破坏**，是 Java 中最安全的单例实现方式。  





## 工厂模式是什么？解决了什么问题？  
工厂模式是一种**创建型设计模式**，它的核心思想是**将对象的创建过程封装起来，由工厂类负责创建对象，而不是由调用者直接通过 new 创建对象**。这样可以将对象的创建逻辑和业务使用逻辑解耦，提高代码的扩展性和维护性。当系统中需要创建大量具有共同接口但不同实现的对象时，如果直接 new 会导致代码大量依赖具体类，新增类型时需要频繁修改业务代码，而使用工厂模式后，调用者只需要依赖抽象接口，通过工厂获取对象即可，符合开闭原则。  



**工厂模式分类：**

| 类型 | 说明 |
| --- | --- |
| 简单工厂 | 一个工厂创建多种对象 |
| 工厂方法 | 一个工厂对应一种产品 |
| 抽象工厂 | 创建产品族 |






## 简单工厂、工厂方法、抽象工厂有什么区别？
简单工厂、工厂方法和抽象工厂都是创建型设计模式，主要区别在于**工厂负责创建对象的粒度不同以及扩展方式不同**。

**简单工厂**由一个工厂类负责创建所有产品，通过参数决定创建哪一种对象，实现简单，但是新增产品需要修改工厂代码；**工厂方法**将对象创建交给不同的具体工厂，每增加一种产品只需要增加对应的工厂和产品，不需要修改原有代码，更符合开闭原则；**抽象工厂**是在工厂方法的基础上进一步抽象，用于创建一系列相关的产品，比如同一个产品族中的多个对象。简单来说，简单工厂解决对象创建集中管理问题，工厂方法解决产品扩展问题，抽象工厂解决产品族创建问题。  

| 对比 | 简单工厂 | 工厂方法 | 抽象工厂 |
| --- | --- | --- | --- |
| **定义** | 一个工厂创建多个产品 | 一个工厂创建一种产品 | 一个工厂创建一组产品 |
| **工厂数量** | 一个 | 多个 | 多个 |
| **扩展方式** | 修改工厂 | 增加工厂 | 增加产品族 |
| **是否符合开闭原则** | ❌ | ✅ | ✅ |
| **复杂度** | 低 | 中 | 高 |
| **使用场景** | 产品较少且稳定 | 产品类型经常扩展 | 产品族场景 |








## 简单工厂和工厂方法有什么区别？  
简单工厂和工厂方法最大的区别在于**创建对象的职责是否由一个工厂类承担**。简单工厂通过一个工厂类根据条件判断创建不同产品，新增产品时需要修改工厂类代码，违反了开闭原则；而工厂方法模式将对象创建过程交给具体工厂子类，每增加一种产品，只需要增加对应的产品类和工厂类，不需要修改原有代码，更符合开闭原则。  

| 区别 | 简单工厂 | 工厂方法 |
| --- | --- | --- |
| **创建方式** | 一个工厂创建所有产品 | 一个工厂创建一种产品 |
| **工厂数量** | 一个 | 多个 |
| **判断逻辑** | 工厂内部 if/switch | 通过多态实现 |
| **扩展方式** | 修改工厂 | 增加工厂 |
| **是否符合开闭原则** | ❌ | ✅ |
| **复杂度** | 简单 | 更复杂 |






## 工厂模式一定比new好吗？  
工厂模式并不是一定比直接 new 更好，它解决的是**对象创建复杂、变化频繁、需要解耦的问题**。如果对象创建非常简单，而且不会发生变化，直接 new 反而更加清晰高效。工厂模式的优势在于将创建对象的逻辑封装起来，降低客户端和具体实现类之间的耦合，提高系统扩展性。但是如果滥用工厂模式，会增加大量类和代码复杂度。因此是否使用工厂模式，需要根据业务复杂度和扩展需求决定。  





## **<font style="color:rgb(51,51,51);">代理模式</font>**
代理模式是一种**结构型设计模式**，它通过为目标对象创建一个代理对象，由代理对象控制对目标对象的访问。客户端不直接访问真实对象，而是通过代理对象完成调用，从而可以在不修改目标对象代码的情况下，增加一些额外功能，比如权限控制、日志记录、事务管理、性能统计等。

代理模式的核心思想是：**访问对象时增加一个中间层，由代理对象代替真实对象完成一些额外操作，再调用真实对象的方法。**

****

**代理模式分类：**

| 类型 | 说明 | 特点 | 应用 |
| --- | --- | --- | --- |
| **静态代理** | 程序员手动创建代理类 | 简单直观，但代理类数量多 | 早期项目、简单场景 |
| **动态代理** | 运行期间动态生成代理对象 | 无需手写代理类，扩展性强 | Spring AOP、MyBatis |
| **远程代理** | 代理本地对象访问远程对象 | 隐藏网络通信细节 | RPC框架 |






## JDK 动态代理和CGLIB代理
JDK动态代理和CGLIB代理都是动态代理的实现方式，区别主要在于代理对象的生成方式不同。**JDK动态代理**是基于接口实现的，通过反射机制生成一个实现目标接口的代理类，因此目标对象必须实现接口；**CGLIB代理**是基于继承实现的，通过生成目标类的子类并重写父类方法实现代理，因此不需要目标类实现接口，但是目标类不能被 final 修饰。Spring AOP中，如果目标对象实现了接口，默认使用JDK动态代理；如果没有实现接口，则使用CGLIB代理。  

| 区别 | JDK动态代理 | CGLIB代理 |
| --- | --- | --- |
| **实现方式** | 实现接口 | 继承目标类 |
| **是否需要接口** | 必须需要 | 不需要 |
| **生成对象** | 接口实现类 | 目标子类 |
| **核心API** | Proxy | Enhancer |
| **调用方式** | 反射调用 | 方法覆盖 |
| **final限制** | 接口方法没有限制 | final类、final方法不能代理 |
| **性能** | 稍低 | 稍高 |
| **Spring使用** | 优先使用 | 无接口时使用 |

## **<font style="color:rgb(51,51,51);">装饰器模式是什么</font>**
装饰器模式是一种**结构型设计模式**，它通过创建一个包装对象，在不改变原对象结构的情况下，动态地给对象增加额外功能。装饰器模式的核心思想是通过组合代替继承，将功能拆分成多个装饰类，可以在运行时灵活组合。相比直接继承扩展功能，装饰器模式更加灵活，避免产生大量子类。  



**装饰器模式结构：**


![](https://cdn.nlark.com/yuque/__mermaid_v3/1446b63c346f07cecacc449e2b116f2a.svg)

| 角色 | 作用 |
| --- | --- |
| Component | 抽象组件，定义基础功能 |
| ConcreteComponent | 真实对象 |
| Decorator | 装饰器基类，持有组件对象 |
| ConcreteDecorator | 具体装饰，实现增强功能 |






## 装饰器模式和代理模式区别  
装饰器模式和代理模式的核心区别在于**目的不同**。**装饰器模式**主要是为了在不修改原对象的情况下，动态扩展对象功能，强调功能增强；**代理模式**主要是为了控制对象访问，强调对真实对象的保护和控制。两者结构上都采用了组合方式，都持有目标对象的引用，所以比较相似，但是使用场景不同。  

| 区别 | 装饰器模式 | 代理模式 |
| --- | --- | --- |
| **目的** | 增强对象功能 | 控制对象访问 |
| **关注点** | 增加功能 | 控制权限、隐藏对象 |
| **对象关系** | 装饰者和被装饰者都是同类对象 | 代理对象代表真实对象 |
| **是否改变功能** | 增加新功能 | 通常不改变核心功能 |
| **真实对象是否暴露** | 通常暴露 | 通常隐藏 |
| **数量** | 可以多个装饰器叠加 | 通常一个代理 |






## 模板方法模式是什么？  
模板方法模式是一种**行为型设计模式**，它通过在父类中定义一个算法执行流程的模板，将其中不变的步骤固定下来，而将可变的步骤交给子类实现。这样可以实现代码复用，同时保证算法流程的一致性。模板方法模式的核心思想是**把不变的流程放在父类，把变化的部分交给子类扩展**。  



**模板方法解决的问题：**

模板方法模式主要解决的是**多个类存在相同业务流程，但部分步骤实现不同，导致代码重复的问题**。它将公共流程抽取到父类中统一管理，将变化的部分交给子类实现，从而实现代码复用，并保证整体流程的一致性。  





## 模板方法为什么使用 final 修饰？  
模板方法中的模板方法通常使用 `final` 修饰，是为了**防止子类重写模板方法，破坏父类定义好的算法流程**。模板方法模式的核心思想是父类负责控制整体流程，子类只负责实现变化的步骤。如果允许子类修改模板方法，就可能导致流程顺序改变，破坏设计目的。  





## 模板方法违反开闭原则吗？  
模板方法模式不是完全符合开闭原则，它通过新增子类实现扩展，不需要修改父类，因此符合开闭原则的一部分。但是由于它依赖继承，如果父类模板流程发生变化，需要修改父类代码，并可能影响所有子类，所以存在一定违反。实际开发中，模板方法适用于流程固定、变化点明确的场景，例如 Spring 的 JdbcTemplate；如果变化频繁，更推荐使用策略模式等基于组合的设计。  





## 策略模式是什么？什么时候使用？  
策略模式是一种**行为型设计模式**，它的核心思想是将一组可以相互替换的算法封装成独立的策略类，并提供统一的接口，让业务代码和具体算法实现进行解耦。使用策略模式后，可以在运行时根据不同场景选择不同的策略，而不需要修改原有业务代码。

策略模式主要用于解决代码中大量 `if-else` 或 `switch `判断的问题，比如支付方式、优惠计算、订单配送、登录认证等场景。当一个功能存在多种实现方式，并且这些实现方式可能经常变化时，就可以使用策略模式。它可以提高代码的扩展性和可维护性，同时符合开闭原则。





## 策略模式如何消除大量if-else？
策略模式消除大量 if-else 的核心思想是**将不同的业务逻辑封装成不同的策略类，然后通过统一接口进行调用**。原本通过 if-else 判断选择哪种处理方式的代码，被拆分成多个独立策略，业务代码只依赖策略接口，不需要关心具体实现。

当新增一种策略时，只需要新增一个策略类，而不需要修改原来的判断逻辑，从而降低代码耦合，提高扩展性。





## 策略模式和模板方法模式区别？  
策略模式和模板方法模式都是为了提高代码复用和扩展性，但两者解决的问题不同。

**策略模式**关注的是算法的替换，它将一组不同的算法封装成独立的策略类，通过组合的方式在运行时选择不同策略。比如支付方式、优惠计算等场景，核心是“有多个算法，选择其中一个”。

**模板方法模式**关注的是流程复用，它在父类中定义一个固定的算法流程，将其中部分步骤延迟到子类实现。核心是“流程固定，部分步骤可以变化”。

简单来说，策略模式是通过组合实现行为替换，模板方法模式是通过继承实现流程复用。

| 对比 | 策略模式 | 模板方法模式 |
| --- | --- | --- |
| **类型** | 行为型设计模式 | 行为型设计模式 |
| **核心思想** | 替换整个算法 | 固定流程，替换部分步骤 |
| **实现方式** | 组合（委托） | 继承 |
| **变化内容** | 整个算法 | 某几个步骤 |
| **调用方式** | 外部选择策略 | 子类决定具体实现 |
| **灵活性** | 更高 | 相对固定 |






## 观察者模式是什么？  
观察者模式是一种**行为型设计模式**，它定义了对象之间**一对多的依赖关系**，当一个对象（被观察者）的状态发生变化时，会自动通知所有依赖它的对象（观察者），让它们进行相应处理。它主要解决的是**对象之间紧耦合的问题**，让被观察者不需要关心具体有哪些观察者，只负责发送通知即可，而观察者自己负责处理变化。在实现上，一般包含三个角色：**被观察者、观察者、通知机制**。被观察者维护一个观察者列表，当状态变化时调用通知方法，遍历所有观察者并执行更新操作。  





## Spring 中哪里使用观察者模式？  
Spring 中观察者模式主要应用在事件监听机制中，也就是 Spring 的事件发布与监听。Spring 提供了 ApplicationEvent、ApplicationListener 和 ApplicationEventPublisher，通过发布事件和监听事件实现对象之间的解耦。

当一个事件发生时，事件发布者只负责发布事件，不需要知道有哪些监听者；所有注册的监听器会自动收到通知并执行对应逻辑。这种一对多的通知机制就是观察者模式。
    



![](https://cdn.nlark.com/yuque/__mermaid_v3/9626789a8d293a983cbdb91b5e145f2c.svg)





## 为什么观察者模式符合开闭原则？  
观察者模式符合开闭原则，是因为它通过抽象的观察者接口，将事件发布者和具体业务处理逻辑进行解耦。当新增一种业务处理逻辑时，只需要新增一个观察者实现类，并注册到主题对象中，不需要修改原来的发布者代码，因此满足对扩展开放，对修改关闭。  





## 观察者模式和发布订阅模式有什么区别？ 
观察者模式和发布订阅模式都属于消息通知机制，核心思想都是一个对象状态变化后通知其他对象，但两者最大的区别在于通知过程是否通过中间层解耦。观察者模式中，观察者和被观察者之间是直接关联的，被观察者维护一个观察者列表，当状态发生变化时，直接调用观察者的方法进行通知，比如 JDK 中的 Observable。而发布订阅模式中，发布者和订阅者之间没有直接关系，它们通过一个**消息中心（Event Bus、MQ 等）**进行通信，发布者只负责发送消息，消息中心负责转发给对应的订阅者。因此，发布订阅模式的耦合度更低，更适合分布式系统和异步通信场景；观察者模式更简单，适合单体应用内部对象之间的状态同步。 

| 对比 | 观察者模式 | 发布订阅模式 |
| --- | --- | --- |
| **通信方式** | 直接通信 | 通过中间层通信 |
| **耦合度** | 较高 | 较低 |
| **是否有中间人** | ❌ 没有 | ✅ 有（消息中心） |
| **通知方式** | 同步通知为主 | 可以异步通知 |
| **关系** | 一对多 | 一对多 |
| **应用场景** | 对象状态变化通知 | 事件驱动、消息系统 |






## 享元模式
享元模式是一种**结构型设计模式**，主要用于减少大量重复对象的创建，通过**共享已经存在的对象来降低内存消耗**。它的核心思想是将对象中的状态分为**内部状态和外部状态**，内部状态是可以共享、不随环境变化的部分，存储在享元对象中；外部状态是随着使用场景变化的部分，由调用方传入。享元模式通常通过一个享元工厂维护一个对象池，当需要对象时先从池中查找，如果存在就直接返回，否则创建新的对象并缓存。它适用于系统中存在大量相似对象，并且对象创建成本较高的场景，例如 Java 中的字符串常量池、Integer 缓存池、线程池等。  


![](https://cdn.nlark.com/yuque/__puml/6732fe624864f1073dacf9e07279a57c.svg)

**内部状态：** 不随环境变化  、 可以共享  

**外部状态：** 根据环境变化、 不能共享  





## 享元模式和单例模式区别  
享元模式和单例模式都是为了减少对象创建、节省资源，但它们解决的问题不同。**单例模式**保证一个类在整个系统中只有一个实例，并提供全局访问点，关注的是对象数量唯一；而**享元模式**通过对象共享来减少大量相似对象的创建，关注的是对象复用和内存优化。单例模式只有一个对象，而享元模式可以有多个对象，只是相同的数据会被共享。单例模式通常用于配置类、线程池、连接池等场景；享元模式常用于大量重复对象的场景，比如字符串常量池、Integer 缓存、游戏中的棋子对象等。

| 对比 | 单例模式 | 享元模式 |
| --- | --- | --- |
| **目的** | 保证对象唯一 | 减少对象创建，复用对象 |
| **数量** | 只能有一个对象 | 可以有多个对象 |
| **关注点** | 控制对象数量 | 节省内存 |
| **创建方式** | 主动限制实例化 | 根据条件共享对象 |
| **状态** | 通常保存全局状态 | 通常分离内部状态和外部状态 |
| **典型场景** | 配置管理器、线程池 | 字符串池、对象缓存 |






## String为什么使用享元模式？  
Java 中的 String 使用享元模式主要是为了**减少大量重复字符串对象的创建，节省内存并提高性能**。因为在实际开发中，大量字符串内容可能是重复的，例如类名、变量名、配置项、日志信息等，如果每次都创建新的 String 对象，会造成大量内存浪费。因此 JVM 引入了**字符串常量池**，将相同内容的字符串进行缓存，当创建字符串时，会优先从常量池中查找，如果存在则直接返回已有对象，而不是重新创建。String 之所以适合使用享元模式，是因为它是不可变对象，字符串内容创建后不会改变，所以多个地方共享同一个 String 对象不会产生数据安全问题。 





## **<font style="color:rgb(51,51,51);">责任链模式</font>**
责任链模式是一种**行为型设计模式**，它将多个处理对象按照一定顺序组成一条处理链，请求沿着链依次传递，每个处理对象决定自己是否处理该请求，如果能处理就进行处理，否则交给下一个处理者。它的核心思想是**将请求发送者和处理者解耦，让多个对象都有机会处理请求**。   



**解决的问题：**① 避免大量 if-else 判断  

​                       ② 降低请求发送者和处理者的耦合  



| 角色 | 作用 |
| --- | --- |
| Handler（抽象处理者） | 定义处理请求的方法，并保存下一个处理者 |
| ConcreteHandler（具体处理者） | 处理自己负责的请求 |
| Client（客户端） | 创建责任链并发送请求 |




**优点：**

| 优点 | 说明 |
| --- | --- |
| 降低耦合 | 请求者不知道处理者 |
| 扩展方便 | 新增处理节点即可 |
| 符合开闭原则 | 增加处理逻辑不用修改原代码 |
| 职责清晰 | 每个处理者只负责自己的任务 |




**缺点：**

| 缺点 | 说明 |
| --- | --- |
| 请求可能无法处理 | 链尾没有处理者 |
| 性能问题 | 链过长会增加调用次数 |
| 调试困难 | 不知道最终哪个节点处理 |






## 责任链模式和策略模式有什么区别？  
责任链模式和策略模式最大的区别在于**解决的问题不同**。策略模式是为了让一个对象可以在多个算法或行为之间进行选择，客户端选择其中一种策略执行；而责任链模式是让多个处理对象按照一定顺序依次处理请求，一个处理者无法处理时交给下一个处理者。

简单来说，**策略模式强调“选择一个执行”，责任链模式强调“多个对象依次尝试处理”**。

| 对比 | 策略模式 | 责任链模式 |
| --- | --- | --- |
| **核心目的** | 选择不同算法 | 多个对象处理请求 |
| **处理对象数量** | 一个策略执行 | 多个处理者可能执行 |
| **调用关系** | 平级 | 链式关系 |
| **决策者** | 客户端或上下文决定 | 每个处理者自己判断 |
| **是否传递请求** | 不传递 | 会传递 |
| **关注点** | 怎么做 | 谁来做 |
| **常见场景** | 支付、排序、优惠计算 | 审批、过滤器、拦截器 |






## 责任链模式如何保证请求一定被处理？
责任链模式**无法天然保证请求一定被处理**，因为请求沿着责任链传递时，如果所有处理者都无法处理，并且链尾没有兜底处理者，请求就会丢失。为了保证请求一定被处理，通常有以下几种方式：

第一，**增加默认处理者（兜底节点）**。也就是在责任链末尾添加一个 DefaultHandler，当所有业务处理者都无法处理时，由它负责处理异常情况或者返回默认结果。

第二，**在链尾进行统一异常处理**。例如，如果请求遍历完整条链仍未处理，可以抛出异常，记录日志，或者返回错误信息，让调用方知道请求没有被处理。

第三，**在构建责任链时强制要求必须存在终止节点**。例如框架层统一创建责任链，不允许业务方随意创建没有结束节点的链。

所以责任链模式本身只负责**请求传递机制**，不保证一定成功处理，是否保证处理需要通过**兜底处理者、异常机制和链路校验**来实现。





## 什么是适配器模式？
适配器模式是一种**结构型设计模式**，它的作用是**将一个类的接口转换成客户端期望的另一个接口，使原本接口不兼容的类能够一起工作**。

简单来说，适配器模式就是在两个接口不匹配的对象之间增加一个转换层，让它们能够协同工作。它通过封装变化，降低了调用方和被适配类之间的耦合。





## Spring 中哪里使用适配器模式？  
Spring 中最典型的适配器模式应用是 **Spring MVC 的 HandlerAdapter（处理器适配器）**。Spring MVC 支持多种类型的 Controller，例如实现 Controller 接口、HttpRequestHandler、Servlet 等，它们的调用方式不同。DispatcherServlet 不直接调用这些 Controller，而是通过 HandlerAdapter 进行适配，将不同类型的处理器转换成统一的调用方式。

这样 DispatcherServlet 只需要调用 HandlerAdapter 的统一接口，而不需要关心具体 Controller 的实现类型，提高了系统扩展性和灵活性。
