## 分布式幂等性如何设计？
第一，**唯一业务号方案**，比如订单创建时生成唯一订单号，将订单号作为业务唯一标识，数据库建立唯一索引，第一次请求成功插入数据，后续重复请求因为唯一约束失败，从而保证幂等；

第二，**状态机控制**，对于订单、支付等业务，通过限制状态流转，比如订单只能从“待支付”变成“已支付”，重复支付请求发现状态已经变化，则直接返回成功；

第三，**幂等 Token 机制**，客户端第一次请求时获取一个唯一 Token，服务端处理请求前先校验 Token 是否已经使用，使用过则拒绝重复操作；

第四，**分布式锁方案**，使用 Redis 等实现分布式锁，在处理关键业务时保证同一业务只能被一个线程执行；

第五，**消息消费幂等**，MQ 消费者可以记录消息 ID 或业务 ID，消费前查询是否已经处理过，如果处理过则直接确认消息，不重复执行业务。  

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| **唯一业务号方案** | 1. 实现简单，只需要数据库唯一索引即可保证幂等；2. 性能高，利用数据库约束，不需要额外组件；3. 可靠性强，数据库天然保证唯一性 | 1. 依赖数据库唯一索引；2. 只能解决“重复创建”问题，不能解决业务状态变化问题；3. 高并发下大量重复请求可能导致数据库压力 | 订单创建、支付流水、交易记录等“一次性业务” |
| **状态机控制方案** | 1. 业务语义清晰；2. 可以控制复杂业务流程；3. 不仅保证幂等，还能防止非法状态转换 | 1. 需要设计状态流转规则，开发复杂度较高；2. 状态设计不好容易出现业务漏洞；3. 需要保证状态更新操作原子性 | 订单状态、支付状态、审批流程、任务状态 |
| **幂等 Token 机制** | 1. 可以在请求进入业务前拦截重复请求；2. 不依赖数据库业务字段；3. 对防止重复提交非常有效 | 1. 需要客户端配合获取 Token；2. Token 存储需要额外组件（Redis等）；3. Token失效时间设计复杂 | 表单提交、支付提交、下单接口、防重复点击 |
| **分布式锁方案** | 1. 可以保证同一时间只有一个请求执行；2. 适合解决并发竞争问题；3. 可以保护共享资源 | 1. 性能较低，会增加请求等待时间；2. 存在死锁风险；3. Redis锁需要考虑过期、续期、误删问题 | 秒杀扣库存、账户余额修改、库存更新 |
| **消息消费幂等方案** | 1. 可以解决 MQ 重复消费问题；2. 保证消息最终只执行一次业务效果；3. 提升消息系统可靠性 | 1. 需要额外保存消费记录；2. 消费记录表会不断增长，需要清理；3. 查询消费状态会增加数据库压力 | Kafka、RabbitMQ、RocketMQ 消费端处理 |






## Redis分布式锁能保证幂等吗？
Redis 分布式锁**可以辅助保证幂等，但不能单独保证完整的幂等性**。它主要解决的是**并发场景下同一时间只有一个请求执行**的问题，避免多个请求同时修改同一份数据。例如秒杀扣库存时，通过 Redis 分布式锁保证同一个商品库存不会被多个线程同时扣减。但是分布式锁只能保证执行过程中的互斥，如果请求执行失败后重试，或者锁释放后再次执行，仍然可能重复处理业务。因此实际项目中通常需要结合业务唯一号、数据库唯一索引、状态机等方案一起保证幂等。  





## MQ为什么会重复消费？  
MQ 会出现重复消费，主要是因为**消息队列为了保证消息可靠性，通常采用“至少一次投递（At Least Once）”机制**，即消息一定会送达，但可能重复发送。当消费者成功处理消息后，如果在返回 ACK 确认之前发生异常，比如消费者宕机、网络波动、ACK 丢失，MQ 会认为消息没有被成功消费，于是重新投递该消息，导致消费者再次处理同一条消息。另外，如果生产者发送消息时发生重试，也可能导致相同业务消息被写入多次。因此 MQ 消费端需要通过消息 ID、业务唯一号等方式实现幂等处理，避免重复消费造成业务错误。  

**原因：**① 消费者处理成功，但 ACK 丢失  

​	       ② 消费者宕机  

​           ③ 消息生产者重试  

​           ④ 消息队列自身重新投递 





## 幂等和防重复提交有什么区别？  
幂等和防重复提交的区别主要在于**解决的问题不同**。防重复提交主要是解决**同一个请求被用户或客户端重复发送的问题**，通常是在请求入口处进行拦截，比如使用 Token 机制、按钮防重复点击等，目的是减少重复请求进入系统；而幂等是解决**同一个业务操作执行多次，最终结果仍然保持一致的问题**，它关注的是业务结果是否正确。防重复提交属于幂等的一种辅助手段，但不能完全替代幂等，因为即使没有用户重复点击，也可能由于网络重试、MQ重复投递、服务故障恢复等原因导致同一个业务被执行多次。因此分布式系统中通常需要通过业务唯一号、状态机、数据库唯一索引等方式实现真正的业务幂等。  

| 对比 | 防重复提交 | 幂等 |
| --- | --- | --- |
| 解决问题 | 防止请求重复发送 | 防止业务重复执行产生错误结果 |
| 关注点 | 请求层面 | 业务层面 |
| 发生位置 | 请求入口 | 业务处理过程 |
| 目的 | 减少重复请求 | 保证最终结果正确 |
| 能否完全解决重复执行 | ❌ 不能 | ✅ 可以 |
| 常用方案 | Token、按钮置灰、前端限制 | 唯一索引、状态机、幂等表、MQ消费记录 |






## **<font style="color:rgb(51,51,51);">分布式事务</font>**

## **<font style="color:rgb(51,51,51);">什么是补偿事务？</font>**
补偿事务是一种通过**执行反向操作来弥补已经完成操作造成影响的分布式事务解决方案**。它的核心思想不是像数据库事务一样直接回滚，而是在事务执行失败后，根据业务逻辑编写一个补偿操作，将已经执行成功的部分进行恢复，从而达到最终一致性。例如订单支付过程中，库存扣减成功，但支付失败，可以通过补偿事务执行库存释放操作，将扣减的库存加回来。补偿事务适用于长事务和跨服务场景，常见实现方式包括 TCC 中的 Cancel 阶段、Saga 模式等。  

![](https://cdn.nlark.com/yuque/__mermaid_v3/46284764cc69c86d17f4d2acc05e4d45.svg)

特点：

| 特点 | 说明 |
| --- | --- |
| 最终一致性 | 最终数据达到一致 |
| 业务侵入高 | 需要编写补偿逻辑 |
| 不是立即回滚 | 通过后续操作恢复 |
| 适合长事务 | 跨服务、跨系统 |


**和数据库回滚区别：**

回滚是**数据库层面**的撤销操作，补偿事务是**业务层面**的反向操作。 

|  | 数据库Rollback | 补偿事务 |
| --- | --- | --- |
| 范围 | 单数据库 | 跨服务 |
| 方式 | 撤销当前事务 | 执行反向业务 |
| 时间 | 立即完成 | 可能延迟 |
| 实现 | 数据库提供 | 开发人员实现 |






## **<font style="color:rgb(51,51,51);">Saga事务模型</font>**
Saga事务模型是一种基于补偿机制实现的分布式事务方案，它将一个长事务拆分成多个本地事务，每个本地事务执行成功后立即提交，如果后续事务失败，则按照相反顺序执行补偿事务，撤销之前已经完成的业务操作。

Saga主要有两种实现方式，一种是**编排式**，由各个服务通过消息驱动完成事务流程；另一种是**协调式**，由事务协调器统一控制事务执行和补偿。相比2PC，Saga性能更高、不会长期锁资源，但只能保证最终一致性，并且需要解决补偿失败和幂等问题。  



**编排式 Saga： **没有中心协调者，每个服务完成自己的事务后，通过消息通知下一个服务。 ** **

![](https://cdn.nlark.com/yuque/__mermaid_v3/797b045f0c71a81493645340f9181f5e.svg)

优点：

+  简单 
+  服务之间松耦合 
+  不需要事务协调器 

缺点：

+  业务流程复杂后难维护 
+  服务之间依赖关系混乱 
+  难追踪事务状态

---



**协调式 Saga：** 通过一个 Saga Coordinator（事务协调器）统一管理  

![](https://cdn.nlark.com/yuque/__mermaid_v3/81253cf6d55c61153ce4fcaf2f5fd829.svg)





## Saga为什么不能保证强一致性？  
 Saga 不能保证强一致性，主要原因是它采用的是**最终一致性模型**，而不是像传统数据库事务一样通过锁和两阶段提交保证所有操作同时成功或同时失败。Saga 会把一个大的分布式事务拆分成多个本地事务，每个本地事务执行成功后立即提交并释放资源，如果后续某个事务失败，就通过执行补偿事务来撤销之前已经完成的操作。但是在这个过程中，会存在一个时间窗口：前面的事务已经提交，后面的事务还没有完成或者失败，此时系统数据处于**中间状态**。例如订单创建成功、库存扣减成功，但支付失败，这时候需要执行补偿事务恢复库存和订单状态，在补偿完成之前，其他请求可能已经读取到了不一致的数据。因此 Saga 无法保证事务执行期间数据始终一致，只能保证经过补偿后最终达到一致状态。  





## Saga补偿失败怎么办？  
Saga 补偿失败时，不能简单依赖一次补偿完成，而是需要通过**重试机制、补偿幂等、人工介入和状态管理**等方式保证最终一致性。一般做法是：首先对补偿事务进行自动重试，如果多次重试仍然失败，则记录异常状态并进入人工处理流程，同时通过消息可靠投递、补偿日志等机制保证后续可以继续恢复。因为 Saga 本身不支持像数据库事务一样的回滚，所以补偿事务必须设计成**幂等的、可重复执行的操作**，最终目标是让业务状态达到一致。  

![](https://cdn.nlark.com/yuque/__mermaid_v3/50f8b332264dc1115b2539fbf74d43f8.svg)





## 为什么 Saga 的补偿事务必须保证幂等？  
Saga 的补偿事务必须保证幂等，是因为 Saga 不像传统数据库事务一样可以直接回滚，而是通过执行反向操作来恢复数据。当补偿过程中出现网络超时、服务宕机、消息重复投递等情况时，补偿事务可能会被多次执行。如果补偿操作不是幂等的，就可能导致重复扣减、重复退款、库存恢复过多等问题。所以在设计 Saga 补偿事务时，需要保证同一个补偿请求执行一次和执行多次的结果一致，从而保证分布式环境下数据最终一致。  

**Saga 为什么容易出现重复补偿？**  

| 原因 | 说明 |
| --- | --- |
| 网络超时 | 请求已经执行成功，但是响应丢失，调用方认为失败 |
| 服务宕机 | 补偿执行过程中服务挂掉，需要重新执行 |
| 消息重复消费 | MQ 为保证可靠性可能重复投递消息 |
| Saga协调者重启 | 需要根据日志恢复状态，可能重新触发补偿 |






## 为什么需要分布式ID？  
分布式 ID 主要是为了解决**分布式系统中数据唯一标识的问题**。在单体应用中，可以直接使用数据库自增 ID，但是在微服务或者分布式环境下，多个服务、多个数据库节点可能同时生成数据，如果继续使用自增 ID，容易出现 ID 冲突、性能瓶颈以及扩展困难的问题。因此需要一个能够在分布式环境下生成**全局唯一、高性能、有序性较好的 ID 生成方案**，比如雪花算法、UUID、数据库号段模式等。  

| 要求 | 说明 |
| --- | --- |
| 唯一性 | 不同节点生成的ID不能重复 |
| 高性能 | 不能每次生成都访问数据库 |
| 高可用 | 生成服务不能轻易宕机 |
| 趋势递增 | 方便数据库索引 |
| 安全性 | 避免暴露业务规模 |






## **<font style="color:rgb(51,51,51);">分布式ID生成有几种方案？</font>**
分布式 ID 生成方案主要有 **UUID、数据库自增 ID、数据库号段模式、Redis 生成 ID、雪花算法(Snowflake)、Leaf、美团 Leaf 等方案**。在实际生产环境中，最常用的是**号段模式和雪花算法**。UUID 优点是生成简单、全局唯一，不需要依赖中心服务，但是长度较长且无序，不适合数据库索引；数据库自增 ID 实现简单，但是依赖单库，扩展性较差；Redis 方案性能高，但是依赖 Redis 可用性；号段模式通过批量申请 ID 段减少数据库压力；雪花算法通过时间戳、机器编号、序列号组成 64 位 ID，保证高性能、高可用并且趋势递增，被很多分布式系统采用。

| 方案 | 原理 | 优点 | 缺点 | 使用场景 |
| --- | --- | --- | --- | --- |
| **UUID** | 随机生成 128 位字符串 | 简单、全球唯一 | 无序、占空间大 | 文件ID、非核心业务 |
| **数据库自增** | 利用数据库 AUTO_INCREMENT | 简单可靠 | 单点、扩展差 | 单体应用 |
| **数据库号段模式** | 一次申请一批 ID | 性能高、减少DB压力 | 依赖数据库 | 大多数业务系统 |
| **Redis** | Redis INCR 自增 | 性能高 | 依赖Redis | 高并发业务 |
| **雪花算法** | 时间+机器+序列 | 高性能、有序 | 时钟问题 | 微服务订单ID |
| **Leaf** | 美团开源方案 | 高性能、高可用 | 部署复杂 | 大型互联网系统 |






## 雪花算法原理
雪花算法是一种分布式 ID 生成算法，核心思想是将一个 ID 拆分成**时间戳、机器 ID、序列号**三部分，通过位运算组合成一个 64 位整数，从而保证在分布式环境下生成全局唯一的 ID。

雪花算法中最高位 1 位固定为 0，表示正数；41 位表示时间戳，用来保证不同时间生成的 ID 不重复；10 位表示机器 ID，用来区分不同服务器节点；12 位表示序列号，用来解决同一台机器同一毫秒内生成多个 ID 的问题。

生成 ID 时，首先获取当前时间戳，如果和上一次生成 ID 的时间相同，就递增序列号；如果进入新的毫秒，则序列号重新从 0 开始。最后将时间戳、机器 ID 和序列号通过位运算拼接，生成最终 ID。

它的优点是生成速度快、不依赖数据库、支持分布式部署，并且生成的 ID 基本趋势递增，适合订单 ID、用户 ID 等业务场景。

**格式：** `0 | 时间戳(41位) | 机器ID(10位) | 序列号(12位)`

| 部分 | 位数 | 作用 |
| --- | --- | --- |
| **符号位** | 1位 | 固定为0，保证正数 |
| **时间戳** | 41位 | 保证不同时间唯一 |
| **机器ID** | 10位 | 保证不同节点唯一 |
| **序列号** | 12位 | 保证同毫秒内唯一 |

## **雪花算法为什么会出现 ID 重复？如何解决？**
雪花算法出现 ID 重复主要有三个原因。第一是**机器 ID 重复**，因为雪花算法依赖 workerId 区分不同节点，如果多个节点配置了相同的机器 ID，那么在相同时间和序列号下就可能生成重复 ID，解决方式是使用 ZooKeeper、Nacos 等方式动态分配机器 ID。第二是**时钟回拨**，雪花算法依赖系统时间，如果服务器时间回退，可能导致生成相同的时间戳，从而产生重复 ID，解决方式是检测到回拨后等待时间恢复，或者直接拒绝生成。第三是**序列号溢出**，同一机器同一毫秒内生成的 ID 超过序列号容量时，也可能出现问题，可以通过等待下一毫秒生成或者扩展序列号位数解决。实际生产中一般通过保证 workerId 唯一和增加时钟回拨保护机制来避免 ID 冲突。  



### 为什么时钟回拨会导致 ID 重复？  
因为雪花算法中的时间戳是 ID 的重要组成部分，如果系统时间从 10000 回退到 9990，那么后续生成的 ID 可能使用已经使用过的时间戳，再结合相同的机器 ID 和序列号，就可能产生重复。  

  

### 生产环境如何解决时钟回拨？  
 常见做法是增加时钟回拨检测，如果发现当前时间小于上一次生成 ID 的时间，就停止生成或者等待时间追上；一些成熟方案比如美团 Leaf 会通过扩展机制降低时钟回拨带来的影响。  







## 限流算法
常见的限流算法主要有 **固定窗口、滑动窗口、漏桶算法、令牌桶算法** 四种。其中生产环境中最常用的是**令牌桶算法和漏桶算法**。固定窗口实现简单，但是存在临界突发流量问题；滑动窗口通过记录时间段内的请求数量解决了固定窗口的不连续问题；漏桶算法能够严格控制请求处理速度，保证系统稳定；令牌桶算法允许一定程度的突发流量，同时限制平均请求速率，是网关和服务限流中最常用的方案。  

| 算法 | 特点 | 优点 | 缺点 | 使用场景 |
| --- | --- | --- | --- | --- |
| **固定窗口** | 固定时间计数 | 简单 | 临界突发 | 简单接口 |
| **滑动窗口** | 统计最近时间 | 准确 | 实现复杂 | Sentinel |
| **漏桶** | 固定速度处理 | 稳定 | 不能突发 | 流量整形 |
| **令牌桶** | 令牌控制 | 允许突发 | 实现复杂 | 网关限流 |






### 说说什么是固定窗口算法
固定窗口算法是一种最简单的限流算法，它将时间划分为一个个固定长度的窗口，在每个时间窗口内维护一个请求计数器，当请求数量超过设定阈值时，拒绝后续请求。例如限制接口每秒最多处理100个请求，那么系统会每1秒创建一个窗口，并统计这个窗口内的请求数量，如果超过100，则进行限流。固定窗口算法实现简单、性能高，但是存在**临界突发问题**，即在两个时间窗口交界处可能出现短时间内大量请求通过，导致实际流量超过限制。  

![](https://cdn.nlark.com/yuque/__mermaid_v3/f16ac5006572c57d91c1ed02e000dfd3.svg)



### 说说什么是滑动窗口算法
滑动窗口算法是对固定窗口算法的一种优化，它通过将一个大的时间窗口划分成多个小窗口，并不断随着时间向前移动，只统计当前时间范围内的请求数量，从而解决固定窗口在边界处出现流量突发的问题。例如限制接口1秒最多100个请求，可以将1秒划分成多个小窗口，实时统计最近1秒内的请求数量，如果超过阈值则拒绝请求。相比固定窗口，滑动窗口限流更加精准，但是需要维护更多时间窗口数据，实现复杂度和内存开销更高。  

![](https://cdn.nlark.com/yuque/__mermaid_v3/b7f2b0a806a1660890937fbb5140712b.svg)

| 对比 | 固定窗口 | 滑动窗口 |
| --- | --- | --- |
| **统计范围** | 固定时间段 | 最近时间段 |
| **窗口是否移动** | 否 | 是 |
| **准确性** | 低 | 高 |
| **实现难度** | 简单 | 复杂 |
| **是否存在边界突发** | 存在 | 基本解决 |


**滑动窗口如何解决固定窗口的临界问题？  **

固定窗口限流的问题主要是存在**临界突发问题**。比如限制接口每秒最多允许100个请求，如果在第1秒最后几毫秒来了100个请求，在第2秒开始又来了100个请求，那么实际上在很短时间内可能通过200个请求，超过了系统承受能力。

滑动窗口通过将一个固定时间窗口划分成多个小窗口，并且随着时间不断移动，只统计当前时间范围内的请求数量，从而避免了固定窗口边界处的流量突增问题，使限流更加准确和平滑。





### 令牌桶和漏桶有什么区别？  
令牌桶和漏桶都是用于**限流**的算法，主要区别在于处理突发流量的方式不同。令牌桶是系统按照固定速率生成令牌，请求过来时需要获取令牌，获取成功才能访问。因为令牌可以提前积累，所以令牌桶允许一定程度的突发流量。漏桶则像一个固定容量的桶，请求先进入桶中，然后按照固定速率流出，超过桶容量的请求会被丢弃，因此漏桶能够严格控制请求处理速率。简单来说，**令牌桶允许突发流量，保证平均速率；漏桶强调平滑流量，保证处理速率恒定。**

## **<font style="color:rgb(51,51,51);">如何提高系统的并发能力？</font>**
提高系统并发能力主要从**架构设计、数据库优化、缓存、异步化、限流、服务拆分和资源优化**几个方面入手。首先可以通过增加服务器节点和负载均衡实现水平扩展，提高系统整体吞吐量；其次使用缓存减少数据库压力，例如 Redis 缓存热点数据；对于耗时操作可以采用消息队列进行异步处理，提高请求响应速度；数据库层面可以通过索引优化、读写分离、分库分表提高处理能力；微服务架构中可以通过服务拆分和限流熔断保护系统稳定性。同时还需要优化代码和 JVM 参数，减少资源消耗。整体思路是**减少单点压力、提高资源利用率、削峰填谷、让系统具备横向扩展能力**。

## **<font style="color:rgb(51,51,51);">数据库如何处理海量数据？</font>**
数据库处理海量数据主要通过**分库分表、索引优化、读写分离、分区表、缓存、归档数据以及数据库集群**等方式提升存储能力和访问性能。

首先，通过**分库分表**将大量数据拆分到多个数据库或数据表中，降低单表数据量和数据库压力；其次，通过建立合理的**索引**提高查询效率，避免全表扫描；对于读多写少的场景，可以使用**读写分离**，让主库负责写操作，从库负责读操作，提高并发能力；另外，可以使用**缓存**减少数据库访问压力，将热点数据放入 Redis 等缓存中。对于历史数据，可以进行**数据归档**，减少在线数据库的数据量。

| 方案 | 解决问题 |
| --- | --- |
| **分库分表** | 解决数据量过大和单库压力 |
| **索引优化** | 提高查询速度 |
| **读写分离** | 提高读并发 |
| **分区表** | 减少扫描范围 |
| **缓存** | 减少数据库访问 |
| **数据归档** | 降低在线数据量 |
| **数据库集群** | 提高整体扩展能力 |
