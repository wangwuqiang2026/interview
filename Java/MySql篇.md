## MySQL 的存储引擎有哪些？  
MySQL 的存储引擎主要有 **InnoDB、MyISAM、Memory、Archive、CSV** 等，其中最常用的是 **InnoDB**。InnoDB 是 MySQL 5.5 之后默认的存储引擎，支持**事务、行级锁、外键和崩溃恢复**，适合大多数业务场景。MyISAM 不支持事务，但查询速度较快，支持表级锁，适合读多写少的场景。Memory 将数据存储在内存中，访问速度非常快，但数据重启后会丢失，适合临时数据。Archive 主要用于数据归档，只支持插入和查询，适合存储历史数据。CSV 用文本文件保存数据，方便数据交换，但功能较少。  

| 存储引擎 | 特点 | 是否支持事务 | 锁粒度 | 适用场景 |
| --- | --- | --- | --- | --- |
| **InnoDB** | MySQL 默认引擎，支持事务、MVCC、崩溃恢复 | ✅ 支持 | 行锁 | 订单、支付、用户等核心业务 |
| **MyISAM** | 查询性能高，结构简单 | ❌ 不支持 | 表锁 | 读多写少、历史数据查询 |
| **Memory** | 数据存储在内存，速度快 | ❌ 不支持 | 表锁 | 临时缓存数据 |
| **Archive** | 高压缩存储，只支持增删查 | ❌ 不支持 | 行锁 | 日志、归档数据 |
| **CSV** | 数据以 CSV 文件保存 | ❌ 不支持 | 表锁 | 数据交换 |






## 为什么 MySQL 默认选择 InnoDB？  
MySQL 默认选择 InnoDB，主要是因为 **InnoDB 在事务支持、并发能力、数据安全和高可用方面更符合现代业务数据库的需求**。首先，InnoDB 支持事务，满足 ACID 特性，并且通过 **redo log、undo log 和 MVCC** 实现事务的可靠性和高并发访问；其次，InnoDB 支持**行级锁**，相比 MyISAM 的表锁，在多用户并发读写场景下性能更好；另外，InnoDB 支持**外键、崩溃恢复和数据持久化**，能够保证数据的一致性和安全性。因此，对于大多数 Web 应用和企业级系统来说，InnoDB 比 MyISAM 更适合作为默认存储引擎。  





## InnoDB 和 MyISAM 有什么区别？  
InnoDB 和 MyISAM 是 MySQL 常见的两种存储引擎，它们最大的区别在于 **事务、锁、索引结构和数据安全性**。InnoDB 支持事务，满足 ACID 特性，并且支持行级锁、MVCC 和崩溃恢复，适合高并发、需要数据一致性的业务场景，例如订单、支付系统；MyISAM 不支持事务，只支持表级锁，查询性能较高，但并发写能力和数据安全性较弱，适合读多写少、对事务要求不高的场景。因此现在 MySQL 默认使用 InnoDB，而 MyISAM 主要用于一些简单查询场景。  

| 对比项 | InnoDB | MyISAM |
| --- | --- | --- |
| **事务支持** | ✅ 支持事务 | ❌ 不支持事务 |
| **ACID特性** | ✅ 支持 | ❌ 不支持 |
| **锁机制** | 行锁、表锁 | 表锁 |
| **并发能力** | 高 | 较低 |
| **MVCC** | ✅ 支持 | ❌ 不支持 |
| **外键** | ✅ 支持 | ❌ 不支持 |
| **崩溃恢复** | 强（redo log恢复） | 弱 |
| **索引结构** | B+Tree | B+Tree |
| **数据和索引存储** | 聚簇索引 | 非聚簇索引 |
| **适合场景** | 高并发业务 | 查询型业务 |






## InnoDB 为什么支持事务？  
InnoDB 支持事务主要是因为它实现了事务所需要的 **ACID 特性**。其中，InnoDB 通过 **redo log 保证持久性，通过 undo log 实现回滚和 MVCC，通过锁机制保证隔离性，通过事务管理保证原子性**。当事务提交时，数据会先记录 redo log，保证即使数据库宕机也能恢复；当事务执行失败时，可以通过 undo log 回滚到事务开始前的状态；同时 InnoDB 使用 MVCC 和锁机制解决多个事务并发访问的问题。因此，InnoDB 能够保证事务的原子性、一致性、隔离性和持久性。  





## undo log、redo log、binlog分别是什么？
MySQL 中的 undo log、redo log、binlog 是保证事务可靠性和数据一致性的三种重要日志，它们分别解决不同的问题。

**undo log（回滚日志）**主要用于事务回滚和 MVCC。事务修改数据之前，会将旧版本数据保存到 undo log 中，如果事务失败或者执行 ROLLBACK，可以利用 undo log 恢复原来的数据；同时 MVCC 通过 undo log 保存历史版本，实现一致性读。

**redo log（重做日志）**是 InnoDB 存储引擎层的日志，用于保证事务的持久性。当事务修改数据时，InnoDB 不会立即将数据页刷入磁盘，而是先记录 redo log。即使 MySQL 崩溃，重启后也可以通过 redo log 恢复已经提交的数据。

**binlog（二进制日志）**是 MySQL Server 层的日志，记录所有修改数据库的操作，主要用于主从复制和数据恢复。

| 区别 | undo log | redo log | binlog |
| --- | --- | --- | --- |
| **中文** | 回滚日志 | 重做日志 | 二进制日志 |
| **所属层** | InnoDB | InnoDB | MySQL Server |
| **作用** | 回滚、MVCC | 崩溃恢复 | 主从复制、恢复 |
| **记录内容** | 修改前的数据 | 数据页变化 | SQL操作或行变化 |
| **空间** | 通常较大 | 固定大小循环写 | 持续增长 |
| **事务提交** | 不决定事务持久性 | 保证持久性 | 保证复制 |
| **是否支持恢复** | 回滚 | 恢复已提交事务 | 恢复历史操作 |








## InnoDB 为什么需要 redo log，而不是直接修改磁盘？  
InnoDB 需要 redo log，而不是直接修改磁盘，主要是为了**提高数据库性能并保证事务的持久性**。如果每次修改数据都直接写磁盘，由于磁盘随机写性能较低，会导致数据库性能严重下降。而 InnoDB 采用 **WAL（Write Ahead Logging，预写日志）机制**，先将修改记录写入 redo log，再异步将数据刷入磁盘。这样事务提交时只需要进行顺序写日志，速度更快；如果 MySQL 宕机，可以通过 redo log 重新执行已经提交的修改，保证数据不会丢失。

## redo log什么时候刷盘？  
redo log 的刷盘时机主要有三种情况：**事务提交时刷盘、redo log buffer 空间不足时刷盘、后台线程周期性刷盘**。其中最重要的是事务提交时是否刷盘，它由参数 `innodb_flush_log_at_trx_commit` 控制。MySQL 默认值为 `1`，表示每次事务提交都会将 redo log 从内存刷入磁盘，能够保证事务的持久性；如果设置为 `0` 或 `2`，可以提高性能，但可能在宕机时丢失部分事务数据。  

| 参数值 | redo log写入 | 是否刷磁盘 | 数据安全 |
| --- | --- | --- | --- |
| 0 | 事务提交时只写内存 | 后台刷盘 | 最低 |
| 1 | 事务提交时写入并刷盘 | 立即刷盘 | 最高（默认） |
| 2 | 事务提交时写磁盘缓存 | 后台刷盘 | 中等 |






## redo log 和 undo log 有什么区别？  
redo log 和 undo log 都是 InnoDB 保证事务可靠性的日志，但作用不同。**redo log **用于保证事务的持久性，记录的是数据修改后的结果，用于数据库宕机后的恢复；**undo log** 用于保证事务的原子性，记录的是数据修改前的状态，用于事务回滚，同时也是 MVCC 实现的重要基础。简单来说，redo log 负责“恢复已提交的数据”，undo log 负责“撤销未完成的操作”。  

| 对比 | redo log | undo log |
| --- | --- | --- |
| 中文名称 | 重做日志 | 回滚日志 |
| 作用 | 保证事务持久性 | 保证事务原子性 |
| 记录内容 | 修改后的数据 | 修改前的数据 |
| 用途 | 宕机恢复 | 事务回滚、MVCC |
| 写入时机 | 修改数据时记录 | 修改数据前记录 |
| 存储位置 | redo log 文件 | undo log 段 |
| 是否循环使用 | 是 | 是 |






## redo log 和 binlog 有什么区别？  
redo log 和 binlog 都是 MySQL 用来保证数据可靠性的日志，但作用和层次不同。**redo log** 是 InnoDB 存储引擎层的日志，记录的是数据页的物理变化，主要用于数据库崩溃后的恢复，保证事务的持久性；**binlog** 是 MySQL Server 层的日志，记录的是数据库的逻辑操作，主要用于主从复制和数据恢复。简单来说，redo log 负责“数据库自己恢复数据”，binlog 负责“数据同步和归档”。  





## MySQL 两阶段提交为什么需要 redo log 和 binlog 配合？  
MySQL 两阶段提交需要 redo log 和 binlog 配合，是为了保证 **redo log 和 binlog 两份日志的数据一致性**。因为 redo log 负责 InnoDB 的崩溃恢复，binlog 负责主从复制和数据恢复，如果两者记录状态不一致，就可能导致数据库恢复后数据和从库数据不一致。所以 MySQL 使用两阶段提交，将事务提交过程拆成 **prepare 和 commit 两个阶段**，保证 redo log 和 binlog 要么都成功，要么都失败。

## MySQL 主从复制原理是什么？
MySQL 主从复制是指将**主库（Master）的数据变化同步到一个或多个从库（Slave）**，从而实现数据备份、读写分离和高可用。

MySQL 主从复制主要依靠 **binlog（二进制日志）** 实现。

主库执行事务后，会将数据修改记录到 binlog 中；从库通过 IO 线程读取主库的 binlog，并写入自己的 relay log（中继日志），然后由 SQL 线程读取 relay log 并重新执行其中的 SQL 操作，最终实现主从数据一致。
![](https://cdn.nlark.com/yuque/__mermaid_v3/6444e999f884f6dbb74db726d1fb8a27.svg)





## MySQL 主从复制延迟如何解决？
MySQL 主从复制延迟是指**主库已经执行完成的事务，在从库还没有同步完成，导致主从数据存在时间差**。解决主从复制延迟，主要从**减少复制压力、提高从库同步能力、优化事务设计、调整复制架构**几个方面入手。

首先，可以**减少主库产生的 binlog 压力**，例如优化大事务，避免一次性更新大量数据，因为大事务会导致从库 SQL 线程长时间执行，产生延迟；同时尽量拆分批量操作。

其次，提高从库的复制能力，可以开启**并行复制**。MySQL 5.7 引入了基于逻辑时钟的并行复制，MySQL 8.0 默认支持更完善的并行复制机制，可以让多个线程同时执行 relay log 中的事务，提高同步速度。

第三，可以优化数据库和 SQL，例如给从库配置更好的硬件资源，提高 CPU、磁盘 IO 性能；优化慢 SQL，减少锁竞争；合理设置 InnoDB 参数，例如增加 buffer pool，提高数据读取效率。

第四，可以调整业务架构，例如**读写分离时不要强制所有查询走从库**。对于刚写入的数据，如果马上读取，可以采用读主库策略，避免因为主从延迟导致读不到最新数据。

第五，对于高并发场景，可以增加多个从库进行负载均衡，或者采用分库分表、缓存等方式降低单个从库压力。

如果主从延迟已经发生，可以通过查看 `Seconds_Behind_Master` 判断延迟情况，并分析是 IO 线程延迟还是 SQL 线程执行慢，然后针对性处理。

| 方案 | 作用 |
| --- | --- |
| **开启并行复制** | 提高从库 SQL 执行能力 |
| **减少大事务** | 降低 relay log 堆积 |
| **优化 SQL** | 减少锁等待 |
| **提升从库硬件** | 提高执行速度 |
| **增加从库数量** | 分散读压力 |
| **读写分离优化** | 避免读取旧数据 |
| **缓存热点数据** | 减少数据库压力 |








## MySQL 为什么不先写 binlog，再写 redo log？  
MySQL 采用先写 redo log，再写 binlog 的顺序，是因为 redo log 是 InnoDB 存储引擎保证崩溃恢复的核心。如果先写 binlog，后写 redo log，在 binlog 已经记录事务但 redo log 还没有持久化时发生宕机，数据库恢复时无法通过 redo log 恢复数据，会导致 binlog 和实际数据不一致，造成主从复制异常。因此 MySQL 通过两阶段提交保证 redo log 和 binlog 的一致性。  





## MySQL 索引是什么？为什么使用索引？  
MySQL 索引是一种**帮助数据库快速查询数据的数据结构**，本质上是对表中某些字段建立的目录。它通过空间换时间的方式，将数据按照一定规则组织起来，使数据库不需要扫描整张表，而是可以通过索引快速定位数据。使用索引主要是为了**提高查询效率，降低数据库 IO 开销**。在 MySQL 中，InnoDB 默认使用 **B+Tree 索引**，它具有查询效率高、支持范围查询和排序等特点。  

| 索引类型 | 作用 |
| --- | --- |
| 普通索引 | 加速查询 |
| 唯一索引 | 保证唯一性 |
| 主键索引 | 唯一 + 非空 |
| 联合索引 | 多字段查询优化 |
| 全文索引 | 文本搜索 |






## 普通索引和唯一索引有什么区别？
普通索引和唯一索引最大的区别在于**是否限制字段值重复**。

普通索引允许索引列存在重复值，主要作用是提高查询效率。例如多个用户可以有相同的姓名，可以给 `name` 字段建立普通索引。而唯一索引要求索引列的值必须唯一，除了提高查询效率之外，还可以保证数据的唯一性，例如用户邮箱、手机号等字段通常会建立唯一索引。

在查询方面，普通索引和唯一索引的查询过程基本类似，都是通过 B+Tree 快速定位数据。区别在于唯一索引找到满足条件的数据后，可以直接确定不会存在其他相同记录，而普通索引还需要继续向后查找相同值的记录。

在写入方面，唯一索引性能通常略低于普通索引，因为插入数据时需要额外进行唯一性检查，判断该值是否已经存在。

因此，普通索引主要用于提升查询效率，而唯一索引除了优化查询外，还承担数据唯一性约束的作用。

| 区别 | 普通索引 | 唯一索引 |
| --- | --- | --- |
| **唯一性** | 允许重复 | 必须唯一 |
| **主要作用** | 提高查询效率 | 查询 + 数据约束 |
| **底层结构** | B+Tree | B+Tree |
| **查询性能** | 稍低 | 稍高 |
| **写入性能** | 较高 | 略低 |
| **是否支持重复值** | 是 | 否 |
| **是否支持多个NULL** | 是 | 是 |
| **Change Buffer** | 支持 | 不支持 |






## 聚簇索引和非聚簇索引有什么区别？
聚簇索引和非聚簇索引的主要区别在于 **索引结构中是否存储完整的数据记录**。在 InnoDB 中，主键索引就是聚簇索引，叶子节点直接存储整行数据；而普通索引属于非聚簇索引，叶子节点存储的是索引字段值和对应的主键值，查询完整数据时还需要根据主键再次查找，这个过程叫回表。简单来说，**聚簇索引决定数据的物理存储顺序，一个表只能有一个；非聚簇索引只是额外建立的查找目录，一个表可以有多个。**

| 区别 | 聚簇索引 | 非聚簇索引 |
| --- | --- | --- |
| **叶子节点存储** | 完整数据行 | 索引值+主键 |
| **数据和索引关系** | 合在一起 | 分离 |
| **数量** | 一个表只能一个 | 一个表可以多个 |
| **InnoDB中** | 主键索引 | 普通索引 |
| **查询效率** | 通常更高 | 可能需要回表 |
| **决定数据存储顺序** | 是 | 否 |






## 为什么 InnoDB 必须使用聚簇索引？  
InnoDB 使用聚簇索引主要是因为它需要将**索引和数据存储在一起**，这样可以减少一次数据查询的 IO，提高查询效率。InnoDB 的数据本身就是按照主键索引组织存放的，因此主键索引就是聚簇索引，叶子节点直接存储完整的数据行。相比 MyISAM 的非聚簇索引，InnoDB 查询数据时不需要通过索引再回表查找数据，访问速度更快。同时，InnoDB 使用聚簇索引也方便实现 MVCC、范围查询以及数据页管理。  







## InnoDB 主键索引和普通索引有什么区别？  
InnoDB 中主键索引和普通索引最大的区别在于叶子节点存储内容不同。主键索引的叶子节点存储完整的数据行，因此也叫聚簇索引；普通索引的叶子节点存储索引字段和对应的主键值，因此也叫二级索引。通过普通索引查询完整数据时，需要先找到主键，再根据主键查询主键索引，这个过程叫回表。由于主键索引决定了数据的物理组织方式，所以一个表只能有一个主键索引，而普通索引可以有多个。  

| 区别 | 主键索引 | 普通索引 |
| --- | --- | --- |
| 别名 | 聚簇索引 | 二级索引 |
| 数量 | 一个 | 多个 |
| 叶子节点 | 完整数据行 | 主键值 |
| 查询 | 直接返回数据 | 可能需要回表 |
| 排序依据 | 主键 | 索引字段 |
| 存储目的 | 存储数据 | 提高查询效率 |






## 什么是回表？如何减少回表？  
回表是指 **InnoDB 使用普通索引查询数据时，先通过普通索引找到对应的主键值，然后再根据主键值到聚簇索引中查询完整数据的过程**。因为 InnoDB 的普通索引叶子节点只保存索引字段和主键值，不保存完整数据，所以需要额外查询一次主键索引，这个过程就是回表。减少回表主要通过**覆盖索引、合理设计联合索引、避免查询过多无用字段**来实现。  





## MySQL 为什么使用 B+Tree 作为索引结构？
MySQL InnoDB 使用 B+Tree 作为索引结构，主要原因有三点：第一，B+Tree 是多路平衡树，一个节点可以存储大量索引数据，降低树的高度，减少磁盘 IO；第二，所有数据都存储在叶子节点，并且叶子节点通过链表连接，非常适合范围查询和排序；第三，B+Tree 查询路径稳定，每次查询都需要访问叶子节点，性能比较稳定。因此 B+Tree 非常适合作为数据库索引结构。  





## 为什么 B+Tree 比 B Tree 更适合数据库？
B+Tree 比 B Tree 更适合作为数据库索引结构，主要原因有三点：**磁盘 IO 次数更少、查询效率更加稳定、范围查询效率更高**。

首先，B+Tree 的非叶子节点只存储索引，不存储实际数据，因此同样大小的磁盘页可以存放更多索引键值，使得树的高度更低。数据库查询时需要访问的节点更少，可以减少磁盘 IO 次数。

其次，B+Tree 的所有数据都存储在叶子节点，并且叶子节点通过链表连接，所以无论查询单条数据还是范围查询，效率都比较稳定。而 B Tree 的数据分布在所有节点中，查询时可能在非叶子节点提前结束，也可能需要继续查找，性能不够稳定。

最后，B+Tree 的叶子节点形成有序链表，非常适合数据库中的范围查询，例如 `where id > 100 and id < 200`、`order by`、分页查询等，而 B Tree 需要进行中序遍历，效率相对较低。

因此，MySQL InnoDB 使用 B+Tree 作为索引结构，是因为它更适合磁盘存储场景，能够减少 IO，提高查询效率。





## 为什么不用 Hash 索引？  
MySQL 不使用 Hash 索引作为默认索引，是因为 Hash 索引虽然在等值查询场景下性能很好，但是不支持范围查询、排序以及联合索引的最左匹配。而数据库中范围查询、排序、分页等操作非常常见，因此 InnoDB 选择 B+Tree 作为默认索引结构。不过在某些特定场景下，例如 Memory 存储引擎，会使用 Hash 索引提高等值查询效率。  





## 联合索引为什么遵循最左匹配原则？  
联合索引遵循最左匹配原则，是因为 **MySQL 的联合索引底层使用 B+Tree 结构，索引中的字段是按照创建顺序进行排序的**。比如建立联合索引 `(a,b,c)`，B+Tree 会先按照 `a` 排序，当 `a` 相同时再按照 `b` 排序，当 `a、b` 都相同时再按照 `c` 排序。因此查询时必须先确定前面的字段，才能利用后面的字段进行快速定位。如果跳过最左边的字段，索引树的有序性就无法保证，MySQL 就无法高效使用该索引。  





## 索引失效有哪些情况？  
MySQL 索引失效主要是指 **查询条件虽然涉及索引字段，但是由于 SQL 写法或数据特点导致优化器无法有效利用索引**。常见情况包括：对索引字段进行函数计算、隐式类型转换、使用左模糊查询、违反联合索引最左匹配原则、使用 `OR` 条件、范围查询后无法使用后续字段、以及索引列区分度太低等。  





## 为什么数据库索引不是越多越好？
数据库索引不是越多越好，因为索引虽然可以提高查询效率，但是也会带来额外的存储和维护成本。

首先，索引本身需要占用磁盘空间。在 InnoDB 中，每个索引都是一棵 B+Tree，数据量越大，索引占用的空间也越多。

其次，索引会影响数据写入性能。当执行 `INSERT`、`UPDATE`、`DELETE` 操作时，不仅需要修改表中的数据，还需要同步维护对应的索引结构。如果一个表存在多个索引，那么一次数据变更可能需要更新多棵 B+Tree，从而增加 CPU 消耗和磁盘 IO，降低写入效率。

另外，索引过多还会增加 MySQL 优化器选择执行计划的成本。优化器需要在多个索引中选择合适的索引，如果索引数量过多，可能增加分析时间，甚至可能选择不合适的执行方案。

因此，在实际开发中，索引设计需要结合业务场景，针对高频查询条件、排序字段、关联字段建立合适的索引，而不是为了提高查询速度无限制地添加索引。





## 主键为什么推荐使用自增 ID？
MySQL InnoDB 中主键推荐使用自增 ID，主要原因是**可以减少页分裂，提高索引插入效率，同时降低索引空间占用**。

首先，InnoDB 的主键索引是聚簇索引，数据按照主键顺序存储。当使用自增 ID 时，新插入的数据通常会追加到 B+Tree 的最右侧叶子节点，只需要顺序插入即可，不需要频繁移动已有数据，因此可以减少页分裂，提高写入性能。

其次，自增 ID 通常是整数类型，占用空间较小。由于 InnoDB 的普通索引叶子节点存储的是索引字段和主键值，如果主键较大，那么每个普通索引都会额外存储更大的主键值，导致索引占用空间增加。

另外，自增 ID 具有递增特点，能够提高索引数据的局部性，减少随机 IO。

不过，自增 ID 也不是绝对适合所有场景，例如分布式系统中可能需要使用雪花算法等分布式 ID 方案来保证全局唯一性。





## 一条 SQL 语句执行流程是什么？  
一条 SQL 语句在 MySQL 中的执行流程主要经过 **连接器、查询缓存（MySQL 8.0 已移除）、分析器、优化器、执行器、存储引擎** 这几个阶段。首先客户端通过连接器建立连接并进行权限验证；然后分析器对 SQL 进行词法分析和语法分析，判断 SQL 是否正确；接着优化器根据索引、表结构、数据分布等信息生成最优执行计划；最后执行器调用存储引擎提供的接口执行 SQL，存储引擎负责真正的数据读写，并将结果返回给客户端。

## 一条 UPDATE SQL 执行流程是什么？  
一条 UPDATE SQL 的执行流程主要包括 **连接器建立连接、查询缓存判断（MySQL 8 已移除）、解析 SQL、优化执行计划、执行更新、记录 redo log 和 binlog、提交事务**。其中 UPDATE 和 SELECT 最大的区别是，UPDATE 不仅需要读取数据，还需要修改数据，因此会涉及 **undo log、redo log、binlog、锁机制以及两阶段提交**。执行时，InnoDB 会先根据索引找到目标数据并加锁，然后修改 Buffer Pool 中的数据页，同时记录 undo log 和 redo log，事务提交时写入 binlog，并通过两阶段提交保证 redo log 和 binlog 一致。

## InnoDB 的事务隔离级别有哪些？默认是什么？  
InnoDB 支持 **4 种事务隔离级别**，分别是 **读未提交（Read Uncommitted）、读已提交（Read Committed）、可重复读（Repeatable Read）、串行化（Serializable）**。它们主要用于解决事务并发执行时产生的 **脏读、不可重复读、幻读** 等问题。

其中 InnoDB 默认的事务隔离级别是 **可重复读（Repeatable Read，RR）**。InnoDB 通过 **MVCC（多版本并发控制）和 Next-Key Lock（临键锁）** 来保证可重复读，并且在很大程度上解决了幻读问题。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 并发性能 |
| --- | --- | --- | --- | --- |
| **Read Uncommitted（读未提交）** | ❌存在 | ❌存在 | ❌存在 |  最高 |
| **Read Committed（读已提交）** | ✅解决 | ❌存在 | ❌存在 |  较高 |
| **Repeatable Read（可重复读，InnoDB默认）** | ✅解决 | ✅解决 | ✅解决（InnoDB） | 中等 |
| **Serializable（串行化）** | ✅解决 | ✅解决 | ✅解决 | 最低 |


**读未提交：** 一个事务可以读取另一个事务未提交的数据。  

**读已提交：** 只能读取已经提交的数据。  

**可重复读：** 一个事务开始后，多次读取同一数据结果一致。  （ MySQL InnoDB 默认级别）

**串行化：** 所有事务按照顺序执行。  





## MySQL 如何解决脏读、不可重复读、幻读？  
MySQL 主要通过 **事务隔离级别、锁机制和 MVCC 多版本并发控制** 来解决脏读、不可重复读和幻读问题。  

+ **脏读**：一个事务读取到了另一个事务未提交的数据。MySQL 通过提高隔离级别，至少使用 **读已提交（RC）**，保证只能读取已经提交的数据，从而解决脏读。
+ **不可重复读**：同一个事务中，两次读取同一条数据结果不同。MySQL 的 **可重复读隔离级别通过 MVCC 创建一致性快照**，保证事务期间读取的是同一个版本的数据，从而解决不可重复读。 
+ **幻读**：同一个事务中，两次查询同一个范围，第二次查询出现了新增或减少的记录。InnoDB 在 RR 级别下通过 **MVCC + Next-Key Lock** 解决幻读，MVCC 保证普通查询的一致性，Next-Key Lock 锁住记录和记录之间的间隙，防止其他事务插入新的数据。







## MVCC 是什么？实现原理是什么？  
MVCC（Multi-Version Concurrency Control，多版本并发控制）是一种**数据库提高并发性能的机制**，它通过保存数据的多个历史版本，让读操作不需要加锁就可以读取一致性数据，从而减少读写之间的阻塞。

在 MySQL InnoDB 中，MVCC 主要通过 **隐藏字段、undo log 和 Read View** 三部分实现。

当事务修改数据时，InnoDB 不会直接删除旧版本，而是将旧数据保存到 undo log 中，并通过隐藏字段记录事务信息。查询数据时，事务会创建一个 Read View，根据可见性规则判断哪个版本的数据对当前事务可见。如果当前版本不可见，就沿着 undo log 的版本链继续查找，直到找到可见版本。

因此，MVCC 解决了多个事务并发读取时的数据一致性问题，例如在 RR（可重复读）隔离级别下解决不可重复读，同时提高数据库并发能力。

## MVCC 为什么能提高并发？  
MVCC 能提高并发的核心原因是：**读操作不需要加锁，通过读取数据的历史版本实现一致性读，从而减少读写之间的阻塞。**

传统数据库中，如果一个事务正在修改数据，其他事务读取同一条数据可能需要等待写锁释放，导致读写互相阻塞。而 MySQL InnoDB 使用 MVCC 后，写事务修改数据时不会覆盖旧版本，而是通过 undo log 保存历史版本；读事务查询数据时，根据 Read View 判断应该读取哪个版本。



**MVCC 和锁的区别：**

|  | 传统锁机制 | MVCC |
| --- | --- | --- |
| **读取方式** | 加锁读取 | 读取版本 |
| **读写关系** | 互相阻塞 | 读写并行 |
| **性能** | 较低 | 较高 |
| **适合场景** | 强一致修改 | 高并发读取 |






## MySQL 为什么使用 WAL（Write Ahead Logging）？
**MySQL 使用 WAL（Write Ahead Logging，预写日志）主要是为了提高数据库写入性能，同时保证事务的持久性和崩溃恢复能力。它的核心思想是：先写日志，再修改数据。**

在传统方式中，如果每次更新数据都直接修改磁盘上的数据页，由于磁盘随机 IO 性能较差，写入效率会非常低。而 WAL 机制会先把修改操作记录到 redo log 中，因为 redo log 是顺序写入，速度远高于随机修改数据页。事务提交时，只需要保证 redo log 持久化即可，不需要立即把数据页刷入磁盘。

当 MySQL 发生宕机时，可以通过 redo log 重新执行已经提交但还没有写入磁盘的数据，从而保证事务不会丢失；如果事务没有提交，则通过 undo log 进行回滚。

所以，WAL 机制通过**将随机 IO 转换为顺序 IO，提高写入性能，同时利用日志实现故障恢复，保证事务的持久性**。





## MySQL 锁有哪些类型？
MySQL 的锁主要用于解决事务并发访问数据时的数据一致性问题。按照不同维度可以分为**全局锁、表级锁、行级锁，以及共享锁、排他锁、意向锁等**。对于 InnoDB 存储引擎来说，最重要的是行级锁，包括记录锁、间隙锁和临键锁。

从**锁粒度**来看，全局锁会锁住整个数据库，表锁会锁住整张表，而行锁只锁住满足条件的数据行，因此 InnoDB 使用行锁可以提高并发性能。

从**锁类型**来看，共享锁 （S锁）  允许多个事务同时读取同一条数据，但是不能修改；排他锁 （X锁）  只允许一个事务持有，用于修改数据。另外 InnoDB 通过意向锁表示事务准备对某些行加锁，提高表锁和行锁冲突判断效率。

在 InnoDB 默认 RR 隔离级别下，还存在记录锁、间隙锁和临键锁。其中记录锁锁住具体记录，间隙锁锁住索引记录之间的范围，临键锁是记录锁和间隙锁的组合，主要用于解决幻读问题。

| 锁类型 | 作用 |
| --- | --- |
| **全局锁** | 锁整个数据库 |
| **表锁** | 锁整张表 |
| **行锁** | 锁具体记录 |
| **共享锁(S)** | 多人读，禁止修改 |
| **排他锁(X)** | 独占修改 |
| **意向锁** | 表示即将加行锁 |
| **记录锁** | 锁某条记录 |
| **间隙锁** | 锁记录之间范围 |
| **临键锁** | 记录锁+间隙锁 |






## 行锁、表锁、间隙锁有什么区别？
MySQL 中行锁、表锁和间隙锁的主要区别在于锁定范围不同。

**表锁**锁住整张表，锁粒度最大，并发性能最低；**行锁**只锁住满足条件的数据行，锁粒度最小，并发性能最高，是 InnoDB 最常用的锁；**间隙锁**锁住索引记录之间的范围，用来阻止其他事务在范围内插入数据，主要用于解决幻读问题。

在 InnoDB 中，行锁依赖索引实现。如果 SQL 使用索引查询，可以锁住具体记录；如果没有使用索引，可能会锁住大量记录，导致锁范围扩大。而间隙锁通常出现在 RR（可重复读）隔离级别下，它不会锁住已有记录，而是锁住记录之间的空隙，防止其他事务插入新的数据。  

| 类型 | 锁住范围 | 并发能力 | 作用 |
| --- | --- | --- | --- |
| **表锁** | 整张表 | 低 | 控制整表访问 |
| **行锁** | 具体记录 | 高 | 控制单条数据修改 |
| **间隙锁** | 记录之间的范围 | 中 | 防止范围插入 |






## 什么情况下会发生死锁？如何解决？
MySQL 死锁是指两个或多个事务互相持有对方需要的锁，导致事务之间相互等待，形成循环依赖，最终无法继续执行的情况。

常见产生原因是多个事务以不同顺序访问相同资源。例如，事务 A 先锁住数据 1，再请求数据 2；事务 B 先锁住数据 2，再请求数据 1，此时两个事务都会等待对方释放锁，从而产生死锁。

MySQL InnoDB 会自动检测死锁，并选择回滚其中一个事务，让另一个事务继续执行。解决死锁主要可以从减少死锁发生和处理死锁两个方面入手，例如保证事务访问资源顺序一致、缩短事务执行时间、合理设计索引减少锁范围，以及捕获死锁异常后进行重试。



**常见死锁场景：** ① 加锁顺序不一致、② 事务持有锁时间过长、③ 大量范围锁导致死锁、④ 更新没有命中索引   





## MySQL 如何检测死锁？
MySQL 主要通过 InnoDB 的**死锁检测机制**来发现死锁。它会维护事务之间的锁等待关系，并构建等待图（Wait-for Graph）。当检测到等待图中出现环路时，说明发生了死锁，此时 InnoDB 会选择其中一个事务作为牺牲者进行回滚，释放它持有的锁，让其他事务继续执行。

在选择回滚事务时，InnoDB 通常会选择回滚代价较小的事务，例如修改数据较少、undo log 较少的事务。回滚完成后，被回滚的事务会收到死锁错误，应用程序需要捕获异常并进行重试。

![](https://cdn.nlark.com/yuque/__mermaid_v3/b1ccc769bb6e409932a0c07cc32270a1.svg)





## 为什么 InnoDB 选择回滚某一个事务，而不是全部回滚？  
InnoDB 在发生死锁时选择回滚其中一个事务，而不是全部回滚，是为了尽可能减少事务失败带来的影响，提高系统并发性能。因为死锁只需要打破循环等待关系即可解除，并不需要所有事务都回滚。

InnoDB 会根据事务回滚成本选择一个“牺牲者”，通常会优先回滚修改数据较少、undo log 较小的事务，因为这样恢复成本最低。被回滚的事务会释放持有的锁，让其他事务继续执行，而没有被回滚的事务可以继续完成提交。





## 如何避免死锁？  
MySQL 避免死锁主要从**减少锁竞争**和**规范事务执行顺序**两个方面入手。常见方法包括：**按照固定顺序访问数据、缩小事务范围、减少事务持有锁的时间、合理设计索引、避免大事务，以及在应用层对死锁进行重试。**

其中最重要的是保证多个事务获取锁的顺序一致。例如两个事务都需要修改用户表中的 id=1 和 id=2 数据，那么都应该按照 id 从小到大的顺序加锁，避免一个事务先锁 id=1，另一个事务先锁 id=2，最终形成循环等待。

| 方法 | 作用 |
| --- | --- |
| 固定顺序访问数据 | 避免循环等待 |
| 缩小事务范围 | 减少锁持有时间 |
| 减少大事务 | 减少锁数量 |
| 增加合理索引 | 减少扫描和锁范围 |
| 降低隔离级别 | 减少间隙锁 |
| 减少锁粒度 | 提高并发 |
| 应用层重试 | 保证最终成功 |






## MySQL 死锁一定是两个事务吗？
MySQL 死锁不一定只发生在两个事务之间，也可能由多个事务形成循环等待。死锁的本质不是事务数量，而是多个事务之间形成了**循环等待关系**。

例如，两个事务可以形成 A 等待 B、B 等待 A 的循环；三个事务也可以形成 A 等待 B、B 等待 C、C 等待 A 的循环。只要存在循环依赖，InnoDB 的死锁检测机制就会判定为死锁，并选择回滚其中一个事务来解除死锁。







## MySQL 如何进行 SQL 优化？  
MySQL SQL 优化主要从 SQL 本身、索引设计、表结构设计以及数据库配置几个方面进行优化。

首先，在 SQL 层面，需要避免使用 `select *`，只查询业务需要的字段，减少网络传输和数据读取。同时要减少不必要的数据扫描，例如合理使用 `where` 条件，避免对索引字段进行函数计算、隐式类型转换等导致索引失效的操作。

其次，在索引方面，需要根据业务查询场景建立合适的索引，例如联合索引要遵循最左匹配原则。同时要避免建立过多索引，因为索引虽然可以提升查询效率，但是会增加插入、更新、删除操作的维护成本。

然后，可以通过 `EXPLAIN` 分析 SQL 执行计划，重点关注是否使用索引、扫描行数以及是否出现全表扫描、临时表、文件排序等情况，根据执行结果进行优化。

最后，对于数据量较大的场景，可以通过分库分表、读写分离、冷热数据分离等架构方式提升数据库性能，同时结合数据库参数调优进一步提高整体性能。





## explain 执行计划怎么看？
`EXPLAIN` 是 MySQL 提供的 SQL 执行计划分析工具，通过它可以查看 MySQL 执行一条 SQL 时选择了什么索引、访问方式、扫描多少数据以及是否进行了额外操作，从而帮助我们定位 SQL 性能问题。

在分析 `EXPLAIN` 时，主要关注几个关键字段：首先看 **type**，它表示 MySQL 的访问类型，通常从好到差依次是 `system、const、eq_ref、ref、range、index、ALL`，其中 `ALL` 表示全表扫描，需要重点优化。其次看 **key**，表示实际使用的索引，如果为空说明没有使用索引。然后看 **rows**，表示 MySQL 预计需要扫描的数据行数，这个值越小越好。还需要关注 **Extra** 字段，例如出现 `Using filesort` 表示需要额外排序，`Using temporary` 表示使用临时表，这些通常需要优化。

实际优化 SQL 时，一般先通过 `EXPLAIN` 判断 SQL 是否走索引，再结合 `type`、`key`、`rows`、`Extra` 等字段分析问题，例如是否存在全表扫描、索引失效、排序或临时表等情况，然后针对性优化索引或者 SQL。

## count(*)、count(1)、count(id)有什么区别？
`count(*)`、`count(1)` 和 `count(id)` 都可以用于统计行数，但它们统计的范围和执行逻辑有所不同。

`count(*)` 统计的是**符合条件的总行数**，不会忽略 `NULL`，是 MySQL 推荐的统计方式。

`count(1)` 本质上和 `count(*)` 类似，也是统计符合条件的行数，因为 `1` 是一个永远不为 NULL 的常量。

`count(id)` 统计的是 **id 字段不为 NULL 的行数**，如果 id 存在 NULL 值，则不会统计该行。

在 InnoDB 中，`count(*)` 通常是性能最好的方式，因为 MySQL 会对它进行特殊优化，而 `count(字段)` 需要判断字段是否为 NULL。

| 方式 | 统计对象 | NULL处理 |
| --- | --- | --- |
| count(*) | 行数 | 包含 NULL |
| count(1) | 行数 | 包含 NULL |
| count(id) | 字段值数量 | 忽略 NULL |






## delete、truncate、drop有什么区别？
`DELETE`、`TRUNCATE`、`DROP` 都可以删除数据，但它们的删除范围、实现方式和是否保留表结构不同。

`DELETE` 是**删除表中的数据**，属于 DML 操作，可以通过 `WHERE` 条件删除部分数据，也可以删除全部数据；删除后表结构仍然存在，并且支持事务回滚。

`TRUNCATE` 是**清空整张表的数据**，属于 DDL 操作，不能指定 `WHERE` 条件，会直接释放数据页，执行速度比 `DELETE` 快；删除后表结构仍然存在，但通常不能回滚。

`DROP` 是**删除整个表**，包括数据、表结构、索引、约束等，执行后表不存在。

| 对比 | DELETE | TRUNCATE | DROP |
| --- | --- | --- | --- |
| **作用** | 删除数据 | 清空数据 | 删除整个表 |
| **删除范围** | 部分或全部 | 全部 | 全部 |
| **是否保留表结构** | ✅ 保留 | ✅ 保留 | ❌ 删除 |
| **是否支持 WHERE** | ✅ 支持 | ❌ 不支持 | ❌ 不支持 |
| **类型** | DML | DDL | DDL |
| **速度** | 慢 | 快 | 最快 |
| **是否记录日志** | 逐行记录 | 记录较少 | 记录较少 |
| **是否触发 DELETE 触发器** | ✅ 会 | ❌ 不会 | ❌ 不会 |
| **是否可回滚** | ✅ 可以（事务内） | 通常不可以 | 通常不可以 |






## 分库分表有哪些方案？  
分库分表是指**当单表数据量过大或者单库并发压力过高时，将数据按照一定规则拆分到多个数据库或者多个表中，从而降低单个数据库的压力，提高系统的存储能力和并发能力**。

分库分表主要分为两类：**垂直拆分和水平拆分**。

垂直拆分主要是按照业务维度进行拆分，包括**垂直分库和垂直分表**。例如将用户、订单、商品拆分到不同数据库中，将一张包含大量字段的用户表拆成用户基本信息表和用户详细信息表。垂直拆分可以降低业务之间的耦合，但是不能解决单张表数据量过大的问题。

水平拆分主要是按照数据规则进行拆分，包括**水平分库和水平分表**。例如按照用户 ID 取模，将不同用户的数据分散到多个数据库或者多个表中。水平拆分能够解决海量数据存储问题，但会带来分布式事务、跨库查询、分页排序等问题。

**常见分片算法：**

| 方案 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **范围分片** | ID范围 | 扩容简单 | 热点 |
| **哈希分片** | hash取模 | 数据均匀 | 扩容困难 |
| **时间分片** | 按日期 | 适合流水数据 | 查询跨度大 |
| **一致性哈希** | 哈希环 | 扩容影响小 | 实现复杂 |




## 分库分表后如何保证事务？
分库分表后，由于数据被拆分到了多个数据库节点，原本 MySQL 单机事务中的 ACID 特性无法直接保证，例如一个订单创建操作可能涉及订单库、库存库、账户库，多个数据库之间无法使用普通的本地事务，因此需要引入**分布式事务方案**。

常见解决方案主要有三种：

第一种是**两阶段提交（2PC）**。通过协调者统一管理多个参与者事务，第一阶段各数据库执行事务并锁定资源，返回准备成功；第二阶段协调者通知所有数据库提交或者回滚。它能够保证强一致性，但是存在性能差、阻塞时间长、单点问题等缺点。

第二种是**TCC（Try-Confirm-Cancel）模式**。将业务拆分为三个阶段：Try 阶段预留资源，Confirm 阶段真正提交，Cancel 阶段释放资源。例如扣库存时先冻结库存，确认成功后真正扣减。TCC 一致性较强，但是业务侵入较大，需要开发补偿逻辑。

第三种是**最终一致性方案**，例如基于消息队列实现。业务操作完成后发送可靠消息，其他服务消费消息完成后续操作。如果失败，通过重试机制保证最终达到一致状态。这种方式性能较高，但是只能保证最终一致性。





## 分库分表后如何分页查询？  
第一种是**分片查询后进行结果归并**。由于数据被分散到多个数据库或表中，无法直接通过 `limit offset` 获取结果，所以需要让每个分片执行查询，然后由中间件将多个分片的数据进行排序、合并，最后截取需要的数据。这种方式实现简单，但是对于深分页性能较差。

第二种是**游标分页，也是生产环境更推荐的方案**。它不再使用 `limit offset`，而是基于上一页最后一条数据的唯一标识进行查询， 例如根据 ID 或时间字段：  

```sql
select *
from order
where id < 上一次查询最后的id
order by id desc
limit 10;
```

 第三种是**借助搜索引擎或中间件实现分页**。对于复杂查询场景，可以将数据同步到 Elasticsearch，由 ES 负责查询和分页。  

| 方案 | 适用场景 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **分片归并分页** | 普通分页 | 简单 | 深分页慢 |
| **游标分页** | 大数据量列表 | 性能稳定 | 无法跳页 |
| **时间分页** | 订单日志 | 查询效率高 | 依赖时间字段 |
| **ES分页** | 复杂搜索 | 能力强 | 维护成本高 |






## 数据库如何处理高并发？
数据库处理高并发主要从**提高数据库处理能力、减少数据库压力、优化 SQL 和架构扩展**几个方面入手。

首先，在数据库层面，可以通过**索引优化、SQL 优化、合理设计表结构**提高单次请求的执行效率。例如使用合适的索引减少全表扫描，避免慢 SQL 占用数据库资源。

其次，通过**缓存降低数据库访问压力**。对于热点数据，可以使用 Redis 等缓存系统，将大量读请求直接从缓存返回，减少数据库查询次数。

第三，通过**读写分离和主从复制**提高数据库的读能力。主库负责写操作，从库负责读操作，将大量查询请求分散到多个从库，提高整体吞吐量。

第四，当单库无法承载数据量和并发压力时，可以采用**分库分表**，将数据拆分到多个数据库和表中，让多个数据库节点共同承担压力。

第五，通过**连接池管理数据库连接**，避免大量请求频繁创建和销毁连接，同时限制最大连接数，防止数据库被连接打垮。

第六，对于高并发写场景，可以通过**异步化和消息队列削峰**，例如用户下单后先发送消息，由后台服务异步处理数据库写入，避免瞬间大量请求直接访问数据库。

最后，还需要通过事务优化、锁优化、批量操作等方式减少数据库竞争，提高并发处理能力。





## 大表如何优化？
大表优化主要是针对**数据量非常大的表导致查询慢、写入慢、索引占用空间大等问题进行优化**。常见优化方式主要包括**SQL 优化、索引优化、表结构优化、数据拆分和架构优化**。

首先，可以进行 **SQL 和索引优化**。例如为高频查询字段建立合适索引，避免全表扫描；避免 `select *`，减少无效字段查询；优化慢 SQL，提高查询效率。

其次，可以进行 **表结构优化**。例如采用冷热数据分离，将经常访问的热数据和很少访问的冷数据拆分；对于大字段（如文本、图片地址等）可以单独拆表，减少主表数据量。

第三，可以进行 **分区表优化**。根据时间、范围等规则将数据划分到不同分区，例如订单表按照月份分区，使查询时只扫描相关分区，提高查询效率。

第四，当单表数据量继续增长时，可以采用 **分库分表**。例如按照用户 ID 哈希分片，将数据拆分到多个数据库和表中，降低单表数据量和数据库压力。

第五，可以使用 **归档策略**，将历史数据迁移到归档库或者数据仓库，减少在线业务表的数据量。

第六，可以引入 **缓存和搜索引擎**。对于热点查询使用 Redis 缓存，对于复杂查询和全文检索使用 Elasticsearch，减少 MySQL 压力。
