## OSI 七层模型有哪些？每层作用是什么？
OSI 七层模型是国际标准化组织提出的网络通信模型，将网络通信过程划分为七层，从下到上分别是：**物理层、数据链路层、网络层、传输层、会话层、表示层、应用层**。

每一层负责不同的功能：

+ **物理层**：负责比特流的传输，规定网络设备之间如何通过物理介质传输 0 和 1，比如网线、光纤、电信号。 
+ **数据链路层**：负责节点之间可靠的数据传输，通过 MAC 地址进行寻址，并负责帧封装、差错检测，例如交换机工作在这一层。 
+ **网络层**：负责数据包在不同网络之间进行路由转发，通过 IP 地址进行寻址，例如路由器工作在这一层。 
+ **传输层**：负责端到端的数据传输，提供可靠或不可靠的数据传输服务，主要协议有 TCP 和 UDP。 
+ **会话层**：负责建立、管理和终止通信会话，比如控制两个应用程序之间的连接。 
+ **表示层**：负责数据格式转换、加密、压缩，例如编码转换、HTTPS 加密。 
+ **应用层**：直接面向用户提供网络服务，例如 HTTP、FTP、DNS 等协议。

| 名称 | 作用 | 常见协议/设备 |
| --- | --- | --- |
| 应用层 | 为用户提供网络服务 | HTTP、FTP、DNS、SMTP |
| 表示层 | 数据格式转换、加密、压缩 | SSL/TLS、JPEG、JSON |
| 会话层 | 建立、维护、结束会话 | RPC、NetBIOS |
| 传输层 | 端到端可靠传输 | TCP、UDP |
| 网络层 | 负责路由和 IP 寻址 | IP、ICMP、路由器 |
| 数据链路层 | 负责 MAC 寻址、帧传输 | MAC、ARP、交换机 |
| 物理层 | 传输比特流 | 网线、光纤、集线器 |

## TCP/IP 四层模型有哪些？  
TCP/IP 四层模型是互联网实际使用的网络模型，它将网络通信过程划分为四层，从上到下分别是：**应用层、传输层、网际层、网络接口层**。

每一层负责不同的功能：

+ **应用层**：负责向用户提供网络服务，处理具体的应用通信，比如 HTTP、DNS、FTP 等协议。 
+ **传输层**：负责端到端的数据传输，保证数据能够从一个应用程序传输到另一个应用程序，主要协议有 TCP 和 UDP。 
+ **网际层**：负责数据包在不同网络之间进行路由转发，通过 IP 地址定位目标主机，核心协议是 IP。 
+ **网络接口层**：负责数据在物理网络中的传输，包括数据链路层和物理层的功能，例如 MAC 地址、网卡、网线等。

| --- | --- | --- |
| **应用层** | 提供应用服务，处理用户数据 | HTTP、HTTPS、DNS、FTP、SMTP |
| **传输层** | 负责端到端通信 | TCP、UDP |
| **网际层** | 负责 IP 寻址和路由选择 | IP、ICMP、ARP、路由器 |
| **网络接口层** | 负责数据在物理网络上传输 | Ethernet、WiFi、MAC、交换机 |

## OSI 七层模型和 TCP/IP 模型有什么区别？  
OSI 七层模型和 TCP/IP 模型都是用于描述网络通信过程的分层模型，主要区别有三个方面：**层数不同、分层方式不同、实际应用不同**。

首先，**层数不同**。OSI 模型将网络通信划分为七层，从下到上分别是：物理层、数据链路层、网络层、传输层、会话层、表示层和应用层。而 TCP/IP 模型将网络划分为四层，分别是：网络接口层、网际层、传输层和应用层。

其次，**分层方式不同**。OSI 模型更加细致，将会话、数据格式转换、加密解密等功能分别划分到了会话层和表示层；而 TCP/IP 模型为了更加贴近实际应用，将会话层和表示层的功能合并到了应用层。

最后，**实际应用不同**。OSI 更多是一个理论参考模型，用于帮助我们理解网络通信过程；TCP/IP 是互联网实际使用的协议体系，例如 HTTP、TCP、IP 等协议都是基于 TCP/IP 模型实现的。

| --- | --- | --- |
| 应用层 | <br/>应用层<br/> | 为用户提供网络服务，例如 HTTP、FTP、DNS |
| 表示层 | | 数据格式转换、加密、压缩 |
| 会话层 | | 建立、管理、终止会话 |
| 传输层 | 传输层 | 负责端到端通信，例如 TCP、UDP |
| 网络层 | 网际层 | 负责 IP 寻址和路由转发，例如 IP 协议 |
| 数据链路层 | 网络接口层<br/> | 负责帧传输、MAC 地址寻址 |
| 物理层 | | 负责比特流在物理介质上传输 |






## 为什么要进行网络分层？分层有什么好处？  
网络分层的主要目的是**降低网络通信的复杂度，让不同设备、不同协议之间能够协同工作**。因为网络通信涉及很多复杂功能，例如数据传输、寻址、路由、可靠性保证、数据格式转换等，如果所有功能都集中在一起实现，会导致系统难以设计和维护。因此，网络采用分层设计，将复杂的网络通信过程拆分成多个独立的层，每一层只负责自己的功能，并通过标准接口与上下层进行通信。



网络分层主要有以下几个好处：

第一，**降低复杂度，便于设计和维护**。每一层只关注自己的任务，例如传输层负责可靠传输，网络层负责路由寻址，应用层负责业务数据处理，开发人员不需要关心其他层的具体实现。

第二，**提高灵活性和可扩展性**。不同层之间通过标准接口通信，某一层发生变化不会影响其他层。例如从有线网络切换到 WiFi，只需要替换底层网络接口层，上层的 HTTP、TCP 等协议无需改变。

第三，**方便协议开发和替换**。每一层可以独立设计协议，例如传输层既可以使用 TCP，也可以使用 UDP，而应用层协议 HTTP、FTP、DNS 等都可以基于 TCP/IP 进行通信。

第四，**促进不同厂商设备之间互联**。通过统一的网络分层标准，不同厂商生产的硬件和软件可以按照相同规则进行通信，例如电脑、手机、服务器之间都可以通过 TCP/IP 网络互相连接。





## 分层后数据如何封装和拆封？  
网络分层后，数据在发送端会按照**从上到下逐层封装**的过程进行传输，在接收端则按照**从下到上逐层拆封**的过程还原数据。

发送数据时，应用层首先产生业务数据，然后每经过一层，该层都会在数据前面添加自己的控制信息，这个过程叫做**封装**。例如传输层添加 TCP 头部，形成 TCP 报文段；网络层添加 IP 头部，形成 IP 数据包；数据链路层添加 MAC 头部和尾部，形成数据帧；最后物理层将数据帧转换成比特流发送到网络中。

接收端收到数据后，会按照相反的顺序进行拆封。物理层接收比特流后交给数据链路层，数据链路层去掉帧头和帧尾；网络层去掉 IP 头；传输层去掉 TCP 头；最后应用层得到真正的业务数据。



数据在各层之间的名称：

| 层 | 数据单位 |
| --- | --- |
| 应用层 | 数据（Data） |
| 传输层 | 报文段（Segment） |
| 网络层 | 数据报/数据包（Packet） |
| 数据链路层 | 帧（Frame） |
| 物理层 | 比特（Bit） |

## HTTP、TCP、IP、Socket之间是什么关系？
HTTP、TCP、IP 和 Socket 是网络通信中不同层次的概念，它们之间是协同工作的关系。

**HTTP** 属于应用层协议，负责定义客户端和服务器之间传输的数据格式和通信规则；**TCP** 属于传输层协议，负责保证数据可靠传输，包括连接建立、数据确认、重传以及保证数据顺序；**IP** 属于网络层协议，负责根据 IP 地址进行寻址和路由，将数据发送到目标主机；**Socket **不是协议，而是操作系统提供给应用程序使用 TCP/IP 协议进行网络通信的接口。实际开发中，应用程序通过 Socket 建立 TCP 连接，然后使用 HTTP 协议组织数据，最终由 TCP/IP 协议栈完成数据传输。  

| 名称 | 所属层 | 作用 |
| --- | --- | --- |
| **HTTP** | 应用层 | 定义数据格式和通信规则 |
| **TCP** | 传输层 | 可靠传输 |
| **IP** | 网络层 | 寻址和路由 |
| **Socket** | 应用接口 | 提供网络编程能力 |






## Socket通信流程是什么？
Socket 通信流程分为**服务端流程和客户端流程**。服务端首先创建 Socket，绑定 IP 和端口，然后监听客户端连接，通过 accept 接收连接；客户端创建 Socket 后，通过 connect 发起连接，TCP 三次握手成功后，双方通过 send/recv 进行数据传输。通信结束后，双方关闭 Socket 释放资源。简单来说，就是**服务端监听，客户端连接，建立通信，数据交互，关闭连接**。

## 为什么服务器 accept 后还要生成新的 Socket？
服务器调用 `accept()` 后生成新的 Socket，是因为**监听 Socket 和通信 Socket 的职责不同**。服务器启动时创建的 Socket 只负责监听客户端连接，当客户端完成 TCP 三次握手后，`accept()` 会返回一个新的 Socket，用于和这个具体客户端进行数据通信。这样服务器可以继续使用原来的监听 Socket 接收其他客户端连接，同时通过新生成的 Socket 与已经连接的客户端进行读写，实现同时处理多个客户端。  





## BIO、NIO、AIO区别？
BIO、NIO、AIO 都是 Java 中进行网络编程时的 I/O 模型，主要区别在于**数据读取方式和线程处理方式不同**。

**BIO**（Blocking I/O）是同步阻塞模型，一个连接通常对应一个线程，简单但并发能力有限；**NIO**（Non-blocking I/O）是同步非阻塞模型，通过 Selector 一个线程可以管理多个连接，提高并发能力；**AIO**（Asynchronous I/O）是异步非阻塞模型，由操作系统完成 I/O 操作后主动通知应用程序，进一步减少线程阻塞。实际高并发网络框架中，Netty 主要基于 NIO 模型。

## 为什么NIO性能更高？
NIO 性能更高的主要原因是**减少了线程数量和线程阻塞，提高了系统资源利用率**。传统 BIO 模型中，一个客户端连接通常需要一个线程处理，当连接数量增加时，会创建大量线程，导致线程上下文切换和内存消耗增加。而 NIO 通过 Selector（多路复用器）让一个线程同时管理多个 Channel，只需要监听哪些连接真正有读写事件，再分配线程处理数据，因此可以用更少的线程支撑更多连接，提高系统吞吐量。  





## **浏览器输入 URL 后发生了什么？**
浏览器输入 URL 后，首先会对 URL 进行解析，判断协议、域名和路径等信息。然后浏览器会先检查缓存，如果缓存中有可用资源，就直接使用缓存。接着浏览器会进行 DNS 域名解析，将域名转换为服务器的 IP 地址。获取 IP 后，浏览器会根据协议建立网络连接，如果是 HTTPS，需要先通过 TCP 三次握手建立连接，然后进行 TLS 握手完成加密协商；如果是 HTTP，则直接建立 TCP 连接。连接建立后，浏览器会封装 HTTP 请求报文，并通过 TCP/IP 协议发送到服务器。服务器收到请求后，经过网卡、操作系统网络栈以及应用服务器处理，返回 HTTP 响应。浏览器收到响应后，会解析 HTML，构建 DOM 树和 CSSOM 树，然后生成渲染树，计算布局并进行页面绘制，最终将页面展示出来。

## 为什么经过路由器 MAC 地址会变化，而 IP 地址不会变化？  
因为 MAC 地址属于数据链路层，只负责局域网内的数据传输，而 IP 地址属于网络层，负责跨网络通信和寻址。当数据经过路由器时，路由器会拆开原来的二层数据帧，然后根据目标 IP 地址重新封装一个新的数据帧，所以 MAC 地址会发生变化；但是 IP 数据包在整个传输过程中保持不变，因为 IP 地址用于标识通信双方的源地址和目标地址，需要保证数据能够最终到达目标主机。  





## 为什么需要端口号？没有端口会怎样？  
端口号的作用是用来标识一台主机上的具体应用程序。因为 IP 地址只能定位到一台机器，但一台机器上通常会运行多个网络应用，比如 Web 服务、数据库、SSH 服务等，如果没有端口号，数据到达主机后就无法知道应该交给哪个程序处理。通过 IP 地址和端口号的组合，可以唯一确定通信双方的应用进程，实现不同程序之间的数据传输。  





## TCP和UDP有什么区别？
TCP 和 UDP 都是传输层协议，主要区别在于**TCP 面向连接，UDP 无连接**。TCP 在通信前需要通过三次握手建立连接，通信过程中会通过确认应答、重传机制、流量控制和拥塞控制等方式保证数据可靠、有序地传输，因此适合对可靠性要求高的场景，比如 HTTP、HTTPS、文件传输等。UDP 不需要建立连接，直接发送数据报，不保证数据一定到达，也不保证顺序，但是传输效率更高、延迟更低，适合实时性要求高但允许少量丢包的场景，比如视频直播、语音通话、在线游戏等。  

| 对比项 | TCP | UDP |
| --- | --- | --- |
| **连接方式** | 面向连接，需要三次握手建立连接 | 无连接，不需要建立连接 |
| **是否可靠** | 可靠传输 | 不可靠传输 |
| **数据形式** | 字节流 | 数据报 |
| **是否保证顺序** | 保证数据按序到达 | 不保证顺序 |
| **是否重传** | 有重传机制 | 没有重传机制 |
| **流量控制** | 有滑动窗口控制发送速度 | 没有 |
| **拥塞控制** | 有拥塞控制，避免网络拥堵 | 没有 |
| **传输效率** | 较低 | 较高 |
| **延迟** | 较高 | 较低 |
| **首部大小** | 20~60 字节 | 固定 8 字节 |






## TCP如何保证可靠性？  
TCP 主要通过**序列号和确认应答、超时重传、快速重传、流量控制、拥塞控制以及连接管理机制**来保证可靠性。

首先，TCP 为每个发送的数据段分配**序列号（Sequence Number）**，接收方通过**确认号（ACK）**告诉发送方已经成功接收到的数据位置。如果数据丢失、乱序或者重复，TCP 可以根据序列号重新排序或者重新发送。

其次，TCP 通过**超时重传机制**保证数据一定能够到达。如果发送方发送数据后，在一定时间内没有收到 ACK，就认为数据可能丢失，会重新发送该数据。除此之外，TCP 还支持**快速重传**，当接收方连续收到三个相同 ACK 时，说明中间的数据段可能丢失，发送方会立即重传，而不需要等待超时。

然后，TCP 通过**滑动窗口机制实现流量控制**。接收方会告诉发送方自己的接收窗口大小，发送方根据这个窗口控制发送速度，避免发送过快导致接收方缓冲区溢出。

同时，TCP 通过**拥塞控制机制**避免网络拥塞。TCP 会根据网络状况动态调整发送窗口大小，包括慢启动、拥塞避免、快速重传和快速恢复等算法，从而提高网络传输效率。

最后，TCP 通过**三次握手建立可靠连接，通过四次挥手关闭连接**，保证通信双方确认彼此状态，避免数据丢失。

因此，TCP 通过**确认机制保证数据收到，通过序列号保证数据有序，通过重传机制保证数据不丢失，通过流量控制和拥塞控制保证传输稳定**，最终实现可靠的数据传输。

| 机制 | 解决的问题 | 原理 |
| --- | --- | --- |
| **序列号** | 数据乱序、重复 | 给每个字节编号，接收方按编号排序 |
| **ACK确认** | 不知道数据是否到达 | 接收方返回确认号 |
| **超时重传** | 数据丢失 | ACK超时重新发送 |
| **快速重传** | 快速发现丢包 | 收到3个重复ACK立即重传 |
| **滑动窗口** | 发送速度过快 | 控制发送方发送量 |
| **拥塞控制** | 网络拥塞 | 根据网络情况调整发送速度 |
| **校验和** | 数据损坏 | 检测传输错误 |
| **连接管理** | 通信状态可靠 | 三次握手、四次挥手 |

## TCP滑动窗口是什么？
TCP 滑动窗口是一种**流量控制机制**，它允许发送方在不等待每个数据包确认的情况下，连续发送多个数据包，从而提高 TCP 的传输效率。

在 TCP 通信中，接收方会通过 TCP 首部中的 **Window 字段（接收窗口 rwnd）** 告诉发送方自己还能接收多少数据。发送方根据这个窗口大小控制发送量，保证不会因为发送过快导致接收方缓冲区溢出。

滑动窗口之所以叫“滑动”，是因为随着接收方不断返回 ACK，窗口会向前移动。例如，发送方一开始可以发送序号 1~5 的数据，当收到前两个数据的确认后，窗口就会向后移动，变成可以发送 6、7 等新的数据。

TCP 滑动窗口主要解决了两个问题：**提高传输效率和实现流量控制**。同时，TCP 还会结合拥塞窗口（cwnd）进行拥塞控制，最终发送窗口大小由**接收窗口 rwnd 和拥塞窗口 cwnd 两者中的较小值决定**。





![](https://cdn.nlark.com/yuque/__mermaid_v3/4067e6642b363ade89294e04f18939b4.svg)





## TCP流量控制是什么？
TCP 流量控制是指 **TCP 通过滑动窗口机制，让发送方的发送速度不要超过接收方的处理能力，从而避免接收方缓冲区溢出导致数据丢失**。

TCP 在连接建立时，接收方会通过 TCP 首部中的 **Window 字段（接收窗口 rwnd）** 告诉发送方自己当前还能接收多少数据。发送方根据这个窗口大小控制发送量，如果接收方处理速度较慢，接收窗口会不断减小，甚至变为 0，此时发送方会暂停发送；当接收方有空闲缓冲区后，会更新窗口大小，通知发送方继续发送。

简单来说，**流量控制解决的是“发送方太快，接收方来不及处理”的问题，它通过接收窗口动态调节发送速度，保证通信双方能够匹配。**

## TCP拥塞控制是什么？
TCP 拥塞控制是指 **TCP 根据网络当前的拥塞情况动态调整发送速率，避免大量数据同时进入网络导致网络拥堵，从而提高网络传输效率和稳定性**。

TCP 通过维护一个 **拥塞窗口 cwnd（congestion window）** 来限制发送方可以发送的数据量。发送方真正能够发送的数据量取决于 **发送窗口 = min(接收窗口 rwnd，拥塞窗口 cwnd)**。

TCP 拥塞控制主要包括四个阶段：**慢启动、拥塞避免、快速重传、快速恢复**。慢启动阶段通过指数增长快速探测网络容量；达到慢启动阈值后进入拥塞避免阶段，采用线性增长；当出现丢包时，TCP 判断网络可能发生拥塞，根据情况降低发送速率，并通过快速重传和快速恢复减少性能下降。

简单来说，**流量控制解决“接收方处理不过来”的问题，而拥塞控制解决“网络承载不过来”的问题。**

## TCP 拥塞窗口 cwnd 如何变化？  
TCP 拥塞窗口 **cwnd（congestion window）** 的变化主要经历 **慢启动、拥塞避免、快速恢复** 三个阶段。

在 TCP 连接刚建立时，cwnd 初始化为一个较小值（通常为若干 MSS），进入**慢启动阶段**，每收到一个 ACK，cwnd 按指数增长，大约每经过一个 RTT 翻倍。当 cwnd 增长到慢启动阈值 **ssthresh** 后，进入**拥塞避免阶段**，此时 cwnd 按线性方式增长，大约每经过一个 RTT 增加一个 MSS。

如果发生丢包，TCP 会根据丢包类型调整 cwnd：

+  如果是**超时重传**，说明网络可能发生严重拥塞，TCP 会将 cwnd 重置为较小值，通常恢复到 1~2 个 MSS，并重新进入慢启动，同时降低 ssthresh。 
+  如果是收到**三个重复 ACK**，说明网络仍然可以传输数据，只是发生了部分丢包，TCP 会执行快速重传，并进入快速恢复阶段，将 cwnd 减半，然后继续拥塞避免。 

所以，TCP 的核心思想是：**网络正常时逐渐增大发送速率，发生拥塞时快速降低发送速率，通过动态调整 cwnd 找到合适的传输速度。**

## TCP滑动窗口和拥塞窗口有什么区别？  
TCP 中的**滑动窗口**和**拥塞窗口**都是为了控制 TCP 数据发送速度，但解决的问题不同。

**滑动窗口主要解决的是接收端处理能力的问题，也叫流量控制。** TCP 会根据接收方返回的 `rwnd（Receive Window）` 动态调整发送窗口大小，避免发送方发送太快导致接收方缓冲区溢出。

**拥塞窗口主要解决的是网络拥塞问题，也叫拥塞控制。** TCP 会根据网络状况动态调整 `cwnd（Congestion Window）` 大小，避免发送过多数据导致网络拥塞。

| --- | --- | --- |
| **英文** | Receive Window | Congestion Window |
| **缩写** | rwnd | cwnd |
| **目的** | 流量控制 | 拥塞控制 |
| **防止** | 接收方处理不过来 | 网络堵塞 |
| **控制对象** | 接收端 | 网络 |
| **决定方** | 接收方通知 | 发送方根据网络判断 |
| **单位** | 字节 | MSS数量 |
| **是否动态变化** | 是 | 是 |








## TCP 有了超时重传为什么还需要快速重传？  
TCP 虽然有超时重传机制，但是超时重传存在一个明显问题：**等待时间较长，恢复速度慢**。因为 TCP 需要等待 RTO（重传超时时间）到期后，才会认为数据丢失并重新发送。而快速重传通过接收方连续返回多个重复 ACK，让发送方能够提前判断某个数据段丢失，不需要等待超时定时器，就可以立即重传，提高数据恢复速度。  



**超时重传和快速重传区别：**

| 对比 | 超时重传 | 快速重传 |
| --- | --- | --- |
| **触发条件** | RTO 超时 | 收到 3 个重复 ACK |
| **判断依据** | 时间 | ACK |
| **恢复速度** | 慢 | 快 |
| **是否等待计时器** | 是 | 否 |
| **适用情况** | 严重丢包、网络异常 | 少量丢包 |






## TCP三次握手过程
TCP 三次握手是客户端和服务器在建立 TCP 连接时进行的三次通信过程，目的是**确认双方的发送和接收能力正常，并同步双方的初始序列号**，为后续可靠传输做准备。

具体过程是：首先客户端主动发送 SYN 报文，表示希望建立连接，并携带客户端的初始序列号 seq=x；

服务器收到后返回 SYN+ACK 报文，其中 SYN 表示同意建立连接，ACK 表示确认收到客户端请求，同时携带服务器初始序列号 seq=y 和确认号 ack=x+1；客户端收到后再次发送 ACK 报文进行确认，确认号为 ack=y+1。完成三次握手后，双方建立 TCP 连接，可以开始数据传输。


![](https://cdn.nlark.com/yuque/__mermaid_v3/16da59a8af4207d5e5dcb447881749b2.svg)

**三次握手解决的问题：**

| 问题 | 解决方式 |
| --- | --- |
| 确认客户端能发送 | 第一次 SYN |
| 确认服务器能接收 | 第二次 SYN+ACK |
| 确认客户端能接收服务器数据 | 第三次 ACK |
| 同步双方序列号 | seq 和 ack |
| 避免历史连接影响 | 第三次确认 |






## 为什么 TCP 是三次握手，不是两次？  
TCP 三次握手的核心目的是**让通信双方确认彼此的发送能力和接收能力正常，同时建立初始序列号，避免历史连接的旧数据影响当前连接**。两次握手无法做到双方都确认对方的收发能力，也无法解决网络中延迟到达的旧连接请求问题。

第一次握手：客户端发送 SYN，表示客户端具有发送能力，并请求建立连接；第二次握手：服务端回复 SYN+ACK，表示服务端收到了客户端请求，并且自己的发送和接收能力正常；第三次握手：客户端回复 ACK，表示客户端收到了服务端响应，此时双方都确认连接可靠，正式建立 TCP 连接。





## 三次握手过程中可以携带数据吗？  
TCP 三次握手过程中，**前两次握手不能携带应用层数据，第三次握手可以携带数据**。原因是 TCP 连接还没有完全建立之前，服务端还无法确认客户端的合法性，因此不会接收应用数据；而第三次握手完成后，客户端已经确认服务端正常，此时可以携带数据发送。不过在实际应用中，第三次握手携带数据的情况比较少，通常还是等连接建立完成后再传输数据。  



![](https://cdn.nlark.com/yuque/__mermaid_v3/b6594274006425589cad3b44fb1221a7.svg)







## SYN 洪泛攻击是什么？如何解决？  
SYN 洪泛攻击（SYN Flood）是一种利用 TCP 三次握手机制进行的拒绝服务攻击。攻击者大量发送伪造源 IP 的 SYN 请求给服务器，但是不完成第三次握手，导致服务器为这些半连接请求分配资源并维护连接状态。当半连接队列被占满后，正常用户无法建立 TCP 连接，从而导致服务不可用。

解决 SYN 洪泛攻击主要有几种方式：第一，使用 **SYN Cookie**，服务器不立即保存半连接状态，而是根据 SYN 信息计算 Cookie，等客户端返回 ACK 后再验证并建立连接；第二，增大半连接队列大小，提高服务器承受能力；第三，限制单个 IP 的连接请求频率，过滤异常流量；第四，使用防火墙、负载均衡等设备进行流量清洗。

## SYN Cookie 的原理是什么？
SYN Cookie 是一种防御 SYN 洪泛攻击的机制，它的核心思想是**不在收到 SYN 请求时立即保存半连接状态，而是把连接信息编码到服务端返回的 SYN+ACK 中，等客户端返回 ACK 后再验证并建立连接**。

正常情况下，服务器收到 SYN 后会创建半连接并保存状态，而 SYN Flood 会利用这一点耗尽服务器资源。SYN Cookie 通过让服务器无状态化，避免大量半连接占用内存。

具体过程是：客户端发送 SYN 后，服务器根据客户端 IP、端口、服务器端口、时间戳等信息计算一个 Cookie，并将 Cookie 放入返回的 SYN+ACK 的序列号中；客户端收到后回复 ACK，服务器根据 ACK 中的 Cookie 重新计算并验证，如果验证通过，说明客户端确实收到了 SYN+ACK，此时再创建连接。



![](https://cdn.nlark.com/yuque/__mermaid_v3/026f52c41b3e24e94ee3986869fc79a6.svg)



**SYN Cookie 优缺点：**

| 类型 | 优点 | 缺点 |
| --- | --- | --- |
| **资源消耗** | 不需要为每个 SYN 请求保存半连接状态，避免半连接队列被占满，有效防御 SYN Flood | 每次收到 ACK 都需要重新计算 Cookie，会增加 CPU 计算压力 |
| **抗攻击能力** | 即使攻击者发送大量伪造 SYN，也不会大量消耗服务器内存资源 | 无法解决大规模 DDoS（例如攻击带宽超过服务器网络带宽） |
| **连接处理方式** | 将连接状态信息编码到 Cookie 中，实现服务器无状态化 | 服务器无法提前保存客户端连接信息 |
| **TCP 扩展支持** | 可以保证基本 TCP 三次握手正常完成 | 部分 TCP 扩展信息无法正常协商，例如窗口扩大（Window Scale）、SACK、时间戳等 |
| **实现成本** | 在 TCP 协议层实现简单，不需要额外硬件设备 | 需要修改 TCP 协议栈行为，不能完全替代其他防护方案 |
| **性能影响** | 正常情况下性能影响较小 | 高并发攻击时，大量 Cookie 计算可能造成 CPU 压力 |
| **适用场景** | 适合服务器遭受 SYN Flood 时快速保护连接资源 | 不适合作为唯一防御手段，需要结合防火墙、负载均衡、流量清洗等 |






## 为什么客户端最后一次 ACK 丢失，连接还能建立？  
客户端最后一次 ACK 丢失，TCP 连接**仍然可以建立**，因为服务器在收到客户端的 ACK 之前，已经处于 **SYN_RECV 状态**，而客户端收到服务器的 SYN+ACK 后，已经进入 **ESTABLISHED 状态**。如果客户端最后的 ACK 丢失，服务器会认为客户端没有收到 SYN+ACK，于是等待一段时间后重新发送 SYN+ACK；客户端收到重复的 SYN+ACK 后，会再次回复 ACK。只要双方最终完成确认，连接就可以正常建立。  





## TCP连接建立失败有哪些原因？
TCP 连接建立失败主要有以下几类原因：第一，**网络不可达**，比如路由异常、防火墙拦截、IP 地址错误；第二，**服务端没有监听对应端口**，比如服务未启动或者端口写错；第三，**服务端资源不足**，比如连接队列满、文件描述符耗尽，导致无法接受新的连接；第四，**TCP 三次握手过程中报文丢失或者超时**，比如 SYN 包、SYN+ACK 包丢失；第五，**服务端主动拒绝连接**，比如发送 RST 复位报文。因此排查 TCP 连接失败通常需要从网络连通性、服务端监听状态、系统资源和应用日志几个方面分析。  

| 错误 | 可能原因 |
| --- | --- |
| Connection refused | 服务没启动、端口没监听 |
| Connection timeout | 防火墙、网络不通、SYN丢失 |
| Network unreachable | 路由问题 |
| Connection reset | 对端发送RST |
| Too many open files | 文件描述符耗尽 |

## TCP四次挥手过程
TCP 四次挥手是 TCP 连接释放的过程，因为 TCP 是**全双工通信**，双方都可以独立发送和接收数据，所以关闭连接时需要双方分别关闭自己的发送方向，因此需要四次交互。

具体过程：

1. **客户端发送 FIN**
    -  表示客户端没有数据要发送了，请求关闭连接。 
    -  客户端进入 **FIN_WAIT_1** 状态。 
2. **服务器回复 ACK**
    -  表示已经收到客户端的关闭请求。 
    -  服务器进入 **CLOSE_WAIT** 状态。 
    -  此时服务器仍然可以继续发送剩余数据。 
3. **服务器发送 FIN**
    -  当服务器数据发送完成后，发送 FIN，表示服务器也没有数据发送了。 
    -  服务器进入 **LAST_ACK** 状态。 
4. **客户端回复 ACK**
    -  表示收到服务器的关闭请求。 
    -  客户端进入 **TIME_WAIT** 状态。 
    -  等待一段时间后关闭连接。





![](https://cdn.nlark.com/yuque/__mermaid_v3/9d7f2160d9f92cbeb7f99585c11a0c5a.svg)





## 为什么需要四次挥手，而不是三次？
TCP 需要四次挥手，而不是三次，主要原因是 **TCP 是全双工通信协议，连接关闭时需要双方分别关闭各自方向的数据传输，而双方的关闭请求不能同时完成**。当一方发送 FIN 表示自己已经没有数据需要发送时，另一方收到后只能先回复 ACK 表示确认收到，但此时另一方可能还有数据没有发送完成，不能立即发送 FIN。所以需要等待剩余数据发送完成后，再发送 FIN 请求关闭连接。因此 TCP 关闭过程需要两个方向分别进行关闭，最终形成四次挥手。  





## 为什么第二次和第三次不能合并？
TCP 四次挥手中，第二次挥手（ACK）和第三次挥手（FIN）通常不能合并，主要原因是**收到对方关闭请求，并不代表自己已经准备好关闭连接**。

当一方发送 FIN 时，只表示：“我这边没有数据需要发送了。”

但是另一方收到 FIN 后，可能还有数据没有发送完成，因此只能先发送 ACK 确认收到关闭请求，继续发送剩余数据。等自己的数据发送完成后，才能发送 FIN 表示关闭自己的发送方向。

所以：

+  ACK：表示“我知道你要关闭了” 
+  FIN：表示“我自己的数据也发送完了，可以关闭了” 

这两个动作发生的时间可能不同，因此需要分开，形成四次挥手。





## 如果服务器收到 FIN 后直接关闭，会有什么问题？  
如果服务器收到客户端的 FIN 后直接关闭连接，会导致**服务器可能还有未发送完成的数据丢失**。因为客户端发送 FIN 只代表客户端已经没有数据需要发送了，并不代表服务器也没有数据需要发送。如果服务器收到 FIN 后立即关闭自己的发送方向，那么服务器缓冲区中还未发送的数据就无法传输给客户端，造成数据丢失。因此 TCP 采用半关闭机制，服务器收到 FIN 后先发送 ACK 确认，然后继续发送剩余数据，等数据发送完成后再发送 FIN 关闭连接。  





## 为什么客户端最后需要等待 TIME_WAIT？  
客户端主动关闭连接后，需要等待 **TIME_WAIT 状态 2MSL 时间**，主要有两个原因：第一，保证客户端最后发送的 ACK 能够到达服务端，如果 ACK 丢失，服务端会重新发送 FIN，客户端可以在 TIME_WAIT 状态下再次回复 ACK；第二，防止旧连接的数据包影响新的连接，等待网络中残留的旧数据包消失，避免新连接收到错误数据。





## CLOSE_WAIT 过多说明什么问题？
CLOSE_WAIT 过多通常说明服务端程序没有正确关闭 Socket 连接。因为 CLOSE_WAIT 表示对方已经发送 FIN，TCP 协议栈已经收到并确认，但是本端应用程序还没有调用 close() 关闭连接，所以大量 CLOSE_WAIT 一般是代码层面的连接释放问题，比如没有关闭连接、异常情况下没有释放资源，导致连接一直占用。

  

**CLOSE_WAIT 和 TIME_WAIT 区别：**

| 状态 | 出现在哪一方 | 原因 | 过多说明 |
| --- | --- | --- | --- |
| **TIME_WAIT** | 主动关闭方 | 等待2MSL，保证可靠关闭 | 连接关闭太频繁 |
| **CLOSE_WAIT** | 被动关闭方 | 等待应用调用close | 程序没有释放连接 |






## TCP半关闭是什么？
TCP 半关闭是指 TCP 连接的一端关闭了发送方向，但是仍然可以接收对方发送的数据。因为 TCP 的连接是全双工的，发送和接收两个方向是独立的，所以一方发送 FIN 后，只代表自己不会再发送数据了，但仍然可以继续接收数据。TCP 半关闭主要通过 shutdown() 实现，在四次挥手过程中也会出现类似状态。  

```java
Socket socket = new Socket(host, port);

// 关闭发送方向
socket.shutdownOutput();

// 仍然可以接收服务端数据
InputStream in = socket.getInputStream();
```

| --- | --- |
| shutdownOutput() | 关闭发送方向，进入半关闭 |
| shutdownInput() | 关闭接收方向 |
| close() | 关闭整个Socket连接 |






## TCP如何处理丢包？
TCP 主要通过**确认机制、超时重传、快速重传、滑动窗口**和**流量控制**等机制来处理丢包。当发送方发送数据后，会等待接收方的 ACK 确认，如果超过一定时间没有收到 ACK，就认为数据丢失，会触发超时重传；如果接收方连续收到后续数据但发现中间某个数据包缺失，会通过重复 ACK 通知发送方，发送方收到多个重复 ACK 后会触发快速重传。除此之外，TCP 还通过序列号保证数据顺序，通过滑动窗口控制发送速度，从而保证数据可靠、有序地传输。

## TCP为什么会产生粘包和拆包？
TCP 会产生粘包和拆包，根本原因是 **TCP 是面向字节流的协议，而不是面向消息的协议**。TCP 只保证数据的可靠传输，不会保留应用层数据包的边界，因此发送方发送的多个数据包，到了接收方可能会被合并读取，也可能被拆分读取。

产生粘包和拆包主要有三个原因：

第一，**TCP 底层会根据网络情况对数据进行分段传输**。如果应用层发送的数据较大，超过 MSS（最大报文段长度），TCP 会将数据拆分成多个 TCP 段发送，接收方读取时可能需要多次才能完整接收，这就是拆包。

第二，**TCP 会进行缓冲优化**。如果应用层连续发送多个较小的数据，TCP 可能会将多个小数据合并成一个 TCP 段发送，接收方一次读取时可能会读到多个完整消息，这就是粘包。

第三，**接收方读取数据的方式也会影响**。TCP 接收缓冲区是一个连续的字节流，应用程序调用 read() 或 recv() 时，只能读取当前缓冲区中的一部分数据，并不知道一次读取的数据对应几个业务消息，因此可能产生粘包或拆包。

因此，TCP 本身没有粘包问题，**粘包和拆包是应用层基于 TCP 实现消息通信时产生的问题**，需要应用层定义消息边界进行解决。

| 原因 | 说明 |
| --- | --- |
| TCP 面向字节流 | 没有消息边界 |
| 发送缓冲区合并 | 多个小包可能合并发送 |
| MSS 限制 | 大数据会被拆分 |
| 网络传输优化 | TCP 会调整发送策略 |
| 接收读取大小不确定 | 一次 recv 不一定对应一次 send |

## 如何解决 TCP 粘包拆包/Netty如何解决TCP粘包？  
TCP 粘包和拆包问题的本质是 **TCP 面向字节流，没有消息边界**。因此解决 TCP 粘包拆包不能依靠 TCP 本身，而需要在**应用层协议中定义消息边界**。

常见解决方案有四种：

第一，**固定长度协议**。规定每个消息大小固定，例如每条消息都是 100 字节，接收方按照固定长度读取即可。优点是实现简单，缺点是容易造成空间浪费。

第二，**消息头 + 消息体方式**，这是最常用的方案。在消息头中添加消息长度字段，例如：

> +----------+-------------+  
| 长度字段  |  消息内容    |  
+----------+-------------+
>

接收方先读取消息长度，再根据长度读取完整消息，可以准确区分多个消息。

第三，**使用分隔符协议**。例如规定每条消息以换行符 `\n` 结束：

> Hello\n
>
> World\n
>

第四，**使用应用层协议**。例如 HTTP、WebSocket、RPC 框架都会设计自己的消息格式，通过协议字段解决 TCP 的边界问题。  





## TCP为什么会粘包，而UDP不会？  
TCP 会产生粘包问题，而 UDP 不会，主要原因是 **TCP 是面向字节流的协议，而 UDP 是面向报文的协议**。

TCP 传输的数据没有消息边界的概念，发送方多次调用 `send()` 发送的数据，在接收方看来只是连续的一段字节流，TCP 只保证数据可靠、有序到达，并不会保留应用层的数据包边界。因此，多个 TCP 数据包可能被合并成一次接收，也可能一个 TCP 数据包被拆成多次接收，这就是 TCP 的粘包和拆包问题。

而 UDP 是面向报文的，每次发送的 UDP 数据报都有明确边界，接收方调用 `recvfrom()` 时，一次对应一个完整的 UDP 报文，所以不会出现 TCP 那样的粘包和拆包问题。





## TCP粘包一定发生吗？
TCP 粘包**不一定会发生**。更准确地说，TCP 协议本身存在产生粘包和拆包的可能，但是否真正发生取决于发送方式、网络情况以及接收方读取方式。

TCP 是面向字节流的协议，它只保证字节可靠、有序地传输，并不会维护应用层消息边界。因此，如果应用层连续发送多个小数据，TCP 可能会将它们合并发送，导致接收方一次读取多个消息，也就是粘包；如果发送的数据较大，TCP 可能会拆分成多个 TCP 段发送，导致接收方多次读取一个完整消息，也就是拆包。

但是，如果发送方发送数据间隔较长，或者每次发送的数据大小刚好满足接收方读取需求，也可能不会出现明显的粘包现象。

因此，**TCP 粘包不是必然发生的问题，而是应用层基于 TCP 进行消息通信时必须考虑的问题，解决方式是在应用层协议中定义消息边界。**

## TCP为什么不设计成面向消息的协议？  
TCP 不设计成面向消息的协议，主要是因为 **TCP 的核心目标是提供可靠、高效的字节流传输，而消息边界属于应用层的需求，不应该由传输层决定**。

如果 TCP 强行维护消息边界，就需要在传输过程中保存和处理消息结构，会增加协议复杂度和传输开销，同时也降低了 TCP 的通用性。不同应用对消息的定义不同，例如 HTTP 请求、文件数据、实时通信消息，它们的消息格式和大小都不一样，TCP 很难设计一种统一的消息边界规则。

因此 TCP 选择提供无边界的字节流，让应用层根据自身需求定义消息格式，例如通过长度字段、分隔符等方式解决粘包拆包问题。





## HTTP协议为什么不会出现粘包问题？
HTTP 协议**并不是不会出现 TCP 粘包问题**，因为 HTTP 底层仍然基于 TCP，而 TCP 本身是面向字节流的，同样可能发生粘包和拆包。

之所以我们通常认为 HTTP 不存在粘包问题，是因为 **HTTP 在应用层定义了明确的消息边界**。HTTP 请求和响应都有自己的格式，例如通过请求行、请求头、空行以及消息体长度字段来确定一条 HTTP 消息的结束位置。

例如 HTTP/1.1 中：

+  如果存在 `Content-Length`，表示消息体的固定长度； 
+  如果使用 `Transfer-Encoding: chunked`，通过分块编码表示消息结束； 
+  HTTP/2 使用二进制 Frame 帧结构，也有明确的数据边界。 

因此，即使 TCP 底层把多个 HTTP 请求合并到一个 TCP 数据流中，或者把一个 HTTP 请求拆成多个 TCP 段，HTTP 层仍然可以根据协议规则正确解析出完整消息。

所以准确来说：

>  HTTP 不是避免了 TCP 粘包，而是通过应用层协议设计解决了 TCP 字节流没有消息边界的问题。  
>

## 长连接为什么容易出现粘包？
长连接更容易出现粘包，并不是因为长连接本身会导致粘包，而是因为**长连接会让多个业务消息复用同一个 TCP 连接，多个消息会连续存在于同一个 TCP 字节流中**，从而增加了 TCP 合并多个消息发送的可能性。

TCP 是面向字节流的协议，它不会记录应用层消息边界。在短连接中，一个连接通常只传输少量数据，连接关闭后消息边界比较容易区分；而长连接会持续传输多个请求和响应，如果应用层没有设计明确的消息边界，就可能出现多个消息被 TCP 合并发送，导致接收方一次读取多个消息，也就是粘包。

因此，**长连接不是粘包的根本原因，TCP 无消息边界才是根本原因，长连接只是增加了多个消息连续传输的场景。**

## HTTP长连接如何实现？
HTTP 长连接是指**客户端和服务器建立 TCP 连接后，在一次 HTTP 请求响应完成后不立即关闭连接，而是复用这个 TCP 连接继续处理后续 HTTP 请求**。HTTP/1.1 默认开启长连接，通过请求头和响应头中的 `Connection: keep-alive` 控制。服务器会维护这个 TCP 连接，在连接空闲超过一定时间或达到最大请求数量后关闭连接。长连接减少了 TCP 三次握手和四次挥手的开销，提高了多个请求场景下的访问效率。  





## HTTP协议特点是什么？
HTTP（HyperText Transfer Protocol，超文本传输协议）是一种**应用层协议**，主要用于客户端和服务器之间进行数据通信。它具有以下几个特点：第一，**基于请求-响应模型**，客户端主动发送 HTTP 请求，服务器根据请求返回响应；第二，**无状态**，HTTP 默认不会保存客户端之前的请求信息，每次请求都是独立的，不过可以通过 Cookie、Session、Token 等机制实现状态保持；第三，**简单灵活**，HTTP 使用文本格式传输数据，支持多种数据类型，例如 HTML、JSON、图片、视频等；第四，**可扩展性强**，HTTP 通过请求头和响应头可以不断扩展新的功能，例如缓存、认证、跨域控制等；第五，**基于 TCP 协议，可靠传输**，HTTP/1.1 和 HTTP/2 通常基于 TCP，保证数据可靠到达，HTTP/3 则基于 QUIC 协议；第六，**支持长连接**，HTTP/1.1 默认开启 Keep-Alive，可以复用 TCP 连接，减少频繁建立连接的开销。  





## HTTP为什么是无状态协议？
HTTP 是无状态协议，指的是**服务器不会保存客户端之前请求的状态信息，每一次 HTTP 请求都是相互独立的**。也就是说，服务器处理当前请求时，并不知道客户端之前发送过什么请求。例如，用户第一次登录成功后，服务器不会自动记住用户身份，当用户再次访问其他接口时，仍然需要重新携带身份信息。HTTP 设计成无状态主要是为了**简化服务器设计、降低服务器压力，提高系统的扩展性**。如果需要保存用户状态，可以通过 Cookie、Session、Token 等机制在 HTTP 之上实现状态管理。  





## HTTP 无状态是不是代表服务器不能保存任何数据？  
不是。**HTTP 无状态并不代表服务器不能保存任何数据，而是指 HTTP 协议本身不会自动保存客户端之前请求的信息，每一次请求对服务器来说都是独立的。** 服务器当然可以保存数据，例如通过 Session、Redis、数据库等方式保存用户登录状态、购物车信息等业务数据。区别在于，这些状态信息不是由 HTTP 协议维护的，而是由应用层自己实现的。  





## Cookie和Session区别？
Cookie 和 Session 都是用来解决 **HTTP 无状态问题** 的机制，主要区别在于**存储位置和实现方式不同**。Cookie 是由服务器发送给客户端，客户端保存的一小段数据，之后每次请求都会自动携带 Cookie 发送给服务器；Session 是服务器端保存用户状态的一种机制，服务器会为每个用户创建一个 Session，并通过 Cookie 中保存的 SessionId 来找到对应的 Session 数据。由于 Cookie 数据存储在客户端，容易被用户查看和篡改，安全性较低；而 Session 数据存储在服务器端，安全性更高。但是 Session 会占用服务器内存，并且在分布式环境下需要考虑 Session 共享问题。实际开发中通常使用 Cookie 保存一些非敏感信息，比如用户偏好、Token 等，而用户登录状态等敏感信息一般使用 Session 或基于 Token 的方案保存。  

| 对比项 | Cookie | Session |
| --- | --- | --- |
| **本质** | 客户端保存数据 | 服务端保存数据 |
| **位置** | 浏览器 | 服务器 |
| **保存内容** | 用户信息、偏好等 | 用户状态 |
| **安全性** | 较低 | 较高 |
| **服务器压力** | 小 | 大 |
| **是否依赖Cookie** | 不依赖 | 传统实现依赖 |
| **分布式问题** | 基本没有 | 需要解决 |
| **常见用途** | 记住账号、用户配置 | 登录状态管理 |

## Token和Session区别？
Token 和 Session 都是用来解决 HTTP 无状态问题，实现用户身份认证的机制。它们最大的区别在于**用户状态保存的位置不同**。**Session** 是一种有状态认证方式，用户登录后，服务器会创建 Session 保存用户信息，并返回一个 SessionId 给客户端，客户端之后携带 SessionId 请求，服务器根据 SessionId 查找对应的用户信息；而 **Token** 是一种无状态认证方式，服务器登录成功后生成一个 Token 返回给客户端，客户端每次请求携带 Token，服务器通过验证 Token 的有效性来确认用户身份，不需要保存用户状态。Session 依赖服务器存储用户信息，安全性较高，但在分布式环境下需要解决 Session 共享问题；Token 不需要服务器保存用户状态，更适合分布式和微服务架构，但 Token 一旦泄露，在有效期内可能被攻击者使用。因此现在很多互联网系统，尤其是前后端分离和微服务项目，更倾向于使用 Token 进行身份认证。

## HTTP请求有哪些方法？
HTTP 请求方法是客户端告诉服务器希望对资源执行什么操作的方式。常见的 HTTP 方法包括 **GET、POST、PUT、DELETE、PATCH、HEAD、OPTIONS** 等。

其中：

+ **GET**：用于获取资源，通常用于查询数据。 
+ **POST**：用于提交数据，通常用于创建资源或执行某些操作。 
+ **PUT**：用于更新资源，通常表示整体替换资源。 
+ **PATCH**：用于部分更新资源。 
+ **DELETE**：用于删除资源。 
+ **HEAD**：类似 GET，但只返回响应头，不返回响应体，常用于检查资源是否存在或获取资源信息。 
+ **OPTIONS**：用于查询服务器支持哪些 HTTP 方法，常用于 CORS 跨域预检请求。





## GET 和 POST 有什么区别？  
GET 主要用于**获取资源**，请求参数通常放在 URL 的查询字符串中，例如 `?id=1`；POST 主要用于**提交数据或修改资源**，参数通常放在请求体（Request Body）中。

GET 请求具有**幂等性**，多次请求相同资源，结果通常不会发生变化；POST 一般不具有幂等性，多次提交可能产生不同结果，例如重复创建订单。

GET 请求的数据会暴露在 URL 中，因此不适合传输敏感信息；POST 参数放在请求体中，相对更加安全，但两者都不是绝对安全的，真正的安全需要依靠 HTTPS 加密。

另外，GET 请求通常可以被浏览器缓存、保存到书签，并且可以被收藏和分享；POST 请求一般不会被缓存，也不能直接通过 URL 访问。

需要注意的是，GET 和 POST 的本质区别不是“GET 没有请求体，POST 有请求体”，因为 HTTP 协议允许 GET 携带请求体，只是实际开发中通常不这么使用。

| 区别 | GET | POST |
| --- | --- | --- |
| **作用** | 获取资源 | 提交数据 |
| **参数位置** | URL | Request Body |
| **是否幂等** | 是 | 通常不是 |
| **是否安全** | 不是 | 不是 |
| **是否缓存** | 可以 | 默认不缓存 |
| **是否收藏** | 可以 | 不可以 |
| **数据量** | 较小 | 较大 |
| **典型场景** | 查询 | 新增、提交 |






## POST一定比GET安全吗？
POST **不一定比 GET 更安全**。很多人认为 POST 安全，是因为 POST 的参数通常放在请求体中，而 GET 参数放在 URL 中，看起来 POST 不会暴露参数。但实际上，**HTTP 本身是明文传输协议，如果没有 HTTPS 加密，GET 和 POST 的数据都可能被抓包获取**。

GET 和 POST 的安全性主要区别在于数据暴露方式：

+  GET 参数放在 URL 中，会出现在浏览器历史记录、缓存、服务器访问日志、Referer 等地方，更容易被泄露。 
+  POST 参数放在请求体中，不会直接显示在 URL 中，但仍然可以被抓包工具查看。





## 为什么登录一般使用POST？
登录一般使用 POST，主要是因为登录操作本质上是**向服务器提交用户认证信息，并可能改变服务器状态**，符合 POST 的语义。

相比 GET，POST 将用户名、密码等参数放在请求体中，不会直接暴露在 URL 中，可以避免参数出现在浏览器历史记录、服务器访问日志、Referer 等位置。同时 POST 对请求体大小没有 URL 那样的限制，更适合提交复杂的认证数据。

但是需要注意，**POST 本身并不能保证安全**，如果使用 HTTP 明文传输，用户名和密码仍然可能被窃取。真正保证登录安全的是 HTTPS，通过 TLS 对数据进行加密。





## HTTP1.0、HTTP1.1、HTTP2.0区别？
HTTP/1.0、HTTP/1.1 和 HTTP/2.0 的主要区别体现在**连接方式、传输效率和协议格式**上。

**HTTP/1.0** 默认采用短连接，每次请求都需要重新建立 TCP 连接，效率较低；**HTTP/1.1** 默认支持长连接，通过 Keep-Alive 复用 TCP 连接，同时引入了缓存控制、分块传输等机制，提高了性能；**HTTP/2.0 **在 HTTP/1.1 的基础上进行了性能优化，采用二进制分帧、多路复用、Header 压缩和服务器推送等技术，可以在同一个 TCP 连接中并发处理多个请求，进一步提升传输效率。不过 HTTP/2.0 仍然基于 TCP，因此存在 TCP 层面的队头阻塞问题，而 HTTP/3.0 使用 QUIC 基于 UDP 解决了这个问题。

| 对比项 | HTTP/1.0 | HTTP/1.1 | HTTP/2.0 |
| --- | --- | --- | --- |
| **发布时间** | 1996年 | 1997年 | 2015年 |
| **连接方式** | 默认短连接 | 默认长连接（Keep-Alive） | 长连接 |
| **TCP连接复用** | ❌ 不支持，一个请求一个连接 | ✅ 支持，多个请求复用 TCP 连接 | ✅ 支持，一个连接处理多个请求 |
| **数据传输格式** | 文本格式 | 文本格式 | 二进制格式 |
| **请求方式** | 请求完成后才能处理下一次请求 | 支持 Pipeline（管线化），但实际应用少 | 支持多路复用 |
| **多路复用** | ❌ 不支持 | ❌ 不支持（本质串行） | ✅ 支持多个请求并行传输 |
| **队头阻塞** | 严重（连接级阻塞） | 存在（HTTP层阻塞） | 解决 HTTP 层队头阻塞，但仍存在 TCP 层队头阻塞 |
| **Header传输** | 每次完整发送 | 每次完整发送 | 使用 HPACK 压缩 Header |

| **缓存控制** | Expires | Cache-Control、ETag、Last-Modified | 继承 HTTP/1.1 |
| **Host字段** | ❌ 不支持 | ✅ 支持 | ✅ 支持 |
| **分块传输** | ❌ 不支持 | ✅ 支持 Transfer-Encoding: chunked | 通过二进制帧实现 |
| **服务器推送** | ❌ 不支持 | ❌ 不支持 | ✅ 支持 Server Push |
| **性能** | 较低 | 较高 | 最高 |
| **适用场景** | 简单网页访问（已淘汰） | 目前大量网站仍使用 | 现代高性能网站和接口 |

| --- | --- |
| **HTTP/1.0 最大问题？** | 每次请求都建立 TCP 连接，性能差 |
| **HTTP/1.1 最大改进？** | 默认长连接，减少 TCP 建立次数 |
| **HTTP/1.1 有什么缺点？** | 请求仍然串行，存在队头阻塞 |

## HTTP2.0多路复用原理？
HTTP/2.0 的多路复用是指**在同一个 TCP 连接上，可以同时传输多个 HTTP 请求和响应，而不需要为每个请求建立单独的连接**。它主要通过引入 **二进制分帧、Stream（流）和 Frame（帧）机制** 实现。HTTP/2.0 会把每个请求和响应拆分成多个二进制帧，并给每个请求分配一个独立的 Stream ID，不同请求的帧可以在同一个 TCP 连接中交错传输，服务器和客户端根据 Stream ID 重新组装完整的请求和响应。这样避免了 HTTP/1.1 中多个请求之间相互阻塞的问题，提高了连接利用率和并发性能。

## HTTP/2.0 为什么采用二进制协议？  
HTTP/2 使用二进制协议主要是为了**提高解析效率、减少解析歧义、支持多路复用以及方便协议扩展**。HTTP/1.1 使用的是文本协议，数据以字符串形式传输，虽然人类容易阅读，但是存在解析复杂、性能较低的问题，例如需要处理空格、换行、大小写等格式。而 HTTP/2 将 HTTP 消息拆分成二进制 Frame，通过固定格式的字段进行解析，客户端和服务器可以直接按照协议定义读取数据，不需要进行字符串解析。同时，二进制分帧机制也是 HTTP/2 实现多路复用的基础，不同请求可以通过不同 Stream 的 Frame 在同一个 TCP 连接中交错传输。因此 HTTP/2 采用二进制协议能够提升传输效率和协议扩展能力。  





## HTTP/2 .0 为什么不能不用 TCP？  
HTTP/2.0 不能不用 TCP，主要是因为 TCP 已经提供了成熟的可靠传输能力，而 HTTP/2,0 只负责应用层的通信优化。如果不用 TCP，而改用 UDP，HTTP/2,0 就需要自己实现 TCP 已经提供的功能，例如数据可靠传输、丢包重传、数据排序、流量控制和拥塞控制，这会大幅增加协议复杂度。同时，TCP 经过几十年的优化，在网络环境中具有非常好的兼容性和稳定性。因此 HTTP/2,0 选择继续基于 TCP，通过二进制分帧和多路复用提升 HTTP 性能，而不是重新实现一个传输层协议。不过 TCP 存在队头阻塞问题，这也是 HTTP/3 使用 QUIC（基于 UDP）协议的原因。  





## HTTP/3.0是什么？  
HTTP/3,0 是 HTTP 协议的第三个主要版本，它最大的变化是**不再基于 TCP，而是基于 QUIC 协议运行**。QUIC 是建立在 UDP 之上的新一代传输协议，它将 TCP 的可靠传输、拥塞控制、TLS 加密等能力集成到了 UDP 上。HTTP/3.0 主要解决了 HTTP/2.0 在 TCP 上存在的队头阻塞问题，同时通过 0-RTT 建连、连接迁移、多路复用等机制降低延迟，提高弱网络环境下的通信性能。

## HTTP/3.0 如何解决 TCP 队头阻塞？ 
HTTP/3 通过**使用 QUIC 协议替代 TCP** 来解决 TCP 队头阻塞问题。HTTP/2 虽然实现了多路复用，但多个请求共享一个 TCP 连接，而 TCP 保证数据必须按顺序交付，因此只要某一个 TCP 数据包丢失，后续所有数据都必须等待重传，导致其他 HTTP 请求也被阻塞。HTTP/3 基于 QUIC，在 QUIC 层将数据拆分为多个独立的 Stream，每个 Stream 都有自己的可靠传输机制，一个 Stream 丢包只会影响当前 Stream，不会阻塞其他 Stream，从而解决了 TCP 层的队头阻塞问题。   





## HTTP和HTTPS区别？
**HTTP 和 HTTPS 都是用于客户端和服务器之间传输数据的应用层协议，最大的区别是 HTTPS 在 HTTP 的基础上增加了 SSL/TLS 加密层，使数据传输更加安全。** HTTP 默认使用 80 端口，数据以明文形式传输，容易被窃听和篡改；HTTPS 默认使用 443 端口，通过 TLS 提供数据加密、身份认证和数据完整性保护。  

| 对比 | HTTP | HTTPS |
| --- | --- | --- |
| **协议名称** | 超文本传输协议 | 超文本传输安全协议 |
| **安全性** | 明文传输，不安全 | TLS 加密传输，更安全 |
| **默认端口** | 80 | 443 |
| **传输方式** | HTTP直接基于TCP | HTTP + TLS + TCP |
| **身份认证** | 没有 | 通过证书验证服务器身份 |
| **数据完整性** | 无法保证 | TLS防止数据被篡改 |
| **性能** | 速度稍快 | 需要TLS握手，有额外开销 |
| **应用场景** | 普通网页、内部服务 | 支付、登录、敏感数据传输 |

## HTTPS 为什么不用非对称加密传输所有数据？  
HTTPS 不使用非对称加密传输所有数据，主要原因是**非对称加密性能太差，不适合大量数据传输**。HTTPS 采用的是**混合加密机制**：首先通过非对称加密（如 RSA、ECC）解决密钥交换和身份认证问题，双方协商出一个对称加密密钥；之后真正传输业务数据时，使用性能更高的对称加密算法（如 AES、ChaCha20）进行加密。这样既保证了安全性，又提高了传输效率。

| --- | --- | --- |
| **密钥数量** | 一个密钥 | 公钥+私钥 |
| **加密速度** | 快 | 慢 |
| **适合场景** | 大量数据传输 | 密钥交换、身份认证 |
| **常见算法** | AES、ChaCha20 | RSA、ECC |






## 非对称加密在 HTTPS 中负责什么？
**在 HTTPS 中，非对称加密主要负责身份认证和密钥交换，而不是负责加密实际传输的数据。** 因为非对称加密计算复杂、速度较慢，不适合大量数据传输；HTTPS 通常在 TLS 握手阶段使用非对称加密建立安全连接，之后使用协商出的对称密钥进行数据加密传输。  





## 中间人攻击是什么？如何防止？
 中间人攻击是指**攻击者插入到通信双方之间，伪装成双方进行通信，并窃取或篡改数据的一种攻击方式**。客户端以为自己在和服务器通信，服务器也以为自己在和客户端通信，但实际上双方的数据都经过攻击者转发。HTTPS 主要通过**数字证书、CA 机构认证、TLS 加密和身份校验机制**来防止中间人攻击。

## DNS解析过程是什么？
DNS 解析过程是将**域名转换成 IP 地址**的过程。当用户在浏览器输入域名后，首先会查询浏览器缓存、操作系统缓存以及本地 DNS 缓存，如果都没有找到，则会向本地 DNS 服务器发起查询。本地 DNS 服务器会采用递归查询和迭代查询的方式，依次向根 DNS 服务器、顶级域名服务器、权威 DNS 服务器查询，最终获取目标域名对应的 IP 地址，并返回给客户端。客户端拿到 IP 后，就可以通过 IP 地址与服务器建立 TCP 连接，后续进行 HTTP/HTTPS 通信。

## DNS为什么使用UDP？
DNS 默认使用 UDP 协议，主要是因为 **DNS 查询具有请求简单、数据量小、实时性要求高的特点**。UDP 不需要建立连接，传输开销小，可以快速完成域名解析，提高访问速度。同时 DNS 查询和响应通常都在一个数据包内完成，不需要 TCP 的可靠传输机制。如果 DNS 响应数据过大，或者需要保证可靠传输时，DNS 会切换使用 TCP 协议。  





## DNS为什么有时候使用TCP？
DNS 有时候使用 TCP，主要是因为 **UDP 存在数据包大小限制和可靠性不足的问题**。当 DNS 响应数据过大，超过 UDP 能承载的范围时，客户端会改用 TCP 重新查询；另外 DNS 服务器之间进行区域传送时，需要传输大量 DNS 记录，为了保证数据完整可靠，也会使用 TCP。因此 DNS 并不是只使用 UDP，而是根据场景选择 UDP 或 TCP。  





## CDN是什么？原理是什么？
CDN（Content Delivery Network，内容分发网络）是一种**利用分布在各地的边缘节点服务器，将用户请求就近分发，从而提高访问速度、降低源站压力的技术**。它的核心原理是通过 DNS 解析将用户请求调度到距离用户最近、状态最好的 CDN 节点，如果 CDN 节点缓存了用户请求的资源，就直接返回；如果没有缓存，则向源站请求资源并缓存下来，再返回给用户。通过这种方式减少网络延迟，提高网站访问速度，同时降低源服务器压力。

| **跨地域访问慢** | 区域化部署 |


---

**CDN和反向代理区别：**

|  | CDN | 反向代理 |
| --- | --- | --- |
| **目的** | 加速访问 | 代理请求 |
| **部署位置** | 全球边缘节点 | 服务器前端 |
| **主要作用** | 缓存静态资源 | 隐藏源站、负载均衡 |
| **典型场景** | 图片、视频、文件 | Web服务 |
